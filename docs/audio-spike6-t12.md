- 音: **調整用の合成だけ**（音色 A・レベル B2 の 18 本、種・型の順に並べて 1・3・5 分につなぐ。44.1 kHz モノ、`out/bass-perf/`、gitignore）。開発用・ホールドアウト・録音は開いていない。

  - JSON: Worker の `JSON.stringify(result).length`。

## 直したところ（出力は同じ）

最初の計測（直す前）では、ベースの段階のうち `bass`（低い CQT の後の B-1〜B-3 とルートの決め直し）が 1・3・5 分で 0.03・0.09・0.25 s と、長さより速く伸びていた（5 分のベースの段階 2.96 s、5 回 2.89〜2.99）。

- 原因: B-3（`cliche.ts` の `splitByBass`）が和音の区間ごとに `segmentBass` を呼び、`segmentBass` が呼ばれるたびに曲全体のベースの音の強さの和（`salience`、36 行 × 全部の列 × 倍音 4）を計算し直していた。区間の数 × 曲の長さで伸びる（5 分で 179 回 × 1.9 MB の確保）。G2 で `cliche.split` を既定の入にしたので効くようになった。
- 直し: `segmentBass.ts` の `salience` を、同じ `LowCqt` と倍音の数なら 1 回だけ計算して使い回す（`WeakMap`）。値は同じ配列そのもの。低い CQT は `lowCqt()` の後で書き換えない。
- 効き目: `bass` 5 分 0.25 → 0.02 s。ベースの段階の中央値 2.96 → 2.81 s（低い CQT は 2.71・2.78 s で、その差は回のゆれ）。

出力が同じことの確かめ:

- 調整用の合成 72 本を `cli.ts --all`（ベースあり、`BAND_SHEETS_COMMIT=adc1c61`）で直す前と後に通し、結果の JSON が `analyzer.timingsSec` を除いて **72 本すべて同じ**（和音 1,769・`/X` 125・失敗 0 も同じ）。ハッシュ `e5b432a11e3c`。
- ブラウザでも和音・`/X`・JSON の大きさが直す前と同じ（JSON の ±1 B は時間の桁）。
- テスト: `ts/bass` 全部、spikes 全体（vitest 1,022 通る・45 飛ばす）、`tsc --noEmit -p spikes/analysis/tsconfig.json`、`bassBench.spec.ts`（T7）、`bassPerf.spec.ts` が通る。`config.test.ts` の固定のハッシュ（あり `e5b432a11e3c`・既定 `9c4d53b4e54e`）とゴールデンは変えていない。`segmentBass.test.ts` に「同じ `LowCqt` では 1 回だけ」「区間ごとに呼んでもまとめて呼んでも同じ」を足した。

## 残る時間の中身と選択肢（ユーザーへ）

残りのほとんどは低い CQT（5 分 2.78 s）で、凍結の `ts/dsp/core/cqt.ts` の中（Node で測ると約 3 分の 1 が調律の推定 `estimateTuning`、残りが 5 オクターブの CQT）。出力を変えずにベースのコードの中だけで縮められるところは見つからなかった。枠の中だが余裕は 0.2 s で、遅い PC では越える見込み。越えたときの案:

1. 低い CQT を別の Worker で v1a と並べて走らせる（出力は同じ。足す時間はほぼ 0 になるが、22 kHz の音の写し 5 分 26 MB と Worker 1 つ分のメモリが増える。Worker の作りの変更なので main の統合で決める）。
2. 調律を v1a の推定から借りる（v1a は打楽器を除いた音で推定するので値が少し違い、**出力が変わる**。調整用でやり直しが要る）。約 3 分の 1 減る見込み。
3. 計画 §6 の決定 2 のとおり、v1a の CQT を使い回す（凍結の `chroma.ts` を変えるので main で）。

大きさは 6 KB の枠の中だが、main の Worker の枠 60 KB は 65 B しか残らない。main に入れるときは、枠の決め方（スパイク 5 の持ち越しの質問 2 と同じ）を main で決める。
