# スパイク 2 タスク計画: 本物の録音に強いコード・拍・セクション（案）

2026-10-11 作成（下書き。「ユーザーに決めてほしいこと」の返事を受けて確定する）。土台はスパイク 1（`audio-spike1-plan.md`、レビュー `audio-spike1-review.md`・`audio-spike1-t15-review.md`）と、全体の進め方 `audio-import-architecture.md`（以下「メモ」）。ここでは**実装はまだしない**。

研究ブランチ `research/audio-analysis` の範囲（2026-10-11 ユーザー決定）: 音の**解析**、解析結果の**精度の評価**、それを**ブラウザ（TS）で動かせるかの見通し**。解析結果をアプリのデータ（`.bandsheet`）に変える部分と、入力を助ける画面は「システムの設計」なので、この計画には入れない。

決まっている条件: AI・学習済みモデルは使わない（信号処理＋人が決めた規則。HMM / ビタビ法は人が決めた値なら可）。試作は Docker の Python CLI（`band-sheets-analysis`）。全体の順番は ①コード＋拍＋セクション → ②鼻歌のメロディ → ③録音からの歌メロと歌詞のタイミング → ④ドラム。

**録音の扱い**: ユーザーの録音は市販曲を含む。曲名・コード進行・ファイル名は、git に入るファイル（この計画・レビュー・コード・テスト）に書かない。文書では `REC`（今の 1 本）・`REC-2`… と書き、数字は集計だけを書く。

## 1. 目的とスコープ

### スパイク 1 で分かったこと

- 合成音源ではほぼ解けた（拍・コード / 拍とも .99 以上）。
- 本物の録音 REC（ユーザーのピアノ、124 BPM のクリックあり、17 小節）は、コード / 拍 .439・コード / 小節 .562 と弱い。正解の注記は正しく、弱いのは解析器の側（R3 の再判断）。
- 原因の見立て: 左手は 1-5-8 の分散和音、右手は和音の一部とメロディ、アドリブとミスタッチがある。そのため ①隣のコードと共通の音、②左手の分散和音の強い 5 度、③3 倍音（5 度上に聞こえる）で取り違える。
- 届かなかった目標: 練習曲のセクション F .472（< .5）、ホールドアウトの L1 の小節の頭 F .750（< .80）、REC のコード .439（願望 .6、記録のみ）。
- 理由: 合成音源の伴奏は「毎拍、同じ形の和音」で、REC のような弾き方を作っていない。だから合成音源では REC の弱さを再現できず、直したかどうかも測れない。

### スパイク 2 が答えること

1. **REC のような弾き方**（左手の分散和音＋右手の和音の一部＋メロディ、2 拍目の裏の先取り）で、コードをどこまで当てられるか。
2. その改善が **1 本の録音に合わせただけでないか**（合成の「REC 型」伴奏、追加の録音、ホールドアウトで確かめる）。
3. スパイク 1 の残りの弱点（テンポの倍・半分、7th の揺れ、確信度、練習曲のセクション、途中から始まる曲のセクションのずれ）を直せるか。

### やらないこと

- 鼻歌のメロディ（優先 ②）。**スパイク 3 に回すことを推奨**（下の理由）。
- 解析結果を `.bandsheet` に変える部分、取り込み・入力補助の画面（研究ブランチの範囲外）。
- ブラウザ（TS）への移植そのもの。スパイク 2 では「何をどう移すか」の机上の棚卸しだけ（決めてほしいこと 5）。
- ドラム、歌メロ、歌詞のタイミング、3/4 拍子の判定。

### 推奨: スパイク 2 はコード・拍・セクションに絞る（鼻歌は次）

- 実際に使うのは本物の録音。そこでのコード .439 が今いちばんの弱点で、ここを直さないと「下書きとして役に立つか」をまだ言えない。
- 届かなかった目標 3 つも、すべてこの範囲。
- 鼻歌は別の方法（単音の高さ、ブラウザで作る予定）で、今の Python の部品をほとんど使わない。同時に進めると、評価の仕組みを 2 つ作ることになり、計画が倍になる。
- 鼻歌は録音の協力を待たずに始められるので、スパイク 3 で独立して進めやすい。

## 3. ユーザーに決めてほしいこと

1. **スパイク 2 の範囲**: コード・拍・セクションの「本物の録音への強さ」に絞り、鼻歌はスパイク 3 にする。→ **推奨: 絞る**（理由は §1）。メモ §8.2 のスパイクの番号は T18 で書き換える。
2. **本物の録音を増やせるか**: 1 本だけでは、直したのが「その 1 本に合わせただけ」か区別できない。→ **推奨: 4 本以上（最低 2 本）**。どれもクリックあり・4/4・30〜90 秒・スマホで可。コード進行の注記は今と同じ形（`<名前>.chords.json`。書き方は手伝う。git には入れない）。弾き方を変えてほしい:
   - (a) 今と同じ弾き方（左手 1-5-8 の分散和音）で別の曲
   - (b) 毎拍の和音（ブロック）で弾いた曲（「弾き方が素直なら当たるか」の比べる相手）
   - (c) ゆっくり（70〜90 BPM）の曲、白玉か分散和音
   - (d) 弱起（1 小節目の前に数拍ある）の曲
   - (e) できれば: スマホを離して置いた部屋の録音、またはギターのストローク
3. **録音の使い分け**: 今の REC と新しい録音の半分を「開発用」、残り半分を「本物の録音のホールドアウト」にする。どれをホールドアウトにするかは、**解析を走らせる前に**決めて記録する（T3）。開発用の録音も「調整の的」にはせず、決まった 3 時点（T5・T14 の途中・T14 の最後）だけで点を見る。→ **推奨: この形**。(b) と (d) をホールドアウトにするのがおすすめ。
4. **新しい目標の決め方**: §2 の「新」を仮の目標として進め、T5 の基準線を見てから確定する。→ **推奨: はい**。
5. **ブラウザ（TS）の見通しをスパイク 2 に入れるか**: → **推奨: 机上の棚卸しだけ入れる**（T-B。使っている librosa の処理ごとに、TS での置き換え候補・ライセンス・手間・速さの見込みを表にする。コードは書かない）。方法がまだ変わるので、移植は方法が固まってから。
6. **録音ごとの倍音の形**（ユーザーの案）の作り方: その録音の中だけから、決まった計算式（例: はっきりした単音の 2・3・4 倍音の強さの比の中央値）で出す。曲をまたいで値を合わせ込むことはしない。→ **推奨: これは「学習」ではなく、録音ごとの音量の正規化と同じ扱いでよい**。気になるなら「録音の倍音の形を使わず、固定の倍音の型だけ」にする。

## 5. 主な設計判断

1. **新しい案はすべて「切り替え」として足す**（既定は切る）。スパイク 1 と同じく、`config.py` の値で入れる・入れないを選ぶ。既定の設定の結果はスパイク 1 と 1 ビットも変わらないことをテストで守る（T0）。どれを既定で入れるかは T14 で決める。
2. **部品ごとに新しいファイル**: `py/dsp/bassroot.py`（T10）、`harmonics.py`（T11）、`voicing.py`（T12）、`posterior.py`（T9）、`seventh.py`（T8）、`tempo.py`（T6）。呼び出す場所（つなぎ目）と設定の欄は T0 が先に全部作る（中身は何もしない仮のもの）。後のタスクは自分のファイルだけを変える。
3. **REC 型の合成伴奏**（`comp: 'rec'`）: 左手は 8 分の 1-5-8 の分散和音（ルート → 5 度 → オクターブ → 5 度…）、右手は 3 和音のうち 2 音（毎回同じとは限らない、種で固定）、高音に短いメロディの音（8 分・16 分、和音の外の音を含む）。小節の頭のコードの変わり目を、一定の割合で 2 拍目の裏に先取りする（REC の「8 分 3 つ＋ 5 つ」の形）。アドリブとミスタッチの代わりに、少しの割合で和音の外の音を混ぜる（種で固定）。正解のコードの始まりは 8 分音符の位置で持つ。
4. **新しいレベル LR**: `comp: 'rec'` を、練習曲（調整用の種 1）と聖者に、L0 相当・L1 相当（別の音色・雑音 30 dB）・L2 相当（部屋）で作る。**曲の作りが違うホールドアウト**として、別の種・別の形（例 8 小節の AABA、弱起 1 拍）の練習曲 `etude3` を LR で作り、`heldOut: true` にする。
5. **本物の録音の受け入れ**: `recordings/` は git に入れないまま。T3 が録音ごとに匿名の名前（`rec-01`…）を付け、本当の名前との対応は git に入らない `recordings/ids.local.json` に置く。ホールドアウトかどうかは注記を受け取った時点で記録する。弱起（最初の音が小節の頭でない）も書けるようにする。git に入るファイルに録音の曲名やファイル名が無いことを確かめる `py/privacy_check.py` を足す。
6. **録音の点を見る回数を決める**: 開発用の録音の点は、決まった 3 時点だけで見る（T5 の基準線、T14 の途中、T14 の最後）。見たら `results/heldout-log.jsonl` に残す（Q1 の記録と同じ所）。ホールドアウト（合成・録音とも）は T15 の 1 回だけ。
7. **改善の判断の順番**: ①LR（合成）で上がる、②L0〜L3 で下がらない、③その後で REC を見る。①と②を満たさない変更は、REC で上がっても入れない（1 本の録音への合わせすぎを防ぐ）。

## 8. 検証の進め方

- 各タスクは「終わりの条件」のコマンドだけを実行し、結果（変更ファイル・テスト件数・未解決の点）を短く報告する。全部のテストは T17 の後だけ。
- 通し実行は T5・T14・T15・T17 だけ。調整中は `--only` で一部だけ流す。
- 解析器が正解を読まないことは、今までどおり構造（`analyze` は wav のパスと設定だけ）とテストで守る。`tempo_hint` はユーザーが知っている情報（クリックのテンポ）で、正解からは取らない。
- 録音の点を見た時点、ホールドアウトを走らせた時点は、すべて `heldout-log.jsonl` に残す。
