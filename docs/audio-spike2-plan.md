### 「AI を使わない」の決まり（2026-10-11 ユーザーが明確化）

システムの中に AI の推論の処理を置かない。性能の高い機械（GPU のサーバーなど）を必要としない。判定は機械的に行う。

| 種類                                               | 可否 | 条件                                                                                                                                                                                                                                                            |
| -------------------------------------------------- | ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 決まった計算式・録音ごとの合わせ込み             | 可   | 例: 録音ごとの倍音の形、音量の正規化、拍の追跡。その録音の中だけで計算する                                                                                                                                                                                      |
| ② 前もって作った表・値                             | 可   | 出どころは 2 つだけ。(i) **音楽理論**（和声: コードの機能、進行。参考文献の名前を書く）、(ii) **自分たちの合成音源・録音での数値の調整**（重みだけ。ホールドアウトの決まりを守る）。表はリポジトリの小さな読める形のファイルにし、出どころを書く（設計判断 13） |
| インターネットのコード譜・コーパス                 | 不可 | 正しさが当てにならない（例: ChordWiki）うえ、年代や流行の偏りがある                                                                                                                                                                                             |

## 1. 目的とスコープ

### スパイク 1 で分かったこと

- 合成音源ではほぼ解けた（拍・コード / 拍とも .99 以上）。
- 本物の録音 REC（ユーザーのピアノ、124 BPM のクリックあり、17 小節）は、コード / 拍 .439・コード / 小節 .562 と弱い。正解の注記は正しく、弱いのは解析器の側（R3）。
- 原因の見立て: 左手は 1-5-8 の分散和音、右手は和音の一部とメロディ、アドリブとミスタッチ。そのため ①隣のコードと共通の音、②左手の強い 5 度、③3 倍音（5 度上に聞こえる）で取り違える。
- 届かなかった目標: 練習曲のセクション F .472（< .5）、ホールドアウトの L1 の小節の頭 F .750（< .80）、REC のコード .439（願望 .6）。
- 合成音源の伴奏は「毎拍、同じ形の和音」で、REC のような弾き方を作っていない。合成では REC の弱さを再現できず、直ったかも測れない。
- 合成の曲には転調が無い。調を使う工夫（下の C）を測れない。

### スパイク 2 が答えること

1. **REC のような弾き方**で、コードをどこまで当てられるか。
2. その改善が **1 本の録音に合わせただけでないか**（合成の REC 型伴奏、追加の録音 5 本、ホールドアウトで確かめる）。
3. **音楽理論**（コードの機能・よくある進行・区間ごとの調）を「弱い後押し」として足すと、本物の録音で当たりが増えるか。
4. スパイク 1 の残りの弱点（テンポの倍・半分、7th の揺れ、確信度、練習曲のセクション、途中から始まる曲のセクションのずれ）を直せるか。

### やらないこと

- 鼻歌のメロディ → **スパイク 3**（決定 1）。
- `.bandsheet` への変換、取り込み・入力補助の画面（研究ブランチの範囲外）。
- ブラウザ（TS）への移植そのもの。机上の棚卸し（T-B）だけ（決定 5）。

- テンションを積んだコード（6/9、7(#9) など）の出力（設計判断 8）。

7. **改善の判断の順番**: ①LR（合成）で上がる、②L0〜L3 で下がらない、③その後で録音を見る。①②を満たさない変更は、録音で上がっても入れない。
8. **コードの語彙（A）**: 出すのは 3 和音（maj・min・dim・aug）、7th（7・M7・m7・m7b5・dim7）、sus4、分数コード（ベースの音）だけ。テンションを積んだコードは出さない。テンションの音は、元のコードに属する経過音・刺しゅう音として扱う。**採点の対応の規則**（T20、正解の側にだけ使う）:
   - 9・11・13 とその変化（b9・#9・#11・b13）、6、add9 は落として元のコードにする（例 `C6`・`Cadd9`・`C6/9` → C、`G7(#9)`・`G9`・`G13` → G7、`CM9` → CM7、`Dm9`・`Dm11` → Dm7、`Dm6` → Dm）。
   - `7sus4` → sus4。5 度を変えたもの（`7(b5)`・`7(#5)`・`aug7`）・`mM7`・`sus2` は語彙に無いので外して数える（確認したいこと 2）。
   - 分数コードのベースは別に採点する（記録のみ）。
   - スパイク 1 の点（ルート＋メジャー / マイナー）は続けて出す（比べるため）。新しく「語彙のコード / 拍」（ルート＋語彙の種類。m7b5・dim7 は dim の仲間、7・M7 は maj の仲間として 3 和音の種類でも数える）を足す。
9. **理論による「後押し」（B）**: ビタビ法の「次のコードへの移りやすさ」に、調の中の機能を使った弱い後押しを足す。禁止は**しない**（どの移り方にも下限の値を残す）。
   - 一番強い: その調のダイアトニック・コードの間の T・S・D の流れ（例 S → D、D → T）。
   - 次に強い（よく使う技法）: セカンダリー・ドミナント（ドッペルドミナント V/V を含む）とその解決、裏コード（トライトーン代理）、同主調からの借用（例 長調の IVm・♭VI・♭VII）。
   - それ以外: 下限の値（まれな動きも出せる）。
   - 強さ = 設定の値 × その小節の調の確信度。調の確信度が低いと後押しは弱まる。
10. **区間ごとの調（C、ユーザーの案）**: 2 回に分けて解く。
    - 1 回目: 今のとおり、理論の後押し無しでコードを出す。
    - 調: 小節を単位にした「調の HMM」（24 調）。1 回目のコードが、その調の表（ダイアトニック・借用など）にどれだけ合うかを点にする。調が変わる値段は、**セクションの境目では安く、セクションの途中では高く**する（境目は「変わりやすい所」で、決めつけない。練習曲のセクション F が .472 と弱いため）。近い調（属調・下属調・平行調・同主調）への移りは少し安くする。
    - 2 回目: 小節ごとの調と理論の後押しを使って、コードを解き直す。
11. **転調の変化形（D）**: 合成の曲に転調が無いので作る。アプリの移調のコード（`src/lib/transpose.ts` の `transposeChartSection`・`transposeChord` でコード譜、`src/lib/transposeScore.ts` でメロディの alphaTab のモデル）を `render/` から呼び、1 つのセクションだけを移調する。正解はそこから作るので正確なまま。正解に小節ごとの調（`keys`）を足す。ホールドアウトの転調の変化形も作る。
12. **和声の知識のノート（E）**: 理論のよりどころは、ユーザーの Drive のフォルダ `knowledge` に日本語の Google ドキュメントとして置く（リポジトリの外）。市販の本は参考に読むだけで、リポジトリには写さない。下書きは git に入らない `spikes/analysis/out/notes/harmony-basis.md`（`out/` は gitignore 済み）に書き（T25）、Drive に上げるのは**その時点でユーザーの許可を得てから**（U1、メインのセッションで行う）。
13. **表のファイルの決まり**: 理論の表は `py/dsp/tables/*.toml`（Python 3.12 の `tomllib` で読む。外部の依存なし）。各ファイルの先頭に出どころを書く: 理論の値は「ノート『和声の基礎（band-sheets 解析用）』の § と本の名前」だけ、調整した重みは「T14 の何回目」。本の文章は写さない。インターネットのコード譜・コーパスの値は入れない。

- 各タスクは「終わりの条件」のコマンドだけを実行し、結果（変更ファイル・テスト件数・未解決の点）を短く報告する。全部のテストは T17 の後だけ。
