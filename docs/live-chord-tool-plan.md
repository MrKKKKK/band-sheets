# ライブ和音チェック（研究用の道具）計画

想定読者: ユーザー（スパイクを採るかを決める人。数字ではなく耳と手で「何が良くなり、何が壊れたか」をつかむために使う）と、この道具を作るエージェント（前提知識の無いサブエージェントを含む）。
目的: PC のライン入力を、スパイクが測っている関数そのもので 1 窓ずつ判定し、和音名と強さと候補 5 つを出す道具について、中身・作り・ブランチ・タスク・残りの問いを決める。

2026-11-23 作成。土台のコード: `spikes/analysis/ts/dsp/`（凍結）、`ts/bass/`（凍結）、`ts/chords2/`（`spike/8-octave` `cd8c9e1`。スパイク 8 は止まり、PR #107 で研究ブランチへ入る）。

## 0. 決まっていること（ユーザー、2026-11-23）

- 入力は PC のライン（`getUserMedia`、`echoCancellation` / `noiseSuppression` / `autoGainControl` は切）。音は保存しない。音価・長さは判定しない。
- 出すのは「その瞬間の芯」: 拍・調・前後のつながり（Viterbi・遷移の重み）は使わない。窓 0.5〜3 秒（既定 1 秒）。
- 調はユーザーが入れ、**表記（C# / Db）だけ**に使う（`src/lib/transpose.ts` `respellChord`）。点数には入れない。
- 一度に見せるロジックは 1 つ（§2 の一覧から選ぶ）。スパイクが測る関数を**そのまま呼ぶ**（書き直さない）。
- **低音は必ず 0.8 秒待つ**（切り替え無し、§1.2）。
- **調律と利得は始めに 1 回測って固定**し、画面に出す。「測り直す」ボタンで両方を測り直す（§1.3）。
- devcontainer `band-sheets` の Vite ページ（`server.host: true`）を PC の Chromium で開く。アプリには入れない。
- ブランチ: `tool/live-chords` → 研究ブランチへ PR。
- 流してよい曲: 開発用の曲 a〜j はよい（採点も値の変更もしないので見る時点ではない）。ただし**印象で次のスパイクの値を決めない**。ホールドアウトの曲（スパイク 7 で取っておいた録音 k〜n の曲）は、録音でも手で弾くのでも流さない。ページの頭に常に出す。
- 画面は §4.2 の ASCII のとおり（Claude Design は使わない）。
- 決定 A（LT5 の後）: スパイク 8 の行は 2 つ見せる。「スパイク 8 D2＋D1（s8-dev-1 で測った設定）」は `e1Config(T7_E1_D2_VALUES, true)`（設定のハッシュ `462ab1385491`、テストで固定）そのまま。「スパイク 8 D1 だけ（測っていない組み合わせ）」はスパイク 8 で一度も測っていないと注に書く。
- 決定 B（LT5 の後）: 静かな窓の門は**固定の利得をかけた後**の音量で判定する（`rmsDb + gainDb < −55`、目標 −22 dBFS の 33 dB 下）。測り始めの引き金は生の音量のまま。

## 1. 芯と窓

### 1.1 窓 1 つ = 「拍」1 つ = 列 1 つ

どのロジックも、窓 `[colStart, colEnd)` を**拍 1 つ・列 1 つ**（`perBeat = 1`、`n = 1`）として既存の関数に渡す。新しい引数は要らない:

- v1a のクロマ: `hpss(y).yHarm` → `chordColumns(yHarm, [colStart], colEnd, { perBeat: 1, tuningFull, tuningBass })`（`n < 2` では `lastBeatEnd` が `duration` を返すので、`duration = colEnd` が列の終わりになる）。`perBeat = 1` なので `cols.bass` は frontEnd の `bassChroma` と同じもの（M1 用）。`loadFeatures` ではなく `hpss`（オンセットは要らない）。
- F1: `octaveCqt(y, cfg.f1, { tuning })` → `f1Beats(wide, [colStart], colEnd, cfg.f1)` → ベースは `bassCqtFrom(y, wide, bassCqt)`、D1 は `foldF1`。`chords2Inputs` は調律を受けないので、その中身の同じ関数を直接呼ぶ。F1 を使わない行のベースは `lowCqt(y, bassCqt, { tuning })`。
- chords2: `analyze(input, cfg)` に仮の調 1 つと `barOfBeat = [0]` を渡す（`n = 1` では `FamilyPrior` の行は読まれない）。区間 → 名前は `toEvalChords(segs, [colStart], colEnd)`、ベースの印は `marksOnV2(low, chords, [colStart, colEnd], appBassConfig())`（beats を 2 つにすると窓全体が拍の頭になり、重みが一様になる）。
- `n = 1` では Viterbi の道 = 放出の最大（同点は小さい番号）、事後確率 `chordPosterior` = `softmax(20 · s)`（`BETA = 20`、`perBeat = 1` なので `EIGHTH_EMIS` は掛からない）。遷移は数学的に効かない。

曲の解析では v1a の列は 8 分（120 BPM で約 0.25 秒）、F1・D2 は拍（約 0.5 秒）。窓 1 秒は、スパイクが 1 列として見たことの無い長さで、和音 2 つが混ざりやすい。0.5 秒が拍 1 つに近い。

### 1.2 低い音を待つ

CQT は C1（32.7 Hz）から 36 ビン / オクターブで、核の長さは **C1 1.59 秒、C2 0.79 秒、C3 0.40 秒**（`ts/dsp/core/cqt.ts`）。左右に 0.8 秒ずつ足して解析し、列は窓だけにする。表示は 0.8 秒遅れる。HPSS の右端（31 フレームの中央値、約 0.36 秒）もこれで足りる。解析に渡す長さは窓 + 1.6 秒（最大 4.6 秒）。

### 1.3 調律と利得（始めに 1 回）

- 開始（と「測り直す」）の後、門（仮 −55 dBFS、道具だけの値。測り始めは生の音量で判定）を超えた最初の 3 秒で測る:
  - 調律: `estimateTuning(y, { sr: 22050, bpo: 36 })`。v1a・ベース・F1 の全部に同じ値を渡す（§1.1）。
  - 利得: その 3 秒の写しに `normalizeLevel`（`src/lib/analysis/inputLevel.ts`）を掛け、返った dB を以後の全窓に掛ける。スパイクの「1 曲に 1 つの利得」（`prepareInput`、RMS −22 dBFS）と同じ考え。
- 窓ごとに測り直さない（呼ぶたびの推定は揺れ、静かな所を持ち上げてしまう）。
- 固定の利得をかけた後の RMS が門より小さい窓は解析せず「音が小さい」と出す（決定 B）。

## 2. ロジックの一覧

名前つきの定数だけを使い、値のつまみは作らない（耳で値を合わせると「調整用の合成音だけで値を決める」に反する）。

| ID        | 中身（呼ぶ関数）                                                 | 状態数 | 正直な注意                                                                                                                                         |
| --------- | ---------------------------------------------------------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `v1a`     | `estimateChords(cChroma, 1, DEFAULT_CHORDS_CONFIG)`              | 120    | 2 回目のパス（理論の重み）は無い                                                                                                                   |
| `base`    | `v1a` → `marksOnV2(…, appBassConfig())`                          | 120    | アプリが取る形。`/X` は**転回だけ**（ペダル・経過・クリシェ・行末の 6 度は前後の区間が要る）                                                       |
| `s7-V1`   | chords2 `analyze`（`T10_V1_OVERRIDES`）→ 印                      | 156    | 不採用（スパイク 7 G3）                                                                                                                            |
| `s8-D2`   | V0 + `d2`（E1、`T7_E1_D2_VALUES`）→ 印                           | 120    | 不採用。1 窓では 2 状態のならし（`switchPenalty`）が効かず、ρ ≥ θ の判定だけ                                                                       |
| `s8-D2D1` | `e1Config(T7_E1_D2_VALUES, true)`（D2 + D1、s8-dev-1 の 2 行目） | 120    | スパイク 8 の s8-dev-1 で測った設定そのまま。1 窓では 2 状態のならしが効かない                                                                     |
| `s8-D1`   | V0 を `foldF1` のクロマで採点（`octaveChroma`）→ 印              | 120    | 測っていない組み合わせ（D2 なしの D1）。不採用。F1 の床（ファイルの中央値 × `floorRatio`）が窓の中の自分自身との比になり、静かな窓でも音を拾う     |
| `s8-cand` | V0 + `d2.output: 'candidate'`（θ_c = `T7C_E1_CANDIDATE_THETA`）  | 120    | 不採用・持ち越し。定数が `null` の間は灰色にして理由を出す（T7c が調整用で選んだ .5 は `docs/audio-spike8-t7c.md` にあるが、定数には入っていない） |

ほか（V2・V3、M1〜M3、組の規則 `bassRoot`）は頼まれたら足す。F1 の値は `DEFAULT_F1_CONFIG` 1 つで、F1 を使う行では拾った音（C2〜B5、強さ順）を補助の行に出す。

**窓では無理なもの（入れない）**: v1a の 2 回目のパス、Viterbi のならし、区間のまとめ、拍・小節頭・区間・調、組の規則 `'context'`、ベースのペダル / 経過 / クリシェ。このため道具の答えは曲の解析よりよく揺れる。

### 2.1 強さと候補 5 つ

- 表示は「**相対の強さ** %」= 列の事後確率（`softmax(20 · s)`）× 100。新しい温度は作らない。候補 5 つは `segmentCandidates(post, states, 1, 0, 1, 5)`。5 つそれぞれの余弦の点 `s` も並べる。
- **同じ数になる行と違う行**: V0 の点を使う行（`v1a`・`base`・`s8-D2`・`s8-cand`）は % と `s` が同じ。違いは規則で決まる答え（`/X`、足す音）だけに出る。数が変わるのは `s7-V1`（状態 156）と、F1 のクロマを使う `s8-D2D1`・`s8-D1`（この 2 つは同じ数）だけで、そこも状態の数とクロマが違うので、% の大小は比べない。アプリの確からしさ（曲全体でならした値）とも別物で、画面にそう書く。
- 規則で答えが変わる行（`base` の `/X`、`s8-D2`）: 答えが 1 位と違えば「規則で入れ替え」と出す。`s8-D2` と `s8-cand` は ρ(d) と θ を出す（`evalAdded`）。ベースは `segmentBass` の音と確からしさ `(s1 − s2) / s1` を出す。
- 候補の 2 つ目の下に「アプリで見せる候補はここまで」（`CANDIDATE_CAP = 2`）の線を引く。無音の列（`no_chord_energy` 未満）は「和音なし」で、% は出さない。

## 3. リファクタ

**要らない**。芯は既存の関数の組み合わせで呼べ（§1.1）、`eval/frontEnd.ts` にも `node:` の読み込みは無い。代わりに道具の PR で、性質のテスト「`n = 1` では調・小節の入力を変えても chords2 の出力（列・事後確率・区間）が同じ」を 1 つ足す。`ts/dsp`・`ts/bass`・`ts/chords2` の差分は 0。

## 4. 道具の作り

```
Chromium（PC）                                     Worker（解析、1 つ）
getUserMedia（3 つの処理を切、deviceId 指定）
 → AudioContext（機器の速さ、例 48 kHz）
 → AudioWorklet（128 サンプルの塊 {frame, 全チャンネル}  ─MessageChannel→  ためる輪（22050 Hz、8 秒）
    塊ごとのピーク・RMS → メイン（メーター）)                                assembleBlocks → toMono
                                                                          計算が終わったらすぐ次:
                                                                            最新 窓+1.6 秒 → resampleSinc → 22050 Hz
                                                                            → 門 → 固定の利得 → 芯（選んだロジック 1 つ）
メイン: 答え・候補 5・補助行・計算 ms・実際の回数を描く   ←──────────    結果 {答え, 候補, s, ベース, ρ, F1 の音, ms}
```

- 塊の並べ直しは `ts/browser/micCheck.ts` の `assembleBlocks`（抜けは 0 で埋め、抜けの数を出す）。worklet は micCheck の形（`{frame: currentFrame, data}`）で、全チャンネルを送る（micCheck の worklet は 1 チャンネル目だけで、ページの中の文字列なので書き出せない）。ステレオは `toMono`（`ts/dsp/core/resample.ts`）。
- Worker は 1 つで、前の計算が終わったらすぐ次を始める（待ち行列は作らず、常に最新の音）。実際の回数と ms を出す。窓 1 秒なら毎秒 2〜4 回で足りる。
- ファイル: `ts/live/`（純粋・テスト付き）と `ts/browser/liveChords*`（ポート 5188 / preview 5189。5180〜5187 は使用中）。
- 外へ出さない: ファイルの入力も保存も無い、`fetch` 無し（既存の no-network のテストと同じ形で確かめる）。結果をファイルやログに書かない。

## 6. 実績

LT0〜LT6 まで済み（LT5 は独立レビュー、LT6 でその指摘とユーザーの決定 A・B を反映）。Node での 1 窓の計算は、窓 1 秒で 83〜142 ms。headless Chromium（偽の入力）では毎秒 5.5〜7.1 回で、毎秒 2 回の目安を満たす。確かめ方は単体テスト・性質のテスト・流しながらの再サンプリングの一致・Playwright の煙のテスト。

### 6.1 ユーザーの確かめ方

1. 鍵盤で C・Am・G7・C/E・Cmaj7 をそれぞれ 2 秒以上のばす。`v1a` では C・Am が 1 位、G7 は `7` か G、C/E は C か Em（v1a の知られた癖）。`base` で C/E が出るか、`s8-D2` で Cmaj7 の `maj7` が出るかを見る。ロジックを切り替えて違いを聞く。
2. 音を止めると「音が小さい」になる。窓を 0.5 → 3 秒にすると、切り替わりが遅くなり 2 つの和音が混ざる。
3. 仮想の入力（使えるなら、OS の仮想ケーブルと自分で作った合成の wav）。無ければ LT4 の自動のテストで代える。
