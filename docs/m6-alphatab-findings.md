# M6 alphaTab 1.8.4 確認結果（閲覧画面の前提）

M6 計画（`m6-plan.md`）の T1。閲覧画面が前提にしている alphaTab 1.8.4 の動きを、コンテナ内で実際に確かめた。

- 読み込み: Node から `alphaTab.importer.AlphaTexImporter` を直接呼び、`MasterBar`（拍子・`tripletFeel`・セクション）と各 `Bar`（調・音部記号・拍の音価・`isEmpty`）を出して比べた。
- 描画: 一時ストーリー（`AlphaTabApi` をそのまま使い、`boundsLookup` の枠を赤（段の `realBounds`）・青（各段の最初の小節の各トラックの `BarBounds.visualBounds`）で重ねて描くもの）を Storybook（別ポート）で開き、Playwright で値を読み、スクリーンショットを撮った。CPU を遅くするのは CDP の `Emulation.setCPUThrottlingRate`。
- 一時ストーリー・スクリプトは確認後に削除済み。ソースコードの変更はなし。
- スクリーンショット: `docs/m6-t1-check.png`（上: 既定の設定＝今の `PartScore` と同じ、中: 閲覧用の設定、下: 閲覧用の設定で幅 500px＝3 段）。

## 1. 要素を無効にした見た目

閲覧用の設定: `NotationElement` の `EffectMarker`・`EffectTripletFeel`・`BarNumber`・`TrackNames`・`EffectTempo`・`ScoreTitle` を `false`（＋今の `PartScore` と同じ `EffectDynamics` を `false`）。

| 確認したこと                   | 結果                                                                                                                                                                                                                                                           |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 既定の設定での重なり（比較用） | 1 小節目の練習番号「A」と 1 拍目のコード名「Am7」が同じ位置に重なる（format-decision.md の既知の課題を再現）。テンポ「♩=120」、Shuffle の表記、赤い小節番号、左のパート名「Vo」「Dr」が出る。                                                                  |
| Shuffle の表記（既定の設定）   | ドラムの `\tf triplet8th` なのに、表記は**メロディの段（描くトラックの先頭）の上**に出る。さらに 2 小節目の頭にも「(♪♪=♪♪)」（ストレートに戻った表記）が出る。`\tf` がマスターバーの属性で、メロディが先にあると 1 小節目にしか効かないため（R7 (a) を再現）。 |
| 閲覧用の設定                   | 練習番号・Shuffle・テンポ・小節番号・パート名・題名がすべて消える。**コード名（`ch`）は 1 拍目でも何とも重ならない**。五線の左端の位置は既定の設定と同じ（パート名を消しても左の余白は変わらない）。                                                           |
| 「rendered by alphaTab」       | **設定に関係なく、描いた譜面の一番下に必ず 1 行出る**（`_layoutAndRenderAnnotation`。設定で消す手段はない）。セクションごとに alphaTab を作ると**セクションの数だけ**出る。→ 計画への影響 1。                                                                  |

## 2. セクションの中でパートごとに小節数が違うとき

メロディ 2 小節＋ドラム 4 小節の文書（`\track` 2 本、どちらも `\section "A"`）。

- マスターバーは 4 個。**短いメロディの 3・4 小節目は空の小節で埋まる**（`Bar.isEmpty === true`、休符 1 つ。描画は休符なしの空の五線）。小節線は 2 本のトラックでそろう。
- `boundsLookup` でも空の小節が普通の小節として入る（`staffSystems[i].bars[j].bars[k]` がトラックの数だけある）。
- `\tf` は `MasterBar.tripletFeel`。メロディが先 → `[2, 0, 0, 0]`（ドラムの `\tf` は 1 小節目だけ）、ドラムが先 → `[2, 2, 2, 2]`。表記を無効にして自分で描く方針（計画の設計判断 3）で問題ない。
- 補足: 2 本のトラックが**別の `\ts`** を持つ文書（メロディ 4/4・ドラム 3/4）では、マスターバーの拍子は**後に書いたトラックのもの**になり、先のトラックは 3/4 の小節に 4 拍が入る（エラーにはならない）。→ 計画への影響 5。

## 3. `boundsLookup` の座標

| 確認したこと                          | 結果                                                                                                                                                                                                                                                                                            |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 基準                                  | **`AlphaTabApi` に渡した要素（コンテナ）の左上が原点の px**。`.at-surface` はコンテナの (0, 0) にある。重ねた枠がスクリーンショットで五線とぴったり合う（`scale` 1.0 と 1.5 の両方）。                                                                                                          |
| 余白                                  | 左・上に 35px の余白（`display.padding`）。この余白は `scale` を掛けても **35px のまま**（中身だけが拡大される）。                                                                                                                                                                              |
| `display.scale` が掛かっているか      | **掛かっている**（`StaffSystemBounds.finish(scale)` 済み）。例: scale 1.0 で 1 段目のメロディの小節 y=59 h=36、ドラム y=151 → scale 1.5 で y=71 h=54、ドラム y=209（= 35 + (元 − 35) × 1.5）。そのまま CSS の px として使える。                                                                 |
| `staffSystems[i].realBounds`          | 段全体（コード名の帯を含む上端〜一番下の五線の下の余白）。**段と段のあいだに 10〜15px の隙間**があり、どの段にも含まれない（例: 1 段目 35〜197、2 段目 207〜）。**最後の段は下の「rendered by alphaTab」の行もほぼ含む**。                                                                      |
| 各トラックの `BarBounds.visualBounds` | **五線の線の範囲だけ**（h=36 at scale 1.0 = 五線の高さ）。上のコード名や下に飛び出す音符は含まない。トラック k の段の最初の小節は `staffSystems[i].bars[0].bars[k]`（`bars[k].bar.staff.track.index === k` を確認）。ShuffleMark は「ドラムの五線の上端 `visualBounds.y` より上」に置けばよい。 |
| いつ揃うか                            | `renderFinished` の時点で既に `boundsLookup` は埋まっていた（段の数も同じ）。`postRenderFinished` ではもちろん揃っている。計画どおり `postRenderFinished` で読めばよい。                                                                                                                        |
| 描画の回数                            | 1 回の `api.tex()` で **`renderFinished`／`postRenderFinished` が 2 回ずつ来ることがある**（フォントの読み込み完了後の描き直しと思われる。20 セクションの測定でも一部のセクションで 2 回）。→ 計画への影響 2。                                                                                  |

## 4. `display.scale` を変えて描き直す

`api.settings.display.scale = 1.5; api.updateSettings(); api.render();` で**描き直せる**（`api.tex()` をもう一度呼ぶ必要はない）。`postRenderFinished` がもう一度来て、`boundsLookup` は新しい倍率の座標になる（幅 700px で 2 段 → 3 段に増えた）。コンテナの高さも描き直しに合わせて変わる。

## 5. `core.enableLazyLoading`

`overflow: hidden` の高さ 400px の枠の中で、内容を `transform: translateY(-2500px)` でずらした 120 段の譜面（部分画像 121 個）:

- `enableLazyLoading = false`: **121 個すべての部分に SVG が描かれた**（`transform` で見えない部分も含む）。
- `enableLazyLoading = true`（既定）: 見えている 5 個だけ描かれ、残り 116 個は空の枠のまま。

→ 計画どおり `false` にすれば、ページめくりの `translateY` で隠れた部分も最初から描かれる。座標（`boundsLookup`）はどちらでも全段分そろう。

## 6. 20 セクション × 3 トラックの描画時間

1 セクション = メロディ・ベース（ヘ音記号）・ドラムの 3 トラック、4〜6 小節（8 分音符を含む）。`AlphaTabApi` を 20 個、幅 1100px、閲覧用の設定・`enableLazyLoading: false`。Storybook のストーリーを開いてから全部の `postRenderFinished` まで。

| CPU            | 全部が描き終わるまで                              |
| -------------- | ------------------------------------------------- |
| 等速           | 約 0.57 秒（最初のセクション 0.42 秒）            |
| 4 倍遅い ×2 回 | 約 2.1 秒・2.3 秒（最初のセクション 1.7〜1.9 秒） |

- セクションはほぼ同時に描き終わる（`useWorkers: false` なので、最初の描画が始まると 20 個が続けて描かれる。1 セクションあたり 4 倍遅い CPU で約 20ms ずつ増える）。最初のセクションだけを先に見せる効果は小さい。
- **判断: 「画面に近いセクションから順に描く」は不要**。全部が揃うまで `ready=false`（ページ数は「計算中」）で十分。

## 7. 持ち越しの補い（セクションの文書と全体の読み込みの一致）

パート全体（`\ts 4 4`・`\ks D` → セクション B で `\ts 3 4`・`\ks Bb`・`:8` → セクション C は音価なし → セクション D で `\clef bass`）を読み、セクションだけの文書と比べた。

| セクションの文書                                                                 | 全体の読み込みのその部分と                                                                                        |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| C: 冒頭に `\ts 3 4`・`\ks Bb` を補い、`\section "C"` の次に `:8` を補う          | 拍子 3/4・調 −2（B♭）・8 分音符が一致（ただし下の注意）。                                                         |
| C: 補いなし（パート冒頭の `\ts 4 4`・`\ks D` のまま）                            | 4/4・調 +2・4 分音符になり**不一致**（補いが必要なことの確認）。                                                  |
| D: 冒頭に `\ts 3 4`・`\ks Bb`・`\clef bass`（セクション内の `\clef` を持ち越し） | 3/4・調 −2・ヘ音記号・2 分＋4 分で一致。                                                                          |
| ドラム B: `\tf triplet8th` を補い（`\section` の前でも後でも）、`:8`             | `tripletFeel = 2`（triplet8th）・8 分音符で一致。`\tf` の次の最初の拍には `:N` が必要（既知の Gotcha のとおり）。 |

**注意（全体の読み込みとずれる場合）**: セクション C のように **`\section "C"` の直後の音符に音価が無い**と、全体の読み込みでは既知の Gotcha のとおり**その音符がセクションの 2 つ目の引数として飲み込まれる**（全体では 5 音、`section.marker` に入る）。セクションの文書で `\section` の次に `:N` を補うと、その音符は**音符として読まれる**（6 音）。つまり「補い」は全体の読み込みと 1 音ずれる。アプリが書くテキスト（`serializeMelody`/`serializeDrums`）は必ず `:N` を書くので起きないが、テキスト入力で手書きしたときに起きる。→ 計画への影響 3。

## 計画への影響

1. **「rendered by alphaTab」がセクションの数だけ出る**（設定では消せない）。`SectionScore`（T13）で、コンテナの高さを最後の段の `realBounds` の下端に切って `overflow: hidden`（または `clip-path`）にするか、`.at-surface` の最後の部分画像を CSS で隠す必要がある。ページめくりの単位（段の `realBounds`）には最後の段の下にこの行がほぼ含まれるので、高さを切らないとセクションの下に毎回 12px 程度の文字が入る。消すか、閲覧画面の最後に 1 回だけ出すかは要判断（alphaTab は MPL-2.0 で表示の義務はないが、出典の表示として 1 回残すのも手）。**計画の変更が要る点**（T13 の内容に追加）。
2. **`postRenderFinished` は 1 回の `tex()` で 2 回来ることがある**。`SectionScore` の `onLayout` は何度呼ばれてもよい作りにし（最後の値を使う）、`ViewerSheet`（T14）の「全部揃った」は「各セクションの最新の `onLayout` が届いた」で判断し、その後に高さが変わったら単位を測り直す。計画の API（`onLayout?: (systems) => void`）はそのままでよい。
3. **`\section` の直後の音価の無い音符**: T12 の golden の比較（「セクションの文書の拍が全体の読み込みと一致」）は、このケースだけ一致しない。T12 は (a) 全体の読み込みに合わせる（このときは `:N` を補わず、`\section` の直後に音価の無い音符をそのまま置いて同じように飲み込ませる。持ち越しの音価は効かなくなる）か、(b) 補いの `:N` で音符として出す（エディタの確認用 `PartScore` とは見た目が 1 音違う）かを決める必要がある。**推奨: (b)**（閲覧ではそのほうが正しい音が出る。テストでは「`\section` の直後に音価の無い音符がある」ケースだけ全体との比較から外し、別に期待値を書く）。前提のずれとしては小さい（手書きのテキストだけ）。
4. **`boundsLookup` の座標はコンテナ基準・`scale` 済みの px** なので、T13 の小節番号・ShuffleMark・`SystemBox`（`top = realBounds.y`、`height = realBounds.h`）はそのまま CSS の px に使える（計画の想定どおり）。ただし**段と段のあいだの隙間は単位に含まれない**ので、T3/T14 の `FlowUnit` は「次の単位の上端まで」を高さにするか、隙間を含めない（`paginate` は単位の `top` を使うので隙間があっても問題ない）。ShuffleMark はドラムの五線の `visualBounds`（五線の線の範囲だけ）の上に置く。余白 35px は `scale` で変わらない。
5. **同じセクションの文書で 2 つのパートの拍子が違うと、後のトラックの `\ts` に合わせて描かれる**（前のトラックの小節があふれて見える）。パートごとに冒頭の `\ts` が違う曲（メロディ 4/4・ドラムの冒頭で `\ts 3 4` など）で起きる。編集画面の `PartScore` も同じ。M6 では「よくある使い方ではない」として扱わなくてよいと思うが、T12 の `bars`（セクションの小節＝全パートの最長）はマスターバーの拍子（最後のトラック基準）とずれうる。T12 は各パートの単独の読み込みの拍子を使い、ずれは T20 のレビューで確認する程度でよい。
6. `display.scale` の変更は `updateSettings()`＋`render()` で描き直せる（計画どおり。`tex()` の再呼び出しは不要）。
7. `enableLazyLoading = false` で `transform` で隠れた部分も描かれる（計画どおり）。
8. 20 セクション × 3 トラックは 4 倍遅い CPU で約 2.1〜2.3 秒。**「近いセクションから順に描く」は入れない**（計画の「遅ければ」の条件に当たらない）。全部揃うまで「計算中」。
9. 短いパートは空の小節で埋まり、小節線はそろう（計画どおり）。要素を無効にすると `ch` は 1 拍目でも重ならない（計画どおり）。
