# スパイク 5 タスク計画: ドラムだけの録音からドラム譜の下書きを出せるか

想定読者: このリポジトリで作業するユーザーとエージェント（タスクを受ける前提知識の無いサブエージェントを含む）。
目的: ドラムの解析のスパイクについて、範囲・データ・指標・段階・関門・タスクを決め、§3 の決定（2026-10-25）を反映した計画。

2026-10-25 作成。参照: `audio-spike4-plan.md`（形・見る時点）、`audio-spike2-plan.md`・`audio-spike3-plan.md`、main の `docs/audio-integration-plan.md` §3.5・§6。

### 守ること（スパイク 2〜4 から引き継ぐ）

- **AI を使わない**: 学習済みモデルは使わない。使うのは決まった計算式と、人が値を決めた規則・HMM、録音ごとの合わせ込み（例: 録音の中の打点からテンプレートを測り直す）、**決めたテンプレートの NMF**。値の調整は自分たちの合成音だけ。
- **プライバシー**: ユーザーの録音は `recordings/`（git に入らない）だけ。git・Drive・Artifact・ログ・報告に、音・図を出さない。録音の楽譜は自分たちで書くので曲は分からないが、ホールドアウトを隠すため `recordings/` だけに置く。名前は匿名（`drm-NN-x`）、数字は集計だけ。解析はブラウザの中だけで通信しない。最後に `py/privacy_check.py`。
- **ホールドアウトと見る時点**: 録音のホールドアウトは楽譜の時点で決め（T4b）、取り込みで解析の前に記録。開発用は 3 回だけ（**録音の見る時点**の話。開発用の合成は実際には 5 回見た。逸脱として「実績」に記録）、ホールドアウトは最後の 1 回だけ。`out/results/heldout-log.jsonl` に残す。
- **PC のブラウザ（Chromium）だけ**。最後は TS を Worker で動かす。
- **ライセンス**: GPL・LGPL・AGPL のコードは読まない・写さない（ADTLib・madmom の学習済み部分・Hydrogen のコードなど）。論文の方法を自分で書くのは可。サンプル音は CC0・パブリックドメイン・MIT/BSD 系だけ（T1 で確かめる。アプリには入れない）。**例外**: キット D（MuldjordKit、CC-BY 4.0、表示は `ts/THIRD_PARTY.md`）は、ユーザーの許可（T10b、2026-10-25）で調整用だけに使う。
- **変えないもの**: `src/`（読むだけ。`drum.ts` の `parseDrums`/`serializeDrums` で往復を確かめる）、`ts/dsp/`・`ts/hum/`・`py/dsp/`（凍結。`ts/dsp/core/` の FFT・変換と `ts/browser/` の読み込みは使う）。

## 1. 目的とスコープ

### アプリの 2 つの目的との関係

1. **慣れた人の速さ**: 練習やライブのドラムだけの録音から、ドラム譜の下書きを作り、一から打ち込むより**直す手数が少ない**こと。
2. **不慣れな人の下書き**: 譜面を書けない人（ドラムを叩くが譜面は苦手な人、ほかのパートの人）が、録音から「何を・いつ叩いたか」のおおよその譜面を得ること。

### 「できた」の意味

- ドラムだけの録音から、`{t, inst, strength, confidence}` の打点と、拍の格子に丸めた打点（アプリのドラムのモデル `DrumEvent[]` に直せて `serializeDrums`→`parseDrums` で往復する）を出せる。
- 合成と録音で §4 の指標を測り、段階ごとに「下書きとして役に立つか」（直す手数 / キーボードの手数）が分かる。
- PC のブラウザで §5 の速さ・メモリ・大きさに収まるかが分かる。

### やらないこと

- バンドの音（ドラム以外が混ざる）、鼻歌・口でのドラム（ボイスパーカッション）。
- `drumDraft.ts`、取り込みの画面、`drumKit.ts` への楽器の追加（main のシステム設計）。
- クリック無しの自由なテンポ（テンポ・拍子・開始は渡す。§3 の決まったこと 5）。
- フラム・ロール・ブラシ、32 分より細かい音・3 連以外の連符（出たら誤りとして数えるだけ）。

## 2. 段階と方法

流れ: 読み込み → モノ・22050 Hz（または 44.1 kHz。高い帯域のため T5 で決める）→ 短時間スペクトル → 始まりの検出 → 楽器の判定 → 強さ（ゴースト・アクセント）→ 拍の格子・丸め・シャッフル → 結果の JSON。

| 段階       | 楽器                                                  | 方法（既定 → 試す切り替え）                                                                                                                                                                                                                     | 主なリスク                                                         |
| ---------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **S-3**    | BD・SD・HH（オープン・クローズをまとめる）            | 始まり: 帯域ごとのスペクトルの増え（対数圧縮）＋録音ごとの閾値。判定: 帯域のエネルギーの規則（低い・中の雑音・高い）→ **決めたテンプレートの NMF**（合成のキットで作る）→ 録音の中の打点でテンプレートを測り直す（合わせ込み）→ HPSS を前に置く | 同時打ち（BD＋HH、SD＋HH）の見落とし。シンバルの残響の中のゴースト |
| **S-9**    | アプリの 9 種類（CR・HH・HO・RD・T1・T2・SD・FT・BD） | タム: 録音の中のタムの打点を低い山の高さで並べて 3 つに分ける（相対の高さ）。シンバル類: 減衰の長さ・スペクトルの重心・帯域の形（CR 長く広い、RD 短く密）。HH と HO: 高い帯域の続く長さ（同時には打たない規則）                                 | タムの数がキットで違う。CR と RD・HO の取り違え                    |
| **S-拡張** | 今のキットに無いもの（下の表）                        | 合成で測るだけを基本にし、録音に入っていれば記録                                                                                                                                                                                                | アプリで書けない（持ち越しの質問 1）                               |

S-拡張の対象（ユーザー、2026-10-25）。**新しい楽器**と**今の楽器の叩き方**で、見分け方もアプリでの書き方も違うので分けて測る（方法は T12 で決める）。

| 種類                 | 対象                                     |
| -------------------- | ---------------------------------------- |
| 新しい楽器           | スプラッシュ、チャイナ、カウベル         |
| 叩き方（スネア）     | リムショット、クロススティック           |
| 叩き方（シンバル）   | ライドのベル                             |
| 叩き方（ハイハット） | フットスプラッシュ、ペダル（足で閉じる） |

全段階で共通: 強さは打点ごとの帯域のエネルギーから、録音の中の分布で「ゴースト・普通・アクセント」に分ける（アプリの `{g}`・`{ac}`）。格子は 16 分（＋ 8 分の 3 連、シャッフルの判定で切り替え）。シャッフルは小節ごとの裏の 8 分・16 分の位置の比から判定し、`swing: {kind, confidence}` と小節ごとの値を出す。

## 3. ユーザーの判断

### 決まったこと（2026-10-25、ユーザー）

1. 入力はドラムだけの録音。楽器は S-3 から始め、9 種類と S-拡張まで調べる。将来の展望（§10）は範囲外。
2. **合成**: 自前の TS のミキサー、キット 3 つ以上（調整用 MuseScore_General のドラム、開発用・ホールドアウトは T1 で探す別々のキット）。ライセンスは T1 で原文を確かめる。
3. **録音**: 電子ドラム ATV aDrums（音源 aD5）のライン出力の音だけで 6 本（開発用 4、ホールドアウト 2）。楽譜はこちらで用意する（§4）。
4. **始まりの許す幅**: ±50 ms が主（mir_eval の既定）、±25 ms も出す（§5）。
5. **テンポ・拍子**は `.txt` で渡す。既存の拍の追跡は読むだけで動かし、当たりを記録だけする。
6. **TS で直接作る**。Python は mir_eval との採点の一致と librosa の `onset_detect` との比べだけ。
7. **目標**: §5 の値は仮。T9 を見て G1 で確定、S-9・S-拡張は G2 で決める。

### 持ち越しの質問（スパイクの後、main で決める）

1. **S-拡張のアプリでの書き方**: 新しい楽器（スプラッシュ・チャイナ・カウベル）は `drumKit.ts` に新しい種類（id・`\articulation` の番号・キー・五線の位置・符頭）を足すのか、叩き方（リムショット・クロススティック・ライドのベル・フットスプラッシュ・ペダル HH）は今の楽器の印（ドラムの alphaTex の書き方に印を足す）にするのか、別の種類にするのか。alphaTab が描けて鳴らせるか（`m5-alphatab-findings.md` と同じ確かめ）。スパイクは解析の `inst` に仮の名前（`SP` `CN` `CB` `SD.rim` `SD.xs` `RD.bell` `HH.foot` `HH.fsp`）を出すだけ。
2. **JS の大きさの枠**: 今の Worker は合わせて gzip 56.6 KB（枠 60 KB）。ドラムの Worker を足すと枠を超える見込み。「Worker ごとの枠」（使う 1 つだけ読み込まれる）に変えるかを main で決める。スパイクはドラムの Worker 単独の大きさを測る。

## 4. データ

### 合成（正解が完全に分かる。`render/drum/`）

- **パターン**: 種で固定した生成器。8 ビート・16 ビート・ハーフタイム・シャッフル（8 分・16 分）・バラード（RD・CR）・ファンク（ゴースト）、4・8 小節ごとのフィル（タム・16 分の連打）、小節の頭の CR。正解は `DrumEvent[]`（アプリのモデル。`serializeDrums` で往復）から作る。S-拡張の楽器・叩き方は正解の中だけの仮の名前で入れる。
- **変化**: テンポ 60〜200、拍子 4/4（3/4・6/8 は少し）、シャッフルの比（2:1 と弱い 3:2）、時刻の揺れ（σ 5〜20 ms）、強さの揺れ・ゴースト・アクセント、部屋の響き・マイクの近さ（近い・頭上・スマホ 1 本）、雑音（30・20 dB）、キットのチューニング。
- **レベル**: **D0**（1 キット、揺れなし、乾いた音）、**D1**（揺れ・強さ・ゴースト）、**D2**（D1 ＋部屋・雑音 30 dB・フィル）、**D3**（D2 ＋スマホ 1 本・雑音 20 dB・密なシンバル・別チューニング）。
- **分け方**: 調整用（種 1〜3、キット A）・開発用（種 4〜5、キット A・B）・ホールドアウト（種 6〜7、**キット C と部屋は調整・開発で使わない**、`heldOut: true`）。
- 同じ種で 1 ビットも同じ wav（ゴールデンのハッシュ）。サンプルは gitignore の `drumkits/` に、SHA-256 を固定した取得スクリプトで置く。

### ユーザーの録音（電子ドラム aD5、ライン出力）

- **性格**: 「人が叩いた、サンプルの音色」。時刻・強さ・叩き方は本物だが、部屋の響き・マイクのかぶりが無く、音色がそろっている。そのため録音の結果は**生ドラムの精度の楽観的な見積もり**として扱う（結論にも書く）。
- **楽譜（T4b）**: こちらで 6 本を、アプリのドラムの alphaTex（`parseDrums` が通る、16〜32 小節）で書く。開発用は a 8 ビート中くらい・CR、b 16 ビート・ゴースト、c シャッフル、d ゆっくり・RD・タムのフィル・オープンとクローズの HH・S-拡張の叩き方。ホールドアウトは **T4b が先に決める**（どの叩き方も開発用にある）: e 16 ビート・ゴーストの別の楽譜、f シャッフルとフィルの別の楽譜。ユーザーはテキスト入力（またはドラム画面）に貼り、見ながら叩く。
- **録り方**: クリックはヘッドホン（録音に入れない）。1 小節のクリックのカウントの後に叩く。aD5 のライン出力を WAV 44.1/48 kHz で録る。
- aD5 の打つ位置の検知で、リムショット・クロススティック・ライドのベルも録れる見込み（S-拡張で使う）。
- ホールドアウトの 2 本（e・f）は、開発用と別の aD5 のキットのプリセットで録る（ユーザーに確認）。
- **`.txt`**: `bpm:`・`拍子:`・`開始:`（楽譜 1 小節目の頭の秒。書き出したファイルの中での値。G2 の決定 9: 録音は叩いた最初の小節から書き出してあったので、6 本とも 0 秒に直した）・`叩き方:`（a〜f）・`キット:`（プリセットの番号）、楽譜と違って叩いたと分かっている小節（**採点から外す**）。正解は楽譜で、解析の後は直さない。
- **時刻の合わせ**: 採点が録音ごとに 1 つの全体のずれ（±100 ms の中で一番合う一定のずらし）を合わせる。解析には渡さず、ずれの値はログに残す。
- **名前・ホールドアウト**: `drm-inbox/` に `a.wav` `a.txt`…。取り込みが `drm-NN-x` に変え、T4b が決めたホールドアウト（e・f）を解析の前にログに記録する。

### 見る時点（録音）

①基準線（T9 の設定）、②調整（T10〜T12）の後、③ホールドアウトと同じ最後の 1 回（T14）。②で直すなら合成で判断できる変更を 1 回まで。

## 5. 指標と目標（仮。§3 の決まったこと 7）

指標は自前で書き、T3 で mir_eval（`onset.f_measure`）と同じ値になることを確かめる。

| 指標                      | 中身                                                                                                                                                                                                                                      |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 楽器ごとの始まり F        | 楽器ごとに 1 対 1 の対応、±50 ms。適合率・再現率。±25 ms は合成だけ（録音は正解が楽譜の格子なので叩き手の揺れを測ってしまう。参考に出すだけ）。録音の主は格子の一致と ±50 ms                                                              |
| 格子の一致                | 小節・tick・楽器がすべて同じ打点の F（丸めの評価）                                                                                                                                                                                        |
| 取り違え                  | 時刻は合ったが楽器が違う打点の表（楽器 × 楽器）                                                                                                                                                                                           |
| 強さ                      | ゴースト・アクセントの一致の割合（記録）                                                                                                                                                                                                  |
| シャッフル                | 小節ごとの「無し・8 分・16 分」の正解率                                                                                                                                                                                                   |
| **直す手数 / キーボード** | 正解に直す最小の操作（打点を足す・消す・楽器を変える・1 格子ずらす・印を変える・シャッフルを切り替える）÷ ドラム画面で一から入れる手数（数え方は T3 で `src/lib/drumInput.ts` を読んで決める。繰り返しの小節をコピーで 1 手と数える版も） |
| テンポ・小節の頭          | 推定のテンポの誤差、小節の頭の F（記録）                                                                                                                                                                                                  |

| 項目                                 | 目標（仮）                                                                                |
| ------------------------------------ | ----------------------------------------------------------------------------------------- |
| S-3 合成の始まり F（各楽器）         | D0 ≥ .98、D1 ≥ .95、D2 ≥ .90、D3 記録                                                     |
| S-3 合成の格子の一致                 | D0 ≥ .97、D1 ≥ .92、D2 ≥ .85                                                              |
| S-3 シャッフル                       | D1・D2 で ≥ .90                                                                           |
| S-3 直す手数 / キーボード            | 合成 D2 ≤ .2、録音（開発用の平均）≤ .5 を願望                                             |
| S-9 合成の始まり F                   | D2 でタム・シンバル類 ≥ .80、HH と HO の分け ≥ .75                                        |
| S-拡張                               | 記録だけ                                                                                  |
| ホールドアウトと開発用の差           | 合成 .1 以内、録音 .15 以内                                                               |
| 速さ（5 分、PC の Chromium）         | 15 秒以内（願望は鼻歌なみの 5 秒。比べ: コード 約 18 秒、鼻歌 約 5 秒）                   |
| メモリ（解析の前からの増え方、5 分） | 200 MB 以下（比べ: コード +250 MB、鼻歌 +130 MB）                                         |
| 大きさ                               | ドラムの Worker 単独で gzip 25 KB 以下（共有の FFT を含む。合わせた枠は持ち越しの質問 2） |
| 画面・通信                           | Worker で止めない。通信 0 件（`noNetwork` のテスト）                                      |

## 6. 主な設計判断

1. **置き場所**: 解析 `ts/drum/`（`onset.ts`・`bands.ts`・`nmf.ts`・`classify.ts`・`toms.ts`・`cymbals.ts`・`strength.ts`・`quantize.ts`・`swing.ts`・`toDrums.ts`・`analyze.ts`・`config.ts`・`score.ts`・`cli.ts`）、合成 `render/drum/`、取り込み `py/drum_intake.py`、Worker `ts/browser/drumWorker.ts`・`drumBench.ts`（新しいファイル）。
2. **設定**: `ts/drum/config.ts` に全部の値とハッシュ。基準線（T9）はコミットで固定。結果の JSON に設定のハッシュとコミット。
3. **結果の JSON**: 既存の `drums`・`swing` をそのまま使い、任意の欄だけ足す（`drums[].tick`・`bar`・`mark`（`g`/`ac`）・`alts`（楽器の 2 番目の候補）、`swingBars`）。`swing` が無い = シャッフル無し（既存の型は `'8' | '16'` だけ）。既存の読み手を壊さない。
4. **正解を読まない**: `analyze` が受けるのは音とユーザーが知っている情報（テンポ・拍子・開始）だけ（構造とテストで守る）。
5. **候補**: 打点ごとに楽器の 2 番目の候補と確からしさ（スパイク 4 と同じく、決めつけより候補）。

**スパイク 5 の問いへの答え**: ドラムだけの録音から、BD・SD ははっきり取れ、HH・シンバル類・タムは条件つきで取れる。下書きとして「役に立つか」は、2 つの目的で答えが違う。

1. **慣れた人の速さ**: まだ示せていない。直す手数がキーボードで一から入れる手数の約 5〜6 割（S-9 でホールドアウト .499・開発用 .614、S-3 で開発用 .546（平均 .566）・ホールドアウト .610）で、願望の ≤ .5 は S-9 のホールドアウトが縁に着いただけ。コピー版（同じ小節のコピーを 1 手と数える）のキーボードと比べると 1.35〜1.8 倍で、「一から打ってコピーする方が速い」。ただしこの比は、直す側にコピーを数えないので 1 を超えやすい（非対称）。
2. **譜面に不慣れな人の下書き**: **確信度のしきい値をつけた運用なら使える見込みがある**（ユーザーの結論、2026-11-01）。HH は元から難しい（弱い HH 1 打を耳で見つけるのも難しい）が、アクセントの HH のように確信度が高い打点もある。確信度が高い打点だけを下書きに入れ、残りは休符にすれば、実用になる。根拠: ホールドアウトの S-9 の HH は適合率 .876・再現率 .594。誤りは余計な打点より見落としが多い。BD・SD は適合・再現とも .84〜.90。しきい値の効きは、メインセッションが事後に記述的に確かめた（2026-11-01。値の選択には使っていない。解析は再実行していない）。元は開発用の録音の保存済みの出力（`recordings/drum-results/look3-S-9/`、設定 `fb158baf9dfe`、a〜d）で、HH だけ、録音ごとの中央値のずらしの後に ±50 ms で単純な貪欲法の対応づけをしたので数字は概算。

- 正解の HH 483 打、推定 320 打、当たり 255 打、外れ 65 打。
- 確信度の四分位点: 当たり .70 / .78 / .99、外れ .51 / .53 / .77。外れの多くは確信度が低いが、約 4 分の 1 は確信度が高い（≥ .77）。
- しきい値 × 適合率 / 再現率: なし .797 / .528、≥ .6 .871 / .420、≥ .8 .931 / .251、≥ .9 .941 / .199。しきい値を上げると適合率は上がるが再現率が大きく落ちる（休符が増える）。
- ホールドアウトの打点ごとの出力は保存しておらず（集計だけ）、使い終えたので、この確かめは開発用だけ。しきい値は、これらの開発用の録音ではなく、調整用の合成と**新しい録音**で選ぶ（持ち越し 1）。

そのほかの結論:

- **S-3 は基準にしない。S-9 を基準の段階にする**。S-3 はホールドアウトで HH を 251 打すべて取り逃した（未知の音色で金属の列に吸われる）。S-9 は金属を減り方・似方で分けるので同じ録音で HH .708。
- **未知のキットへの強さは揺れる**。既知のキット（調整に使った音）では目標を満たすが、未知のキットでは HH・金属の分け方が大きく揺れる。合成のホールドアウト（キット C）の差 .1 以内は**未達で、未達のまま残す**（結果を見てから目標を変えない。ユーザー決定 2026-11-01）。向きも両方に出た（S-9 は B が上、S-3 は C が上）ので、調整への合わせすぎというより、未知のキットごとの揺れ。録音のホールドアウトは別のプリセット 1 種類（Real Groove）だけで、「未知の音色」の根拠は 1 種類分。
- **録音は楽観的な見積もり**: aD5 のライン出力は部屋の響きもマイクのかぶりも無い。生ドラムのマイク録音は測っていない。
- **スプラッシュ・チャイナは録音で未確認**。ユーザーの曲には出る（G2 の決定 8）が、6 本の楽譜には無かった。合成ではキット A でスプラッシュ .98・チャイナ 1.00、未知のシンバルのチャイナは取れない（D・H で 0）。次の録音に入れる。リム/クロススティック・ライドのベル・カウベル・ペダル HH も録音には無く、「無いときに誤って出す数」（4 本で 7 打）しか分からない。
- **`開始:` のずれは誤りが目立たない**: 1 小節ずれていても繰り返しの型で多くの打点が合い、R3 まで気づかなかった。取り込みで 1 小節目の頭の位置を確かめる手順が要る。
- **合成の改善は半分しか本物に移らない**: R1（本物に近づけた合成）で CR を直した結果、本物で HH → RD が増えた（開発用 ③ S-9）。合成の D1 の HH 95% は本物の精度を保証しない。
- **速さ・メモリ・大きさは収まる**: Worker 31.5 KB は枠 35 KB の中（G2 の決定 4）。アプリに入れるときの「Worker ごとの枠」（持ち越しの質問 2）は main で決める。
- 解析は AI を使わず（決めたテンプレートの NMF と規則）、通信しない。ホールドアウトは守った（録音は 1 回、合成のホールドアウトは別の 1 回）。

## 持ち越し

main（アプリへの組み込み）で決める・やること:

1. **確信度のしきい値の運用**: 楽器ごとに「確信度しきい値 × 適合率・再現率」を測る（合成の調整用で、本物は新しい録音で）。確信度が高い打点だけを下書きに入れ、残りは休符にする「確かな打点だけ」の下書きモードを設計する。
2. **S-拡張のアプリでの書き方**（持ち越しの質問 1）: 新しい楽器（SP・CN・CB）を `drumKit.ts` に足すか、叩き方の印にするか。優先はスプラッシュとチャイナ。クロススティック・ベル・ペダル HH は見送ってよい（G2 の決定 8）。alphaTab が描けて鳴らせるかの確かめ。
3. **Worker の大きさの枠**（持ち越しの質問 2）: 31.5 KB（枠 35 KB）。既存の Worker と合わせた枠を「Worker ごとの枠」に変えるか。
