## 2. must-fix

### M1 合成の音符 F が「歌った高さ」で採点され、「正しい音名」の割合より高く出る

- 場所: `spikes/analysis/ts/hum/score.ts:101`（`sungMidi = midi + cents/100`）・`:109-110`、正解側 `ts/hum/baseline.ts:82`（合成の正解に `cents` を渡す）と `render/hum/truth.ts:101`（`cents` は 1 音ごとのずれ＋録音全体のずれ＋ゆっくりした高さの移りを含む）、推定側 `ts/hum/report.ts:73` と `ts/hum/notes.ts:910`（推定の `cents` は、推定したチューニングを引いた後の残り）。
- 何が起きるか: 合成の正解の高さは「書いた音＋声のずれ」、推定の高さは「選んだ半音＋チューニングを引いた残り」で、±50 cents で比べている。声が書いた音から 50 cents 以上ずれて歌った音（H3・H4 の声は、わざとそう作ってある）では、解析が書いた音と違う半音を選んでも「合っている」と数える。逆に録音は、正解が書いた音だけ（`cents` なし、`heldout_eval.ts:83`）なので、「正しい音名か」で採点している。合成と録音で、同じ名前の指標の意味が違う。
- 大きさ（開発用の合成、小節頭、hum-v3。`out/t14/cents.ts`）:

  | レベル | 今の F（始まり） | 推定の高さにチューニングを足し戻した F | 書いた音名が同じかで採点した F |
  | ------ | ---------------- | -------------------------------------- | ------------------------------ |
  | H2     | .996             | .996                                   | .968                           |
  | H3     | .853             | .861                                   | .705                           |
  | H4     | .609             | .617                                   | .416                           |

  2 列目との差（推定の cents にチューニングを足していない分）は小さい。大きいのは 3 列目との差で、H3 で .15、H4 で .19。G1 で決めた H3 ≥ .75 は、今の定義では満たす（ホールドアウト .889）が、「正しい音名」の定義では開発用でも満たさない（.705）。

- 入力の補助として大事なのは「書くべき音名が出るか」で、丸めた音符の正解率（`quant.*`、MIDI の一致）と直す手数はこの定義になっている。F だけが違う。
- 直し方（T15）: 合成の F に「書いた音名で比べる」版（正解・推定とも `cents` を 0 にして ±50 cents＝MIDI の一致）を足し、表の見出しはそちらにする。歌った高さの版を残すなら、推定の高さを `midi + (cents + tuningCents)/100` にする（`analyze.ts` の注のとおり）。
- ホールドアウト: 合成のホールドアウトの 1 本ごとの出力は `out/hum/t11` に保存されていない（`t11-summary.json` は平均だけ）。新しい定義のホールドアウトの値は、もう一度走らせないと出ない。走らせるかはユーザーが決める（設定は凍結のままなので偏りは入らないが、ホールドアウトを 2 回見ることになる。走らせるならログに 1 行）。走らせないなら、新しい定義は開発用だけの値として書き、ホールドアウトは「未測定」とする。

### M2 録音の改善は採点の変更によるもの。未達の目標と合わせて、結論にそのまま書くこと

- 根拠（`out/results/heldout-log.jsonl` の 61〜64 行、開発用 4 本の平均）:

  |                                                                | F（始まり） | 丸めの正解率 | 直す手数 / キーボード |
  | -------------------------------------------------------------- | ----------- | ------------ | --------------------- |
  | 見る時点 ①（基準線）、正解をそのまま                           | 0           | 0            | 1.039                 |
  | 見る時点 ①、正解を時刻と移調で合わせた診断                     | .406        | .255         | .666                  |
  | 見る時点 ②（hum-v3）、正解を解析の格子の上に置く（採点の基準） | .364        | .228         | .608                  |
  | 見る時点 ②、時刻を合わせた診断                                 | .408        | .252         | .608                  |

  0 → .364 は、`開始` の意味の変更（1 音目の秒）と、移調を除く採点（`transposeInvariant`）と、正解を解析の格子に置く採点の変更から来ている。同じ基準（時刻を合わせた診断）で比べると、段階 2・3 の解析の変更（格子の位置合わせ、しゃくりで区切らない規則、hum-v3 の調整）の効果は F .406 → .408、丸め .255 → .252 で、ほぼ 0。直す手数だけ .666 → .608 と少し良くなった。合成の H4 は調整用で F .284 → .593 と大きく上がったが、録音には移らなかった。H4 もまだ本物の代わりにはならない。

- 正解を解析の格子に置く採点が数字を大きく見せていないか: 格子は 16 分の単位でしか動かず、正解の音の始まりには合わせていない。格子を間違えると正解もずれて F は下がる。実際、正解を使って時刻を合わせた診断（.408）より低い（.364）。ユーザーの書いた `開始` をそのまま使うと .039 で、これと比べれば有利。どちらにしても、録音の F は「解析が自分で決めた拍の位置から見て、正しい音が ±50 ms に出たか」という意味になる。
- 移調を除く採点: 録音ごとに −24〜+24 の 49 通りから、一番多く合う移調を選ぶ。点の低い録音では少しだけ有利に出る。また直す手数に「移調する」の 1 手を足していない（N1）。
- 結論に書く未達（T16、表で「未達」と書く）:
  - 合成の音符 F の H1 ≥ .95: ホールドアウト .919（開発用 .983）。F の ±1 半音版が .982 なので、ほとんどが半音の誤り（S9 の仮説を参照）。
  - 合成の丸めの正解率の H1・H2 ≥ .80（§5。G1 では変えていない）: H2 のホールドアウト .778。開発用 .931 との差 .153 は、§5 の「同じレベルで .1 以内」も超える。
  - 録音の直す手数 ≤ .5: 開発用 .608、ホールドアウト .666。S1 のとおり、実際の編集の手数はこれより多い見込み。
  - メモリ（S5）。
- 満たしたもの: 合成の F の H0・H2・H3（今の定義）、直す手数の H2 .143 ≤ .15（ぎりぎり）・H3 .388 ≤ .5、ホールドアウトと開発用の差（合成の F は各レベル .1 以内、録音は F .123・手数 .058 で .15 以内）、速さ、大きさ、画面、通信。

## 3. should-fix

### S1 直す手数の「分ける」「まとめる」がアプリの編集に無い（数えすぎではなく、数え足りない）

- 場所: `ts/hum/score.ts:377-470`（`editScript`。1 音を 2 つに分ける・2 音を 1 つにまとめるを 1 手とする）、`ts/hum/score.ts:351`（キーボードの手数）。
- アプリのメロディ画面の `KeyM`・`KeyV`（`src/components/MelodyEditor/MelodyEditor.tsx:96-97`）は、歌詞の音節を「つめる・分ける」操作（`src/lib/melodyLyrics.ts:181`・`:198`）で、音符を分け・まとめる操作ではない。今のアプリでは、分ける＝長さを変える＋音を足す（2 手以上）、まとめる＝消す＋長さを変える（2 手）。
- 大きさ: 開発用の合成では、分ける・まとめるを 2 手にした上限で H3 .370 → ≤ .387、H4 .602 → ≤ .655。録音は余分な区切りが開発用 4 本の合計で正解 219 音に対し 56 あり、すべてまとめるで直すと、直す手数 / キーボードは最大で約 +.16 増えうる（.608 → 最大 .77 ほど。未測定）。
- さらに、直す手数には「どこが違うか聞いて探す」「その音まで移動する」が入っていない。一から入れるときは前から順に打つだけで、移動は要らない。比べ方として、解析の側に有利。
- 直し方: `editScript` に操作ごとの重みを渡せるようにし、アプリの実際の操作（分ける 2、まとめる 2）でも出す。結論では「手数の比はアプリでの手間の下限」と書く。できれば計画 §7 の最後の「1 曲だけキーボードで入れる時間を測る」を、直す時間でも測る。

### S2 全体に遅れて歌う癖が 16 分の半分に近いと、反対側に倒れて全部の音が 16 分ずれる

- 場所: `ts/hum/quantize.ts:273-275`（癖の上限 min(80 ms, 16 分の 0.45)）、`:212-220`（0 から中央値で動かす推定）。
- 例（調整用の合成 `syn-h2-rand-s2`、107 bpm、16 分＝140 ms）: 正解の遅れの中央値は +52 ms。検出した始まりは、しゃくりなどでさらに遅れて、16 分の半分（70 ms）を超え、推定は −46 ms（反対側）になった。始まりの正解率は .30、丸めの正解率は .067（F は 1.000）。1 音目を渡しても（−0.7 拍＋tick）、丸めは .033 のまま。
- 録音でも、丸めの誤りのうち「始まりの位置が違う」が多い（開発用 4 本の合計で、高さの合った組 128 のうち 45）。この仕組みが一部に効いている可能性がある（未確認）。
- 直し方の案: 癖の推定と格子の位置合わせを一緒に決め、1 音目の位置（分かるとき）で、どちらに倒すかを決める。または「全体を 16 分前（後ろ）にずらす」を丸めの候補として出す（1 手で直せる候補）。

### S3 格子の位置合わせが、短い雑音 1 つで全体をずらす

- 場所: `ts/hum/quantize.ts:285-288`（`firstNoteSec − phaseRangeBeats` より後で最初に見つけた音を 1 音目とする）。重みが 20 なので、この 1 音でほぼ決まる。
- 例（手で作った音符、`out/t14/probe.ts` (b)）: 本当の 1 音目の 0.3 拍前に 60 ms の短い音（息・クリックの漏れ）があると、位置は −1 ではなく −2 になり、全部の音が 16 分遅れて書かれ、余分な音も 1 つ残る。最短の長さの規則（16 分の半分、120 bpm で 62 ms）を超える長さなら、実際に起こる。
- 直し方の案: 1 音目の候補を「8 分以上の長さ」か「`firstNoteSec` に一番近い音」にする。または、2 番目の候補の位置を `GridPhaseMeta` に出して、画面で選べるようにする。

### S4 `小節頭:` のとき、1 小節目より前に歌った音が tick 0 に潰れる

- 場所: `ts/hum/quantize.ts:312`（tick を 0 以上に切る）、`:323-349`（同じ位置の音を動かす・まとめる）、`:356`（警告は数だけ）。
- 例（`out/t14/probe.ts` (a)）: 1 小節目の頭を正しく渡し、その前に弱起の 2 音を歌うと、2 音のうち 1 つは消え（まとめられ）、1 小節目の頭の音は 16 分後ろに押される。結果は普通に往復を通るので、気づきにくい。
- 1 音目＋tick を渡す今の取り込みでは起きないが、アプリで「小節頭」を渡す使い方や、頭の前の雑音では起きる。
- 直し方の案: 1 小節目より前に音があれば、弱起の小節を 1 つ前に足す（小節頭を 1 小節前にする）か、少なくとも分かる警告（「1 小節目の前に n 音」）を出す。

### S5 メモリの目標を満たさない。安く減らせる所がある

- 計画 §5「解析の前からのブラウザのプロセスの増え方 5 分で 150 MB 以下」に対し、T12 の初回（cold）は +180〜181 MB（3 ページとも）。**未達**。速さ（1 分 0.97 s、5 分 4.49 s）は満たす。
- 同じページで続けて走らせると、解析の前の値が 109 → 291 → 321 MB と積み上がり、最高 430 MB になった（`out/hum/t12/perf.json`）。漏れなのか、GC がまだ返していないだけなのかは分からない。アプリで何本も続けて解析する使い方では大事なので、持ち越しに書く。
- 安く減らせる所（5 分・44.1 kHz の入力で見積もり）:
  1. `ts/hum/notes.ts:239`（`frameLevelDb`）が、22.05 kHz の信号全体の累積和を `Float64Array` で持つ。5 分で約 53 MB。窓は 10〜32 ms なので、フレームごとに足し算しても数千万回で済む（または Float32 で区切って持つ）。
  2. Worker が入力（44.1 kHz の Float32、約 53 MB）を解析の終わりまで持ち続ける（`ts/browser/humWorker.ts:41-46`、`ts/hum/analyze.ts:92` の後も `y` が生きている）。変換の後に手放せば減る。
  3. 計測ページの読み込みを、ファイルの rate ではなく 22050 Hz の `OfflineAudioContext` で行う（`ts/browser/humBench.ts:68`）。ブラウザが C++ で変換するので、自前の変換（時間の約 60 %、5 分で約 2.8 s）が要らなくなり、入力の大きさも半分になる。スパイク 3 で自前の変換にしたのは Python と同じ結果にするためで、鼻歌は Python と比べない（決定 3）ので、この理由は無い。ただしブラウザごとに変換の質が違うので、合成で f0 と音符 F を測り直す。
  - 1 と 2 だけでも 100 MB 前後減る見込みで、目標に入る可能性が高い（測り直しが要る）。
- 計測の入力は H0 の合成（サイン波に近い）だけ。時間の 9 割は変換と f0 で、声の種類にはほとんどよらないが、記録に書いておく。

### S7 `privacy_check` の鼻歌の並びの検出が、同じ MIDI の並びだけ
