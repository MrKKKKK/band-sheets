# スパイク 7 T9: 音が同じ組の読み分けの部品

想定読者: T9 の部品を V1 に組み込む T10 のエージェントと、G3 で `pairRule` の 2 つの規則から 1 つを採るメインのセッション・ユーザー。
目的: 計画 §2.3 の後処理をどう作ったか、単体テストで何を固定したか、調整用の合成で 2 つの規則がどう出たかを残し、T10 が気をつける所を渡す。

2026-11-22。コードは `spikes/analysis/ts/chords2/pairRule.ts`（部品）、`analyze.ts`（呼び出し）、`eval/t9_pairs.ts`（調整用の合成の採点）。開発用・ホールドアウトは開いていない（見る時点は増えていない）。

## 1. 作った規則

- **順**: `analyze()` の最後（Viterbi・区間のまとめ・上位 k 候補の後）に 1 回だけ動く。M3 は T8 の分で、M3 が組の区間に触らないことは T8・T10 で守る（`otherReading(r, stage) !== null` が「組の読み」の判定）。左から順に、前の区間はここで決めた読み、次の区間は Viterbi の読みを使う。和音の無い区間（N）は前後のつながりを切る。
- **対象**: その段階に両方の種類がある組だけ（V1 = `6`/`min7`・`m6`/`m7b5`、V2 から `sus2`/`sus4`）。V0 では何もしない。aug・dim7 は対象外で、根音は今の `ROOT_TIE` のまま。
- **点**（読み r ごと。ノートの段の値で固定、調整なし）:

| 点 | 値 | `context` | `bassRoot` |
| --- | --- | --- | --- |
| ベース | b が r の根音なら +1.0 | ○ | ○ |
| 前後 | 段(前 → r) × r の区間の調の確信度 + 段(r → 次) × 次の区間の調の確信度 | ○ | 0 |
| 根音の続き | r の根音が前か次の根音と同じなら +0.6（1 回だけ） | ○ | ○ |

- 段は `harmony.json` の `tierMatrix`（強 1.0・中 0.6・弱 0.3）。新しい種類は §1.4 の仲間の行・列を読む（`sus2` は maj と min の強い方）。加えて §3.7・§6.2 の「`sus2` → 同じ根音のメジャー系・マイナー系・ドミナント系」を中（0.6）で足した（`tierMatrix` は同じ根音の移りを持たないため）。調は区間の最初の拍の `BarKey`。確信度が負なら 0、調が無ければ前後の点は 0。
- **選び方**: 合計が高い方。差が 1e-9 以下なら同点で、今の語彙（v1a）にある読み（`min7`・`m7b5`・`sus4`）。Viterbi がどちらを出したかには依らない。
- **候補**: 選ばなかった読みを区間の `chordCandidates`（1 つ）にいつも入れる。上位 k の `candidates`・確信度・区間の長さは変えない。
- **ベース b**: B の方法が `off` のときは b が無い（ベースの点 0）。方法が入っているときは「区間の和音は b を含む」（M3、§2.1）として b = `/X` の音、無ければ根音（`segmentBassPc`）。読みを変えたら b はベースのまま残り、新しい根音と違えば `/b` になる。

- **正解表の 25 行**（`TRUTH_ROWS`）を、行の調（確信度 1）・ベース・前後で 2 つの規則に通し、選んだ読みを行ごとに固定した。Viterbi の読みがどちらでも同じ結果になることと、もう一方がいつも候補に残ることも見る。

| `bassRoot` | 23/25 | 6/8 | A10（手がかりが無く同点 → Am7）、B5（ベース F# が F#m7b5 の根音） |

## 3. 調整用の合成（T5 の組の例、`c2-t-pair-*` 216 本）

`npx tsx ts/chords2/eval/t9_pairs.ts run` → `report`（`spikes/analysis` から、デブコンテナで 4〜5 分）。入力の音量をそろえ、v1a の前段 → chords2（切り替えは `pairRule` 以外切）→ 後処理。ベースは 2 通り: 推定（スパイク 6 の `segmentBass` を chords2 の区間に。T8 と同じ設定）と、正解のベース（ベースの誤りを分けるため）。単位は正解表の行が出る区間（V1 は A・B の 171、V2 は 225。うち食い違う例 63・72）。「音だけ」「ベースだけ」は組を読めたと仮定した参考（`eval/pairs.ts`）。

V2（主な表）:

| 行 | 食い違う例 | 全体 |
| --- | --- | --- |
| 規則なし（Viterbi のまま） | 3/72 = .042 | 12/225 = .053 |
| `context`（推定ベース） | 6/72 = .083 [.039–.170] | 13/225 = .058 [.034–.096] |
| `bassRoot`（推定ベース） | 6/72 = .083 [.039–.170] | 13/225 = .058 [.034–.096] |
| `context` / `bassRoot`（正しいベース） | 5/72 = .069 | 18/225 = .080 |
| 参考: 音だけ | 27/72 = .375 | 90/225 = .400 |
| 参考: ベースだけ（推定 / 正しい） | 35/72 = .486 / 27/72 = .375 | 178/225 = .791 / 180/225 = .800 |

- **後処理まで届く区間が少ない**: 行の区間で Viterbi が組の読み（どちらか）を出したのは V2 で 20/225（食い違う例 7/72）、V1 で 13/171。ほかは 3 和音（`C`・`Am` など）で、後処理は動かない。全体の当たりが低いのはこのため。
- **組として読めた区間だけ**（V2 20 区間）: 食い違う例は両方の規則とも 6/7（正しいベースで 5/7）、全体 13/20（正しいベースで 18/20）。規則なし 3/7・12/20、ベースだけ（推定）6/7・13/20。
- **2 つの規則の差は 0 区間**（V1・V2、どちらのベースでも）。前後の点は付いている（60 本を見て 13 判定のうち 12 で前後の点が 0 でない）が、ベースと根音の続きの差を逆転させた区間が無かった。G3 の決まり（食い違う例で差が 5 区間未満なら `bassRoot`）に当てると、調整用では `bassRoot`。決めるのは G3 で、開発用（T10 の ③）の数を見てから。
- 推定ベースは食い違う例の 76 % で正しいが、組として読めた 7 区間では 0/7（`/X` の音ではなく根音などを拾った）。それでも当たりが 6/7 なのは、外れたベースが正解の根音に当たったため（偶然の分を含む）。

## 4. T10 への申し送り

1. **`6` は Viterbi から出ない**: `6` の型は同じ音の `min7`（基本の種類）と点が同じなので、新しい種類の門（`newQualityMargin` 0.05、`vocab_weight` 1.0）を必ず通らない。`C6` はこの後処理でしか出ない。`m6`・`sus2` は門を通りうる。組の区間が 3 和音で読まれる（上の 20/225）のは門と 7 の和音の門（`seventh_weight`）の値の問題で、T10 の調整の対象。
2. **ベース b の渡し方**: `segmentBassPc` は「B の方法が入っていれば区間の和音は b を含む」と置いた。T8 の M1・M3 の出力がそうなっているかを T10 で確かめる（違えば b を別に渡す）。B が切のときはベースの点が無い。
3. **M3 は組の区間を飛ばす**（§2.1）: 判定は `otherReading(reading, stage) !== null`。
4. **前後の点の調**: 区間の最初の拍の調だけを使い、転調の境目で前の調との max を取る事前分布（ノート §6.3）の扱いはしていない。転調の多い録音で効くかもしれない。
5. **`sus2` の解決の段**（ノート §3.7・§6.2、中）は後処理の点にだけ入っていて、遷移の事前分布（`prior.ts`）には無い（同じ根音の移りは 0 のまま）。V2（T11）で事前分布にも入れるかを決める。
6. 計画 §2.3 の「正解表の手計算で 19 行対 20 行」とこの実装の 24 対 23 は合わない。手計算の前提（仲間の写し・`sus2` の解決・同点の決まり）が違ったためと思われる。正解表の行そのものとの食い違いは上の 3 行（B8・A10・B5）だけ。
7. 結果の JSON の `chordCandidates`（計画 §6）はまだ無い。区間の `chordCandidates`（`{root, quality}` の配列）から写す。
