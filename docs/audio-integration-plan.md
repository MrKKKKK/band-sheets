- 研究ブランチの `CLAUDE.md`（`spikes/analysis/ts` の TS 移植、`ts/hum`・`render/hum`）、`spikes/analysis/ts/THIRD_PARTY.md`。

### 守ること（決まっていること）

- **AI・学習済みモデルを使わない**。決まった計算式と規則だけ（メモ §9）。移すときに新しい手法を足さない。
- **サーバーなし**。解析は **PC のブラウザの中だけ**。タブレット・Chromebook は演奏中に見るためのもので、解析はしない。
- **入力はファイル**（ユーザーが音声ファイルを選ぶ）。Drive に音を上げない。
- **結果は下書き**。ユーザーが直す。精度は最優先ではない。候補を出し、1 つに決めつけない。「正しい」と言えるのは作曲者だけで、決めるのはユーザー。
- **ChordPro のテキストが唯一の元**（`CLAUDE.md` の Source layout）。候補などの解析の情報は、テキストに書かない限り残らない。
- 純粋な関数は `src/lib` でテスト駆動。画面は Claude Design でスケッチし、**ユーザーが同意してから作る**。1 つの画面は 1 つの目的。
- GitHub Flow: `main` から `feature/…` などの短いブランチ、PR、CI が通ったら squash merge。研究ブランチは main に merge しない。
- ライセンス: GPL・LGPL・AGPL は入れない。librosa（ISC）と fft.js（MIT）の表示を、ビルドした JS にも残す。

## 1. 目的とスコープ

### 目的（「入力の補助」の 2 つの意味。ユーザー、2026-10-18）

1. **譜面を書き慣れた人の速さ**: 録音から、テンポ・調・セクション・コードの下書きを作り、一から書く手間を減らす。
2. **譜面を書くのが難しい人の下書き**: 子どもの頃にピアノ・バイオリンを習った人、独学のギターの人、大人の趣味の人などが、**歌うだけで**メロディの高さと音の長さのおおよその下書きを得る。
   - スパイク 4 では、(1) の速さは鼻歌では示せなかった（直す手数はキーボードの約 6 割）。(2) は見込みはあるが未証明（高さの 2 番目までの候補 約 .55、リズムが弱い。不慣れな人での評価はしていない）。
   - そのため鼻歌は **任意の機能で、「下書き」とはっきり示す**（ユーザー確認済み 2026-10-18）。正確な書き起こしとは言わない。
   - 不慣れな人は誤りに気づきにくい。**録音と下書きの聞き比べ**と**音ごとの候補**を、鼻歌の機能の必須の部品にする。

### やらないこと（この計画では）

- マイクで録る画面（クリックの出力と録音の入力の遅れを測っていない。スパイク 4 の T13 は未実施）。v1 は音声ファイルだけ。後で、小さな遅れの測定の後に足す（§10。§9 Q6 の決定）。
- バンドの音からの歌メロ、歌詞の聞き取り、歌詞のタイミング合わせ（タップ補助。メモ §4.5、優先 3）。
- 既にある曲へのコードの下書き（歌詞に合わせる入れ方も、コードだけの行のセクションとして足す入れ方も）。v1a は**新しい曲だけ**（§9 Q2 の決定）。歌詞に合わせるには音節の時刻が要る。
- ドラムの解析（次の研究スパイク）。ただし後で足せる形にしておく（§3.5）。
- タブレット・Chromebook での解析、10 分を超える音、4/4 以外の拍子のコード解析、解析の速さの改善（Worker の並列。持ち越し）。
- キャリブレーション（既知のフレーズを歌って声の癖を測る）。後で（§10）。

### v1 でユーザーが得るもの（おすすめの順番）

| 段階          | 中身                                                                                                                                                 | 解析器                                             |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| **v1a（先）** | 曲の一覧の「録音から新しい曲を作る」: 音声ファイル → テンポ・拍子（4/4）・調・セクション・コードだけの行（ダッシュ記法、§3.6）の**新しい曲の下書き** | スパイク 3（拍・小節の頭・コード・調・セクション） |
| **v1b（次）** | メロディ画面の「鼻歌から下書き」: クリックを聞きながら歌った録音 → **今の曲の 1 つのセクションのメロディの下書き**（聞き比べ・候補つき）             | スパイク 4（鼻歌）                                 |

**v1a を先にする理由**:

1. 解析器が成熟している。Python と同じ結果が出ることを 137 本中 136 本で確かめた（スパイク 3）。精度の評価もスパイク 1・2 で本物の録音まで済んでいる。
2. 出力が今のテキストの形にそのまま入る（`{tempo}`・`{key}`・セクション・`[C]` の行、低い確信度は `[Am?]`）。エディタに新しい機能が要らない。
3. 共通の土台（ファイルの読み込み、変換、Worker、遅延読み込み、ライセンス表示、エラー、中止）を v1a で作れば、v1b はその上に載る。
4. v1b は聞き比べと候補の画面が必須で、画面の量が多い。土台が先にあれば、v1b の作業は画面と変換に集中できる。

逆に v1b を先にする理由もあった（解析の JS が小さい 20 KB、曲の情報からテンポ・拍子・調を受け取れるので入力が少ない、目的 2 に直接効く）。**決定（2026-10-18）: v1a が先、v1b が次**（§9 Q1）。

- **元の記録**: `src/lib/analysis/origin.ts` に、写した研究ブランチのコミットと設定のハッシュ（コード `adec583eb3c6`、鼻歌 `f7a35fb44ae5`）を定数で置く。テストで「今の設定のハッシュ = この値」を確かめる。値を変えるとテストが落ちる。
- **直す順番**: 解析の中身は main で直接変えない。研究ブランチで直して測り（Python が基準の部分は Python が先）、その後に main へ「写し直し」の PR を出す（`chore/<issue>-analysis-sync-<commit>`）。main で直してよいのは、型・lint・import の道など、結果が 1 ビットも変わらない直しだけ。
- **lint・型**: スパイクのコードは oxlint・prettier・`tsc -b` の外にあった。写すときにアプリの規則（strict、oxlint、prettier）を通す。結果が変わる直しはしない（§2.4 の固定のテストで守る）。
- **librosa の表示**: librosa をなぞったファイルの先頭の 1 行（`// Follows librosa 0.11.0 (ISC, …)`）はそのまま残す。

### 2.2 Worker と遅延読み込み

- **置き場所**: 純粋な解析は `src/lib/analysis/`。ブラウザの部分は `src/analysis/`:
  - `decodeFile.ts`: `File` → `decodeAudioData` → モノラルの `Float32Array`（読み込みはメインのスレッドだけで可能。スパイク 3 と同じ）。
  - `analysis.worker.ts`: 22050 Hz への変換（自前の sinc）と解析。`{kind: 'chords' | 'hum', …}` を受ける 1 つの入口。
  - `analysisClient.ts`: `AnalysisClient` の型（`run(input, onProgress): Promise<Result>`、`cancel()`）と本物の実装。テストと Storybook 用に `fakeAnalysisClient.ts`。
- **Vite**: `new Worker(new URL('./analysis.worker.ts', import.meta.url), { type: 'module' })`。Worker は別の chunk になる。
- **画面も遅延読み込み**: 取り込みの画面（§4）は `React.lazy` + 動的 `import()`。曲の一覧・エディタ・ビューアの最初の読み込みには、解析のコードも取り込みの画面も入れない。**タブレットのビューアは解析のコードを 1 バイトも読まない**。
- **確かめ方**: `npm run build` の後に小さなスクリプト（`scripts/check-bundle.mjs`）で、①入口の chunk に解析の印の文字列が無い、②Worker の chunk に ISC と MIT の表示がある、③Worker の chunk の大きさ（gzip）を CI に入れる。
- **大きさの目安**: スパイクの計測で Worker はコード 33 KB・鼻歌 20 KB（gzip）。目標はコードと鼻歌を合わせて 60 KB 以下（表を含む）。
- **ライセンス表示**: Worker の先頭に `/*! … */` の表示を入れ、ビルドで消えないことを上の ②で確かめる。消える場合は `dist/THIRD_PARTY_LICENSES.txt` を出し、`/*! */` の 1 行でそれを指す。`fft.js` は版を固定（4.0.4、`dependencies`）。表示の元は `THIRD_PARTY.md` をアプリ用に写した `src/lib/analysis/THIRD_PARTY.md`。

### 2.3 Worker の決まり

- 1 回の解析ごとに新しい Worker を作り、終わったら `terminate()`（続けて解析したときのメモリの積み上がり 165 → 272 MB の対策。原因は不明のまま）。
- 音のデータは `ArrayBuffer` の移譲（コピーしない）。メインのスレッドの `AudioBuffer` は渡した後すぐ手放す。
- 進み具合は段階ごと（読み込み・変換・拍・コード・セクション・調、または f0・音符・丸め）に送る。
- Worker の中で通信の道（`fetch`・`XMLHttpRequest`・`WebSocket`・`importScripts`・`EventSource`）を最初に消す。テストでも確かめる（§5）。

### 2.4 研究ブランチとの一致を守る（固定のテスト）

- 研究ブランチの比べのテスト（Python の中間値）は写さない（中間値は main に無い）。
- 代わりに **固定の答え（golden）のテスト**を置く: 合成の小さな音（コード用 1 本・鼻歌用 1 本、各 10 秒前後、合わせて 500 KB 以下）と、研究ブランチの TS の解析器（`origin.ts` のコミット）が出した結果の JSON をコミットする。main の解析器が同じ JSON を出すことを確かめる（離散の欄は完全一致、小数は 1e-6 以内）。
- 合成の音は研究ブランチの `render/` で作る（合成だけ。録音は使わない）。作り方は `src/lib/analysis/fixtures/` のテストのファイルの先頭のコメントに書く。

## 3. データの流れ

```
File ─decodeFile→ Float32Array(モノラル) ─Worker→ 解析結果（中間 JSON、メモリの中だけ）
   └→ 聞き比べ用の object URL（端末の中だけ）
解析結果 + 画面の選択（候補・ずらし・移調） ─純粋な変換→ テキスト（ChordPro / alphaTex）─1 回の setText→ 曲
```

### 3.1 中間 JSON

- 形は研究ブランチと同じ `format: 'band-sheets-analysis', version: 1`（コードは `TsAnalysisResult`、鼻歌は `HumAnalysisResult`）。型は `src/lib/analysis/` が持つ。解析と変換の間の約束はこれだけ。
- v1 では**保存しない**（メモリの中だけ。画面を閉じたら消える）。決定済み（§9 Q4 (a)）。

### 3.4 候補とユーザーの直し

- **候補は確かめの画面（S3・S4）の中だけの一時的な状態**（決定。§9 Q4 (a)）。テキストには書かない。
- 流れ: 解析 → 確かめの画面で全体の直し（小節の頭のずらし、テンポ、オクターブ・移調）と、気になる所の候補の選択 → 「下書きを入れる」で 1 回だけテキストに書く → その後は**今までのエディタ**で直す（かんたん入力・テキスト入力・メロディ画面）。
- 書いた後のテキストは普通の曲と同じ。解析の情報には戻らない（作り直したいときはもう一度解析する。コードで 30 秒前後、鼻歌で数秒）。
- 鼻歌を入れるセクションに音符が既にあれば、上書きの確認をする（取り消しは確認の画面で「キャンセル」）。

### 3.5 ドラムを後で足すために

- 解析の種類を 1 か所の表にする: `kind`（`'chords' | 'hum'`、後で `'drums'`）ごとに、Worker の中の入口、入力の型、結果の型、変換の関数、確かめの画面。
- 中間 JSON には既に `drums: [{t, inst, strength, confidence}]` と `swing` の欄がある（メモ §5.2）。変換は `serializeDrums` で書く（`drumDraft.ts`）。画面は「録音から取り込む」の種類を 1 つ足し、確かめの画面を 1 つ足す。
- Worker の `kind` ごとに、使わない解析器を読まないように、Worker の中で動的 `import()` で分ける（大きさが気になったとき）。

### 3.6 コードだけの行の書き方（ダッシュ記法。§9 Q3 の決定）

スパイク 1 で、ユーザーが録音の正解を書くときに使った自分流の書き方（`research/audio-analysis` の `spikes/analysis/RECORDING.md`、「ダッシュ + 角括弧」）をそのまま使う。コード譜サイト（ChordWiki など）の取り込みに近い形。解析器が出す拍・コードの時刻から書けるので、1 小節に 1 つのコードより正確にリズムが残る。

- 形: `|[C]--------|[C]----[F]----|[G]--------|[G]--------|`（4/4 の例）。コードを `[ ]` で囲み、後ろの `-` 1 つが**八分音符 1 つぶん**、`=` 1 つが**十六分音符 1 つぶん**（ユーザーの決定）。`|` で小節を区切る。**1 行 = 4 小節**（ユーザーが選んだ）。最後の行は 4 小節に満たなくてよい。行の頭と終わりの `|` は書く（読むときはなくても可）。
- 1 小節の長さ: `-` を 1、`=` を 0.5 と数えた合計が、拍子の八分音符の数（4/4 は 8、3/4 は 6、6/8 は 6）に等しい。**合わないときはエラー**（行番号つき。スパイク 1 の取り込みと同じ）。ただし、その小節のどのコードにも `-` `=` が無いときは**等分**（`|[C][G]|` は半分ずつ）。コードが 1 つだけで `-` が無い小節は小節全体。
- 変換が書くとき: 各コードの長さを**十六分音符の格子に丸める**（コードの変わり目 = 解析器の時刻を、小節の中の十六分音符の位置に最も近いものへ）。長さ L 個なら `-` を L の半分（切り捨て）個、L が奇数なら最後に `=` を 1 つ。丸めて長さ 0 になったコードは前のコードに併合し、同じコードが続くときも併合する。小節の頭には必ずコードを置き（頭に `-` だけは書かない）、コード 1 つの小節も `-` を明示して書く（`[C]--------`）。コードの無い小節（無音など）は `N.C.` のコード名があるかを T0 で確かめて決める。低い確信度の `?` はコード名の中に入れたまま（`[Am?]`）。
- 数え方（決定 2026-10-18、ユーザー）: **スパイク 1 と同じく `-` `=` だけを数える**。コード名自体は長さを持たない（4/4 の 1 小節 = `-` 8 個。`[Dm]---[Am7]- --[Abm7]--` は 3+3+2）。例は `|[C]--------|[C]----[F]----|` の形で書く。
- **アプリはこの書き方をまだ知らない**。今は `-` `=` `|` も歌詞のテキストとして扱われる。次を T0 で直す（§8）:
  1. **小節の数え方**（`src/lib/autoScroll.ts` `lineBarCount`）: 今は「コード 1 つ = 1 小節」なので、例の 1 行は 4 小節のところを 5〜6 と数えてしまう。**ダッシュ行**（コード以外の文字が `|` `-` `=` と空白だけで、`|` を 1 つ以上含む行）は、`|` で区切った小節のうち中身のあるものの数（頭と終わりの `|` は数えない）。それ以外の行は今のまま（コード 1 つ = 1 小節、コードの無い歌詞の行 = 1 小節、空行・raw 行 = 0。`m6-plan.md` T4・確認したい点 3 の決定を変えない）。判定は `dashChart.ts` の `isDashLine`。
  2. **音節の扱い**（`syllables.ts` `chartSyllables`、`melodyLyrics.ts` の自動割り当て、`melodyChords.ts` の `chartChords` / `copyChordsFromChart`）: ダッシュ行の `-` `=` `|` は音節に数えない（後からそのセクションにメロディを足したときに「-」の歌詞が付かない）。ダッシュ行のコードは歌詞に結びつかないので、今の「コードだけの行 → null」と同じに扱い、**v1 ではメロディへ写さない**。小節と拍の位置でメロディの音に写すこと（ダッシュ行は拍の位置を持つので可能）は後で（§10）。
  3. **表示の確かめ**: `ChordLyricLine` と閲覧画面（コードが `-` の上に載る。比例フォントだとコード名が `-` 数個より広く重なるおそれ）、かんたん入力のステップ 1（歌詞。`lyricsText` / `applyLyrics` で、ダッシュ行を触らなければコードが保たれること）が壊れないか、Storybook と PC のブラウザで見る。必要ならダッシュ行だけ等幅にする（`isDashLine` で判定した印のクラス）。直しが要る範囲は T0 で決める。
  4. **検証**: 上の小節の長さの規則を `dashChart.ts` の `validateDashLine`（行ごとのエラーの一覧）で持つ。画面で手書きしたときの扱い（エラーを出すか、そのまま歌詞として表示か）は T0 で決める。ビューアは読むだけなので、エラーの行も表示は壊さない。
- **ユーザー向けの説明を書く**: 手書きの曲でもこの書き方を使えるので、書き方の説明（ヘルプ）を用意する。置き場所はアプリの中にヘルプがあるかを確かめて決める（無ければ S1・S3 のスケッチ D1 で決める）。内容は `docs/requirements.md` にも書く（T9）。

## 5. プライバシー

- **音は端末から出ない**。送信なし、Drive に上げない。解析は Worker の中だけ。
- 音のデータ・中間 JSON・候補は**保存しない**（localStorage・IndexedDB にも書かない）。画面を閉じたら消える。聞き比べの object URL は画面を閉じるときに `revokeObjectURL`。
- 曲として残るのは、ユーザーが「下書きを入れる / 曲を作る」を押したテキストだけ。新しい曲は「この端末だけ」の下書きとして作り（「サンプル曲を追加」と同じ `addLocalSong`）、**Drive に行くのはユーザーが保存したとき**だけ（今までの保存の流れ）。
- Worker の中の通信の道は消す（§2.3）。単体テストで、解析の関数と Worker の入口が通信の関数を呼ばないことを `noNetwork` のスタブで確かめる。e2e で、取り込みの間に余所への要求が 0 件であることを `page.route` で確かめる。
- エラーのメッセージやログに、曲の中身（音名・コード・テンポ）を出さない。
- リポジトリに**ユーザーの録音と市販の曲の音を入れない**。テストの音は合成だけ（§7）。
- 著作権の注意（メモ §7）: 自分のための耳コピの補助。画面の説明に「自分で使うため」と書くかは、スケッチのときに決める。

## 6. 速さ・メモリ・エラー・中止（PC の Chromium）

### 6.1 目標

| 項目                                   | コード（v1a）                                       | 鼻歌（v1b） | 根拠（スパイク）                                                     |
| -------------------------------------- | --------------------------------------------------- | ----------- | -------------------------------------------------------------------- |
| 5 分の曲の時間（読み込みから結果まで） | 40 秒以内                                           | 10 秒以内   | 16〜17 秒（CPU の取り合いで 27〜32 秒。ユーザーは了承）/ 4.5〜4.7 秒 |
| メモリ（解析の前からの増え方）         | 300 MB 以下                                         | 150 MB 以下 | +268 MB（5 分ステレオ 48 kHz）/ +131 MB                              |
| 画面                                   | 止まらない（Worker）。進み具合を出す                | 同じ        | 両方で確かめ済み                                                     |
| 長さの上限                             | 10 分（超えたら読み込まずにエラー）                 | 10 分       | 10 分超は未確認（持ち越し）                                          |
| JS の大きさ                            | Worker 合わせて gzip 60 KB 以下、最初の読み込みは 0 | 同じ        | 33 KB / 20 KB                                                        |

時間は進み具合と一緒に「5 分の曲で 30 秒ほど」と目安を出す。速くする（Worker の並列、WASM の FFT）は持ち越し。

### 6.2 エラー（日本語。スパイク 3 の決定「案 a」）

| 場合                                                      | 出し方                                                                                     |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| ブラウザが読めない形式・壊れたファイル                    | 「このファイルは読み込めませんでした。wav・mp3・m4a などの音声ファイルを選んでください。」 |
| 空・短すぎ（1 秒未満）・有限でない値・無音・拍が 2 つ未満 | 解析器の `AnalysisInputError` の `code` ごとのメッセージをそのまま出す（既にある）         |
| 長すぎ（10 分超）                                         | 読み込む前に長さを見て止める                                                               |
| 鼻歌で音が見つからない・少なすぎる                        | 「歌が見つかりませんでした。録音の音量と、歌い始めの位置を確かめてください。」             |
| Worker が落ちた・メモリ不足                               | 「解析できませんでした。ほかのタブを閉じてから、もう一度試してください。」                 |

- **形式**: wav と、ブラウザが読める形式（mp3・m4a など）を受ける。mp3 の始まりの遅れ（数十 ms）と、m4a のサンプルレートが読めずブラウザの変換を通ること（スパイク 3 の持ち越し）は、**下書きの用途では許す**（拍の位置が数十 ms ずれるだけ）。画面ではどの形式も同じに扱う。
- **中止**: 「中止」で `worker.terminate()`。すぐ止まりメモリも戻る。読み込み（`decodeAudioData`）の途中なら、終わった結果を捨てる。中止の後は受け取りの画面に戻り「中止しました」と出す。画面を離れたときも同じ。

- 未解決の項目はない。ダッシュ記法の数え方は、スパイク 1 と同じく `-` `=` だけを数える（コード名は長さを持たない。§3.6）。

以下は聞いたときの選択肢（記録）。

**Q1. v1 の順番**（決定: (a)）

- (a) コードの下書き（v1a）が先、鼻歌（v1b）が次。**おすすめ**: 解析器が成熟していて、出力が今のテキストにそのまま入る。共通の土台を先に作れる（§1）。
- (b) 鼻歌が先: 目的 2（不慣れな人）に直接効き、解析の JS が小さい。ただし聞き比べと候補の画面を土台と同時に作ることになる。
- (c) 両方を同時に: 一番長くかかり、確かめる時点が遅くなる。

**Q2. コードの下書きの行き先**（決定: (a)）

- (a) 新しい曲だけ。**おすすめ**: 既にある曲の歌詞にコードを合わせるには、音節の時刻（タップ補助など、優先 3）が要る。
- (b) 既にある曲にも、コードだけの行のセクションとして足す（歌詞の行とは別）。
- (c) 既にある曲の歌詞にも合わせて入れる（v1 では無理。後の機能）。

**Q3. コードだけの行の書き方**（決定: **ダッシュ記法**（下の (a)〜(c) ではない。§3.6））

- (a) 1 行 = 4 小節、1 小節に 1 つのコード（同じコードが続く小節も書く。例 `[C]　[C]　[G]　[G]`）。1 小節に 2 つ以上あれば全部書く。**おすすめ**: 自動スクロールの「コード 1 つ = 1 小節」の見積もり（`estimateChartBars`）とほぼ合い、小節の数が見て分かる（メモ §5.4 の 10）。
- (b) コードが変わる所だけ書く（短くなるが、自動スクロールの小節の数がずれる）。
- (c) 1 行 = 2 小節など、ほかの区切り。

**Q4. 候補（と中間 JSON）を残すか**（決定: (a)）

- (a) 確かめの画面の中だけ。テキストに入れた後は消える。**おすすめ**: テキストが唯一の元の決まりを守れる。保存するものが増えない（プライバシー）。作り直すときはもう一度解析すればよい。
- (b) この端末（localStorage）に、曲ごとに一定期間残し、後から候補を見直せるようにする。
- (c) 曲のテキストに、知らない行として候補を書き込む（Drive にも残る。テキストが読みにくくなる）。

**Q5. 鼻歌の下書きの印**（決定: (a)）

- (a) テキストには入れず、画面だけで示す（確かめの画面の見出し・説明・ボタンの名前）。**おすすめ**: 入れた後はユーザーのメロディとして普通に直す。alphaTex の中の印は読み取り専用のおそれがある。
- (b) 曲の先頭に `{comment: メロディ A は鼻歌の下書き 2026-10-18}` を足す（コードの下書きと同じ考え。消すのはユーザー）。

**Q6. 録り方（v1b）**（決定: まず (a)、後で (b)（§10））

- (a) ファイルだけ: DAW やスマホで、ヘッドホンでクリックを聞きながら録って書き出す。**おすすめ**: スパイク 4 と同じ条件で、精度の数字がそのまま当てはまる。
- (b) アプリの中でクリックを鳴らしながらマイクで録る画面も作る: 手軽だが、出力と入力の遅れの補正が未測定（スパイク 4 の T13）。先に小さな確かめが要る。

**Q7. 歌い始めの位置の受け取り方（v1b）**（決定: (a)）

- (a) 「歌い始めは何小節目の何拍目か」を選んでもらい（初めは「1 小節目の 1 拍目」）、秒は解析が最初の音から自動で見つける。**おすすめ**: 秒を書かなくてよい。弱起の曲も拍で指定できる（スパイク 4 の申し送り）。
- (b) 録音の中の 1 小節目の頭の秒を入れてもらう（正確だが、波形を見ないと分からない）。
- (c) 録音に入ったクリックの音から自動で見つける（ヘッドホンだと入らない。スピーカーだと声の検出を乱す）。

**Q8. 聞き比べの下書きの音**（決定: まず (a)、後で必要なら (b)（§10））

- (a) Web Audio の簡単な音（サイン波など）。**おすすめ**: 追加のダウンロードが無く、軽い。高さを聞き分けるには十分。
- (b) alphaTab の再生（音色のファイル、数 MB を読む）。ピアノなどの音で聞ける。

**Q9. 不慣れな人での試し（目的 2）**（決定: 基本は (b)。(a) は任意）

- (a) v1b ができたら、知り合いの 1〜2 人に使ってもらい、感想と直す時間を記録する（録音はリポジトリに入れない）。**おすすめ**: 目的 2 は未証明なので、一度は確かめたい。人を探すのはユーザー。
- (b) 試さず、ユーザー自身の使い心地で判断する。
