研究ブランチ `research/audio-analysis` の範囲（2026-10-11 ユーザー決定）のうち、優先 2 の「鼻歌 → メロディ」の**解析と精度の評価**に当たる（メモ §8.2 の旧「スパイク 2」の項目。スパイク 3 の決定 6 で番号をスパイク 4 にした）。

### 守ること（スパイク 2・3 から引き継ぐ）

- **AI を使わない**: スパイク 2 の計画の冒頭の表のとおり。学習済みモデル（CREPE、basic-pitch、SPICE、SwiftF0 など）は使わない。使うのは、決まった計算式の音の高さの追跡（YIN、pYIN の考え方、自己相関、ケプストラム）と、人が値を決めた HMM・ビタビ法（メモ §9 の確認したいこと 1 で「入れてよい」と決定済み）と、はっきり書ける規則（音符の区切り、拍への丸め）だけ。値の調整は**自分たちの合成音だけ**で行う（ユーザーの録音は見る時点を決めて確かめるだけ）。
- **プライバシー**: ユーザーの声の録音は個人のデータ。`recordings/`（git に入らない）の中だけに置き、git・Drive・Artifact・ログ・報告に、音そのもの、録音の図（波形・音の高さの線）、曲名、歌詞、調、**音符の並び**（並びから曲が分かるため）を書かない。名前は匿名（`hum-01-a` …）、数字は集計だけ。解析はブラウザの中だけで、音を送らない（通信をしないことをテストで確かめる）。最後に `py/privacy_check.py` を走らせる。
- **ホールドアウトと見る時点**: スパイク 2 と同じ。録音は取り込みの時点で（解析の前に）開発用かホールドアウトかを決めて記録する。開発用の録音を見るのは 3 回だけ（設計判断 7）、ホールドアウトは最後の 1 回だけ。見た時点は `out/results/heldout-log.jsonl` に残す。
- **解析は PC だけ**（スパイク 3 の G1 の決定）: 目標と計測は PC のブラウザ（Chromium）。Chromebook・タブレットは閲覧用なので測らない。
- **ブラウザだけで動く形**: スパイク 3 で TS を Worker で動かせると分かったので、鼻歌の解析は TS で作る（決定 3）。
- **ライセンス**: GPL・LGPL・AGPL は入れない（aubio・Essentia・Tony のコードは読まない・写さない）。論文の方法（YIN 2002、pYIN 2014、Tony の音符の HMM 2015）を自分で書くのは可。librosa（ISC）の `pyin` は Python の比べる相手としてだけ使う。依存を増やすなら MIT・BSD・ISC・0BSD・Apache-2.0 だけ（例: pitchy は 0BSD だが、使うかは T4 で決める。既定は自前）。
- **アプリの `src/` は変えない**: `.bandsheet` への変換、取り込みの画面、マイクの録音の画面はシステムの設計で、研究ブランチの範囲外。`src/lib/` は**読むだけ**（`render/` が今もしているように、`melody.ts` の `splitAtBars` などを呼んで「メロディの形にできるか」を確かめる）。
- **スパイク 3 の解析器は変えない**: `ts/dsp/` は凍結（使うのは `ts/dsp/core/` の FFT・変換・メモリの数えと `ts/browser/` の読み込み・Worker の仕組み。足すときは新しいファイルに）。`py/dsp/` も変えない。
- **ユーザーの方針（2026-10-17）**: 解析は入力の補助で、参考の情報を出すもの。精度は最優先ではない。1 つの答えより、**候補を出す**ほうがよい。

## 1. 目的とスコープ

### スパイク 4 が答えること

1. クリックを聞きながら歌った鼻歌の録音から、**音符（音の高さ・始まり・長さ）を拍の格子の上に**、メロディのモデル（`MelodyEvent`: 高さ、tick の長さ、休符）に直せる形で出せるか。
2. その精度は、合成の鼻歌（正解が完全に分かる）と、ユーザー自身の録音（開発用・ホールドアウト）でどれくらいか。どの種類の誤り（音の区切り、オクターブ、リズムの丸め）が残るか。
3. 「直す手数」（§4）が、キーボードで一から入れるより少なくなりそうか（メモ §4.4「鼻歌の取り込みは、キーボード入力より速くならないと意味が無い」）。
4. PC のブラウザで、待たずに（数秒で）終わるか。

### やらないこと

- `.bandsheet` への変換、取り込みの画面、マイクで録る画面（システムの設計）。スパイク 4 は「解析の JSON（秒の音符＋ tick に丸めた音符と候補）とその評価」まで。
- 歌詞（ユーザーが貼り、今のメロディ画面の自動割り当て `autoAssign` で並べる。声から言葉を聞き取るのは AI 無しではほぼ無理）。
- クリック無しの自由なテンポ（拍の推定から要る。持ち越し。決定 2）。
- 曲を聴きながら歌い直す使い方（メモ §4.5 の 2）、バンドの音からの歌メロ、和音。
- 連符・シャッフルの自動の判定（既定は 16 分の格子だけ。8 分の 3 連は切り替えとして合成で測るだけ。決定 5）。弱起・拍子の途中の変更（モデルに無い）。
- オクターブの書き方（男声を 1 オクターブ上に書くか）、音名の書き方（`C#4` か `Db4` か）。解析は鳴った高さの MIDI 番号を出し、書き方は変換の側（メモ §5.4 の 9）。

## 2. 流れと各段階の方法

流れ: 読み込み → モノラル・22050 Hz（スパイク 3 の自前の変換）→ 音の高さ（f0）と声の有無 → 音符への区切り → 1 音ごとの高さと候補 → 拍の格子（クリックのテンポと 1 小節目の頭から）→ tick への丸め → 結果の JSON（＋メロディのモデルにできるかの確かめ）。

| 段階                 | 方法（既定）                                                                                                                                                                                                                                                                                                                | 切り替え・候補（既定は切る）                                                                        | 主なリスク                                                                   |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 入力                 | ファイル（DAW や スマホから書き出した wav・ブラウザが読める形式）。`ts/browser/` の読み込み → 自前の変換（決定 1）                                                                                                                                                                                                          | マイク（`getUserMedia`）は持ち越し、または小さな確かめ（T13、決定 1 で選ぶ）                        | クリックが録音に漏れる（下の「クリックの漏れ」）                             |
| f0（音の高さ）       | **YIN**（差分関数を FFT で、累積平均で正規化、放物線で補間）。窓 1024（46 ms）・ずらし 256（11.6 ms）、範囲 65〜1050 Hz（C2〜C6）                                                                                                                                                                                           | **pYIN の考え方**: 閾値を何通りも使って候補を出し、半音の 1/5 刻みの状態＋「声なし」の HMM でつなぐ | オクターブの誤り（低い男声、息の多い声、基音の弱い声）                       |
| 声の有無             | pYIN の「声あり」の確からしさ ＋ 音の大きさ（その録音の静かな所から雑音の高さを測り、それより一定以上大きい所。録音ごとの合わせ込み ①）                                                                                                                                                                                     | —                                                                                                   | 息・子音（「た」の t）・部屋の響きの尾                                       |
| 音符への区切り       | 規則: ①声のある区間ごとに分ける、②区間の中で、中央値でならした高さが半音の約 6 割以上動き、それが一定時間（約 60 ms）続いたら別の音、③高さの移り（しゃくり・ポルタメント）の間のフレームは高さに数えない、④短すぎる音（16 分の半分未満）は隣にまとめる、⑤同じ高さの続き（「らら」）は音の大きさのくぼみ・立ち上がりで区切る | Tony の考え方の**音符の HMM**（各半音に「立ち上がり・安定・終わり」の状態。値は人が決める）         | 口を閉じた「ん〜」で同じ高さが続くと区切れない。ビブラートで音を割ってしまう |
| 1 音の高さと候補     | 安定した部分（前後の 2〜3 割を除く）の中央値（cents）。録音全体の**ずれ（チューニング）**を引いてから一番近い半音に。半音の境目（±50 cents）に近い音は、次の候補（隣の半音）を確からしさつきで出す                                                                                                                          | 調を渡されたとき、境目に近い音だけ**候補の順番**を調の音に寄せる（決めつけない。決定 6）            | 歌っているうちに高さが少しずつずれる（ずれを区間ごとに測る案は切り替え）     |
| オクターブの直し     | 前後の音から 12 半音離れた短い音を、前後に近いオクターブに直す（規則）。直したことを候補に残す                                                                                                                                                                                                                              | —                                                                                                   | 本当にオクターブ跳ぶメロディを直してしまう                                   |
| 拍の格子             | **クリックあり**（決定 2）: テンポ（bpm）・拍子・1 小節目の頭の秒は、ユーザーが知っている値を渡す（スパイク 2 の録音の `.txt` と同じ。正解からは取らない）。拍の推定はしない                                                                                                                                                | 録音の中のクリックの漏れから頭を合わせる（`カウント:` と同じ考え）                                  | 頭の秒がずれると全部が少しずれる                                             |
| 丸め（クオンタイズ） | 拍の時刻を基準に「何拍目の何割か」にしてから **16 分の格子**へ（メモ §5.4 の 1）。その録音で歌が拍より早い・遅い癖（始まりのずれの中央値）を先に引く（①）。音の終わりは、次の音の始まりまでの隙間が 8 分の半分より短ければつなぐ（レガート）、長ければ休符。小節をまたぐ音はモデルのとおり 1 つ（書くときのタイは変換の側） | 8 分の 3 連の格子（拍ごとに誤差の小さい方。メモ §5.4 の 2）。丸めの候補（2 番目に近い格子）も出す   | 16 分 1 つのずれが多い（人のリズムの揺れ）。付点と「8 分＋休符」の取り違え   |
| 結果                 | JSON: 秒の音符 `{start, end, midi, cents, confidence, candidates}`（今の `AnalysisNote` を広げる）＋ tick の音符 `{startTick, ticks, midi, candidates}` ＋休符。メロディのモデルの `MelodyEvent[]` にして `splitAtBars` と `serializeMelody` が通ることを確かめる（`src/lib` を読むだけ）                                   | —                                                                                                   | —                                                                            |

**クリックの漏れ**: ヘッドホンでクリックを聞けば録音に入らない（推奨）。スピーカーで鳴らすと、クリックの音が「声あり」や音の始まりに混じる。合成の変化形にクリックの漏れを入れて測る（§4）。

**声の範囲**: 範囲 C2〜C6 で、低い男声の鼻歌（G2〜G4 あたり）と女声を両方含む。メロディ画面の入力の範囲（C3〜C7）より下が出ることがあるが、解析は鳴った高さのまま出す（書き方は変換の側）。

## 3. ユーザーの判断

### 決定（2026-10-18、ユーザー）

- 1〜7 はすべて推奨どおり（ファイルだけ・クリック必須・TS で直接・録音 6 本・16 分の格子・調に寄せない・目標は G1 で決める）。

### G1 の決定（2026-10-18、ユーザー）

- 続ける。目標を引き上げる: 合成の音符 F（始まり）H0 ≥ .98、H1 ≥ .95、H2 ≥ .90、H3 ≥ .75。直す手数（キーボードの手数に対する割合）H2 ≤ .15、H3 ≤ .5。
- 調整の優先: H3 の同じ高さの続きの区切り（「ん〜」）と、丸めの始まり・長さ。オクターブと高さは後回し。
- 録音はユーザーが録り終え、メロディの正解を書いている（届きしだい R1）。
- 記録: T7 の動作確認で、合成のホールドアウト 1 本（`syn-h0-saints-s7`）をガードを入れる前に一度だけ解析した。音符の数と時間だけを見て、保存・採点はしていない。ホールドアウトとして使い続ける。

### 決めてほしいこと（当時の案）

1. **入力: ファイルか、マイクか**。→ **推奨: スパイク 4 はファイルだけ**。DAW（Cakewalk Sonar）やスマホで、クリックを聞きながら録って書き出す。何度でも同じ音で比べられ、録音の取り込み・匿名化・見る時点の決まり（スパイク 2）がそのまま使える。マイクで録る画面はシステムの設計で、一番の難しさは「鳴らしたクリックと録った声のずれ（出力と入力の遅れ）の補正」。これを先に知りたいなら、T13（ブラウザでクリックを鳴らしながら録り、遅れを測るだけ。音は保存しない・送らない）を足す。
2. **クリック（メトロノーム）**。→ **推奨: クリックありを必須にする**（ヘッドホンで聞き、録音には入れない。テンポ・拍子・1 小節目の頭の秒を `.txt` に書く。1 小節目の前に 1 小節のカウントを聞いてから歌い始める）。拍の位置が最初から分かり、精度が大きく上がる（メモ §9 の確認したいこと 7）。クリック無しは持ち越し。
3. **Python で先に試すか、TS で直接作るか**。→ **推奨: TS で直接作る**。理由: ①スパイク 3 で FFT・変換・wav の読み込み・Worker・計測ページ・通信しないテストが TS にそろった、②YIN と規則の区切りは数百行で、移す相手を持つより 1 回で書くほうが安い（スパイク 3 は移植だけで 1 スパイクかかった）、③Python と同じ結果にする比べ（一致の決まり）が要らない、④メモ §2.2 も「鼻歌は最初からブラウザで」。Python は**比べる相手と道具だけ**: librosa の `pyin` との f0 の比べ（T4、開発用の合成だけ）、mir_eval との採点の確かめ（T2）、図（`py/tools/`、合成だけ）。
4. **録音: どの曲を・何本・どう歌うか**。→ **推奨: 6 本（開発用 4、ホールドアウト 2）**。各 8〜16 小節・30〜60 秒、4/4、ユーザーが楽譜を知っていて band-sheets のメロディ画面で書ける曲。歌い方: (a) 「ら」「た」など 1 音ごとに区切って中くらいのテンポ、(b) (a) と同じ曲を口を閉じた「ん〜」で、(c) ゆっくり（70〜90 BPM）で長い音が多い曲、(d) 速め・16 分やシンコペーションのある曲、(e)(f) 別の曲（どちらかはスマホで録る）。どれがホールドアウトかは取り込みの時点で曲ごとに自動で決める（スパイク 2 と同じ: 曲の番号が偶数ならホールドアウト。同じ曲の (a)(b) は同じ側）。**正解はユーザーが解析の前に**メロディ画面で書いたメロディ（パートのテキストを `.txt` に貼る）。歌い直したくなったら、解析を走らせる前なら何度でも可。
5. **リズムの範囲**。→ **推奨: まず 16 分の格子だけ**（全〜16 分、付点、休符、小節をまたぐ音）。連符・シャッフルは既定で出さない。8 分の 3 連は切り替えとして合成で測るだけ（録音の正解に 3 連が無ければ既定に入れない）。
6. **調に寄せるか**。→ **推奨: 寄せない（既定は切る）**。調（ユーザーが曲の情報に書いた `{key}` を渡す）は、半音の境目に近い音の**候補の順番**にだけ使う切り替えにして、合成で効果を測る。決めつけると、調の外の音（経過音・借用）を消してしまう。
7. **目標の決め方**。→ **推奨: §5 の値は仮。T8 の基準線（合成）を見てから G1 で確定する**（スパイク 2 と同じ）。精度は最優先ではないので、録音の目標は「記録」寄りにし、続けるかの判断は「直す手数」（§4）で見る。

## 4. 評価

### 合成の鼻歌（正解が完全に分かる）

band-sheets のメロディ（`MelodyEvent[]`）から、**声に似た音**を自分で合成する（alphaTab の音色ではなく、高さの線を細かく作るため。T1）。

- 音: 声帯の振動に似た倍音（高い倍音ほど弱く）＋母音の山（「あ」「う」「ん」）。高さの線は正解の音符から作り、次を種で固定して足す: しゃくり（始まりが 50〜100 cents 低い）、音の間の移り（30〜120 ms）、長い音のビブラート（5〜6 Hz、±20〜60 cents）、1 音ごとの高さのずれ（σ 15〜40 cents）と録音全体のずれ、始まりのずれ（σ 20〜60 ms と、全体に遅れる癖）、音の終わりの早さ（レガート・切る）、息の音（フレーズの間）、雑音（30・20 dB）、部屋の響き、クリックの漏れ、基音の弱い声（オクターブの誤りの試験）。
- レベル: **H0**（サイン波に近い、高さと時刻が正確）、**H1**（声に似た音＋ビブラート・移り・しゃくり）、**H2**（H1 ＋高さのずれ・時刻の揺れ・雑音 30 dB）、**H3**（H2 ＋口を閉じた「ん〜」で同じ高さの続き・基音が弱い・雑音 20 dB・響き・クリックの漏れ）。
- メロディ: 「聖者の行進」、「きらきら星」（どちらもトラディショナル）、練習曲のメロディ（`render/etude.ts`）、新しい**鼻歌用の作り物のメロディ**（種で固定。8 分・16 分・付点・休符・小節をまたぐ音・同じ高さの続き・オクターブの跳び。低い声用と高い声用の範囲）。
- 分け方: **調整用**（種 1〜3）・**開発用**（種 4〜5、調整には使わないが見てよい）・**ホールドアウト**（種 6〜7 と、合成の種も別。`heldOut: true`、最後の 1 回だけ）。
- 正解は 2 つ: ①**歌った時刻**（揺れを足した後の秒。f0・区切りの採点用）、②**楽譜の時刻**（tick。丸めの採点用）。合成なのでフレームごとの f0 の正解もある。

### ユーザーの録音

- 決定 4 の 6 本。取り込みはスパイク 2 の `intake.py` と同じ考えで、新しい `py/hum_intake.py`（T3）が匿名の名前（`hum-NN-x`）、ホールドアウトの記録（解析の前）、モノ 44.1 kHz への変換、正解の JSON を作る。正解・対応表は `recordings/`（git に入らない）だけ。
- 正解は「ユーザーが歌うつもりのメロディ」で、歌った時刻は分からない。そのため録音の採点は、楽譜の時刻（tick）を、テンポと 1 小節目の頭から秒にしたものと比べる（始まりの許す幅は合成より広い版も出す）。

### 指標（自前で書く。T2 で mir_eval と同じ値になることを確かめる）

| 指標                           | 中身                                                                                                                                                                                | 使う正解      |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| 音符 F（始まり・高さ）         | mir_eval の `transcription` と同じ定義: 始まり ±50 ms、高さ ±50 cents、1 対 1 の対応。適合率・再現率も                                                                              | 歌った時刻    |
| 音符 F（始まり・終わり・高さ） | 上に終わり（±max(50 ms, 長さの 20 %)）を足す                                                                                                                                        | 歌った時刻    |
| ゆるい版                       | ①高さを音名だけ（オクターブ無視）、②高さ ±1 半音、③始まり ±100 ms（録音用）                                                                                                         | 同上          |
| f0（合成だけ）                 | フレームごとの高さの正解率（±50 cents）、音名の正解率、声ありの再現率・誤検出率、オクターブの誤りの割合                                                                             | フレームの f0 |
| 丸めた音符の正解率             | 正解の音符の並びと出力の並びを対応づけ（編集距離）、始まりの tick・長さ・高さがすべて同じ音の割合。始まりだけ・高さだけの割合も                                                     | 楽譜の時刻    |
| **直す手数**                   | 正解に直すのに要る最小の操作（高さを変える、長さを変える、足す、消す、2 つに分ける・まとめる）の数 ÷ 正解の音の数。キーボードで一から入れる手数（音の数 ＋ 長さの切り替え）と比べる | 楽譜の時刻    |
| 候補の当たり                   | 高さ・丸めの 2 番目までの候補に正解が入る割合（候補を出す価値の目安）                                                                                                               | 両方          |

正解の音が 16 分より短いもの（合成の装飾）は、今の `score.py` の `_melody` と同じく数えない。

## 6. 主な設計判断

1. **置き場所**: TS は `spikes/analysis/ts/hum/`（`f0.ts`・`pyin.ts`・`notes.ts`・`quantize.ts`・`toMelody.ts`・`analyze.ts`・`config.ts`・`score.ts`・`cli.ts`、各 +test）。合成は `render/hum/`（`melodies.ts`・`contour.ts`・`voice.ts`・`variants.ts`・`truth.ts`・`cli.ts`）。Python は `py/hum_intake.py` と `py/tools/` の新しいファイルだけ。`ts/dsp/`・`py/dsp/`・`src/` は変えない（`src/lib` は読むだけ）。
2. **設定**: `ts/hum/config.ts` に全部の値（窓、範囲、閾値、区切りの規則の値、格子、切り替え）と、その JSON の SHA-256 のハッシュ。結果の JSON に設定のハッシュとコミットを入れる。**基準線の設定**（T8）はコミットで固定し、後で変えない（見る時点 ① の比べる相手）。
3. **結果の JSON**: `render/types.ts` の `AnalysisResult` の `melody` を広げる（新しい欄はすべて任意: `cents`・`candidates`・`quantized: {bpm, ts, startSec, events}`）。既存の読み手（`score.py`）が壊れないことをテストで守る。
4. **正解を読まない**: `analyze` が受け取るのは音（または y）と「ユーザーが知っている情報」（テンポ・拍子・1 小節目の頭の秒・任意で調）だけ。合成の正解・録音の正解は採点だけが読む（構造とテストで守る）。
5. **合成は TS で、劣化は既存の道具で**: 声に似た音は `render/hum/` で作る（`MelodyEvent` から直接、正解も同じ所から）。雑音・響きは、`py/degrade.py` がそのまま使えれば使い（T1 で確かめる）、使えなければ `render/hum/` の中に簡単なものを書く。
6. **候補の形**: 1 音ごとに高さの候補（最大 3、確からしさつき）、丸めの候補（最大 2）。確からしさは「一番目と二番目の差」から出す（スパイク 2 のコードの候補と同じ考え）。
7. **見る時点（録音）**: ①基準線（T8 の設定。録音が届いたらいつ走らせてもよい。設定が固定なので偏らない）、②合成での調整（T9・T10）の後の設定、③ホールドアウトと同じ最後の 1 回（T11）。②で直すなら、合成で判断できる変更を 1 回まで（スパイク 2 の設計判断 7 と同じ）。

- R2: 合成の誤りの種類が、自分の録音と似ているか（似ていなければ合成を直す）。
- 最後: 直す手数がキーボードより少ないか。候補（2 番目の高さ・丸め）が役に立ちそうか。続けるなら、マイクの画面・変換（オクターブ・音名の書き方）でシステムの設計に申し送ること。

## 10. リスク

| リスク                                                               | 対策                                                                                                                                       |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **同じ高さの続き・口を閉じた鼻歌で音を区切れない**（いちばん大きい） | 歌い方 (a)「ら」「た」を推奨し、(b)「ん〜」は難しい方として分けて測る。音の大きさのくぼみの規則、音符の HMM（T10）。「分ける」を候補で出す |
| 人のリズムの揺れで、16 分 1 つの丸めの誤りが多い                     | 始まりの癖を録音ごとに引く。丸めの候補を出す。指標を「始まりだけ」「高さだけ」に分けて、直す手数で判断する                                 |
| オクターブの誤り（低い男声・息の多い声）                             | pYIN の HMM、オクターブの直しの規則、基音の弱い合成（H3）で測る。直したことを候補に残す                                                    |
| 合成の声がきれいすぎて、録音の難しさを再現しない                     | R2 で誤りの種類を比べ、似ていなければ T1 に変化を足す（スパイク 2 の LR と同じ）                                                           |
| 録音に合わせてしまう（6 本と少ない、1 人の声）                       | 見る時点を 3 回に決める。調整は合成だけ（T9）。ホールドアウトは 1 回                                                                       |
| 正解（書いた楽譜）と実際に歌ったものが違う                           | 解析の前に、ユーザーが自分の録音を聞いて正解を直してよい。解析の後に正解を直すのは、見る時点の記録つきでユーザーと決めた時だけ             |
| **録音の音符の並び・声が外に出る**                                   | 並びは曲を特定できるので集計だけ。図・音は `out/` の中だけ。`privacy_check` に鼻歌の正解の並びを足す（T3）。T14 で確かめる                 |
| 鼻歌がキーボードより遅く、機能の価値が無い                           | 直す手数をはじめから指標にする。結果がそうなら「続けない」も結論として記録する                                                             |
| クリックの漏れ、録音の頭の秒のずれ                                   | ヘッドホンを推奨。合成にクリックの漏れを入れる（H3）。頭の秒は DAW の書き出しの位置で決める（`RECORDING.md`）                              |
| ライセンスの混入（Tony・aubio の考え方の写し）                       | 論文だけを読む。依存は増やさない（pitchy を使うなら 0BSD の表示）。T14 で確かめる                                                          |
