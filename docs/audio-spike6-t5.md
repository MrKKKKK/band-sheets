# スパイク 6 T5: B-1（コードの区間ごとのベースの音）

読む人: ユーザー（G1 で合成の結果を見る人）と、T6（分数の印）・T8（基準線）・T9（調整）の担当。
目的: B-1 の 4 つの方法（計画 §2 の ①〜④）を調整用の合成で比べた表と、採った方法・設定・開発用の確認・T6 への申し送りを 1 か所にまとめる。

## 評価の方法

- 実行: `ts/bass/segment_eval.ts`（`spikes/analysis` で `npx tsx ts/bass/segment_eval.ts [--split dev --dev-look "<理由>"]`）。比べたときのコミット `41ee6fc`（4 つの方法がある版）、採った形は `80d3fc8`（方法 ② だけ）。設定 `bass-v0` ハッシュ `5170bd9d0922`。
- 合成: `out/bass/`（T2）。調整用 = 音色 A・種 1〜3 の 72 本（B0〜B3 各 18 本、51.1 分）。値を選んだのは調整用だけ。
- 区間は 2 通り: **正解の区間**（正解のコードの区間と正解の拍。上限）と、**v1a の区間**（`ts/dsp/analyze` が出した区間と拍。`out/bass-eval/v1a/` に置いて使い回す）。
- 採点: `ts/bass/score.ts` の `scoreBass` の `segBass.rate`（1 拍 2 点）。B-1 の音名がルートと違えば `/X` として結果のコードに書き、同じなら書かない。「v1a のルートだけ」の行は、ベースの段階が無いときの値（比べる基準）。
- 取り違えの表は正解の区間で、区間ごとに「出した音名 − 正解の音名」（半音）を数えた。オクターブは、音名が当たった区間のうち MIDI が正解の `played` と同じ割合。
- ホールドアウト（音色 C・種 6〜7）は開かない。`heldout_guard.ts` が、ホールドアウト・音色 C・確かめられないもの（manifest が読めない、manifest に無い名前、登録の無い録音）を wav を開く前に断る。

## 方法（計画 §2 B-1）

共通: 低い CQT（`lowCqt.ts`、凍結の `ts/dsp/core/cqt.ts` を呼ぶだけ）を C1 から 5 オクターブ・半音ごと（3 本のうち最大）にする。ベースの候補は C1〜B3、その上は倍音として読むだけ。区間の頭の 1 拍の重み `headWeight`。確信度は 12 の音名の点の (1 位 − 2 位) / 1 位、2 位を候補として返す。

| 方法 | 中身                                                                                                                 |
| ---- | -------------------------------------------------------------------------------------------------------------------- |
| ①    | 今のベースのクロマと同じ形（C1〜B3 を 12 の音名にたたむ）を、頭に重みをつけて平均                                    |
| ②    | 倍音の和（候補の音の 1〜4 倍音の和）を頭に重みをつけて平均し、音名の点 = その音名のオクターブの中の最大。MIDI も出す |
| ③    | ② と同じだが、低い帯域の音の始まりから 0.15 秒だけ重み 1（ほかは 0.1）                                               |
| ④    | 拍ごとの倍音の和を HMM（ビタビ）でつなぐ。留まる 0.8、半音・全音・オクターブの動きを 3 倍通りやすく。区間は拍の票    |

④ は最初の形（出力の確からしさ = 倍音の和の比そのまま）で B0 .592 だった。音とその 5 度の倍音の和が近く、留まる方が安くなるため。比を 8 乗して B0 .997 にした（値は調整用の B0 で 4 / 8 / 16 を見て 8）。

## 終わりの条件

- **B0 で区間のベース ≥ .97（正解の区間）: 満たす**（調整用 1.000、開発用は下）。
- 単体テスト（`segmentBass.test.ts`、合成の音）: 2 倍音が基音より 18 dB 強い E1 → E1（オクターブ）、3 倍音が 12 dB 強い C2 → C（5 度）、基音の無い A1（2〜5 倍音だけ）→ A1、左手の 1-5-8 の分散和音 C2 G2 C3 G2 → C、ピアノの左手が C2 ＋ C の和音でベースが E1 → E（2 位が C）、ウォーキング C E F F# → C、無音 → 確信度 0。

## 開発用の確認（1 回、値を選ぶのには使っていない）

`heldout-log.jsonl` の 1 行目（`bass-synth-dev`、コミット `26dc6e4`、設定 `5170bd9d0922`、96 本 = 音色 A・B、種 4〜5、67.2 分）。T5 で開発用を見たのはこの 1 回だけ。見た後で値は変えていない。

| 区間             | B0   | B1   | B2   | B3   | 全体 |
| ---------------- | ---- | ---- | ---- | ---- | ---- |
| 正解             | .995 | .983 | .988 | .970 | .984 |

- 取り違え（2272 区間で 36）: 5:13・8:13・7:4・2:3・3:2・1:1。調整用に無かった「5」（正解の 5 度下を出す = 下の音の 3 倍音が正解の音に重なる、倍音の和の下への誤り）が出た。オクターブも B3 で .840 に下がった（調整用 .939）。音色 A と B を分けて集計しなかったので、どちらの音色かは分からない（次に開発用を見るときは音色ごとに分ける）。

## 速さ

Node・1 スレッド、調整用 51.1 分: 低い CQT（チューニングの推定を含む）が 1 分の音あたり約 0.5〜0.6 秒、B-1 の残りは 1 分あたり 1 ms ほど。5 分の曲で約 3 秒で、§5 の「v1a に足した分 +3 秒以内」のほぼ全部を使う（ブラウザの計測は T12）。

## T6 への申し送り

- 正解の区間なら ② はほぼ上限（全体 .986）。v1a の区間では .894 で、差の大部分は v1a の区間（境目・ルート）による。B0 はベースだけの音なので v1a のコードの区間そのものが弱い（ルートだけ .865）。クリシェは上の和音が変わらないと v1a が区間を 1 つにまとめるので、B-3（T10）の分を含む。
- ② の残りの誤りは「8」（正解 − 4 半音を出す。例: 正解 `/E` に C を出す）が最多で、ピアノの左手がルートを弾き、ベースだけが `/X` を弾く曲（`pianoRoot`）によるものと見られる（曲ごとには確かめていない）。単体テストではこのとき 2 位がルートになる（合成での割合は未測定）。T6 で「1 位がルートでない・確信度が低い・2 位がルート」の扱い（`/X` を出さない）を決める材料になる。
- 次に多いのは「1」「2」「3」（半音・全音・短 3 度上）で、B3（スマホの低音の弱り・雑音 20 dB）に集まる。開発用では「5」（5 度下への誤り）とオクターブの誤りが増えた（上の節）。T9 で倍音の重み（今はどれも 1）を見る候補。
- 確信度（`confidence`）と 2 位（`second`）は返しているが、しきい値はまだ見ていない（T6 の `slash.minConfidence`）。
- `segmentBass` は区間と拍を受けるだけで正解を読まない。結果の JSON・`analyze` へのつなぎは T7。
- 開発用の合成を見るときは `--dev-look` が `out/results/heldout-log.jsonl` に 1 行足す（`input: "bass-synth-dev"`）。devcontainer のワークツリーでは git がコミットを読めないので `-e BAND_SHEETS_COMMIT=<sha>` を渡す。
