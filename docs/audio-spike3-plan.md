### 守ること（スパイク 2 から引き継ぐ）

- **AI を使わない**: スパイク 2 の計画の冒頭の表のとおり。移すのは今の決まった計算式・HMM・理論の表だけ。学習済みモデル（Essentia の TF モデル、basic-pitch など）は使わない。移植のついでに新しい手法を足さない。
- **ライセンス**: 公開の Web アプリに入る前提で、**GPL・LGPL・AGPL は入れない**（Essentia.js は AGPL、aubio は GPL、Chordino は GPL なので、コードも移さない）。librosa（ISC）・NumPy・SciPy（BSD）の処理を書き直すのは可。ただし librosa の書き方をなぞった部分には ISC の著作権表示を残す（`spikes/analysis/ts/THIRD_PARTY.md`）。soxr・libsndfile（LGPL）は今までどおりローカルの Python だけ。
- **プライバシー**: ユーザーの音声はブラウザの外に出さない（送信なし、解析は端末の中だけ）。録音の曲名・コード・調・歌詞は git に入るファイルに書かない（`py/privacy_check.py` を最後に走らせる）。
- **Python の解析器は凍結**: スパイク 3 の間、`py/dsp/` と `py/dsp/tables/` は変えない（比べる相手が動かないように）。Python 側に足すのは中間値を書き出す道具（`py/tools/`）だけ。移植の途中で Python のバグが見つかったら、記録して、直すかどうかはユーザーと決める。
- **アプリの `src/` は変えない**: アプリへの組み込み（画面、`.bandsheet` への変換、どこから呼ぶか）はシステムの設計で、研究ブランチの範囲外。TS のコードは `spikes/analysis/ts/` に置く。
- **ホールドアウト**: 移植の確かめは「Python と同じ答えが出るか」で、精度の調整ではない。それでも、ホールドアウトの変化形と録音は使わない（決定 5）。

## 1. 目的とスコープ

### スパイク 3 が答えること

1. 今の解析器（スパイク 2 の既定の設定）を TS に移したとき、**Python と同じ結果**（§4 の許す差の中）が出るか。
2. それが **Chromebook（ユーザーが見るのに使う端末）と PC のブラウザ**で、待てる時間・メモリで動くか。
3. 移すのに**どの部分が難しいか**、ライブラリを使うか自分で書くか。続けるなら残りの手間はどれくらいか。

### やらないこと

- アプリ（`src/`）への組み込み、取り込みの画面、`.bandsheet` への変換、CLI をやめる判断（結果を見てシステムの設計で決める）。
- 精度の改善・設定の調整（スパイク 2 の持ち越しはそのまま残す）。
- 既定で切っている切り替えの移植（`chroma.kind: 'cens'`、`beats.method: 'plp'`、`smoothing: 'median'/'none'`、`harmonics`、`bass_root`・`slash`、`top_voice_discount`、`seventh_mode: 'segment'`、`power`、`vocab: 'v1'`、`key.track: 'global'` の後押し、`keyest` の KK 以外の使い道）。TS は**既定の道筋だけ**を持ち、既定と違う設定はエラーにする。
- 鼻歌（スパイク 4）、マイク入力、ドラム、歌メロ。
- 採点（`score.py`・`report.py`）の移植。TS の結果の JSON を Python の採点にそのまま通す。

## 3. ユーザーの判断

### 決めてほしいこと

1. **範囲**: (a) 全部を移す、(b) まず縦の一本（読み込み → HPSS・打撃 → 拍 → クロマ → コード 1 回目 → 結果）を移して、Python との一致と速さを見てから残りを決める。→ **推奨: (b)**。数値で難しい所（HPSS・拍・CQT）はすべてこの一本に入っていて、残り（小節の頭・セクション・調・後押し）は numpy だけの規則で、同じ入力なら同じ答えにしやすい。一本の後に関門 G1 を置く（§6）。
2. **速さとメモリの目標**: §2 の「制約と目標」の値（Chromebook 5 分の曲 60 秒、PC 20 秒、ピーク 300 MB）。→ **推奨: この値で始め、G1 の PC の計測を見て見直す**。取り込みは 1 曲に 1 回なので、進み具合が見えれば 1 分は待てると考えた。
3. **Chromebook での計測の方法**: 研究ブランチは GitHub Pages に出ない。(i) 計測ページを Claude の Artifact（非公開）にして Chromebook で開く、(ii) PC の開発サーバーに家の LAN から入る（WSL2 なので設定が要る）。→ **推奨: (i)**。音は合成音（ページに入れた 1 分の合成音をつなげて 1・3・5 分）。手元のファイルを選んで測ることもできるが、ファイルはページの中だけで使い、送らない。あわせて **Chromebook の機種名（CPU・メモリ）を教えてほしい**。
4. **ライブラリか自前か**: → **推奨: FFT だけライブラリ（`fft.js`、MIT、依存なし、版を固定）、ほかは全部自前**。librosa に当たる JS のライブラリは無く、あっても挙動を合わせられない。WASM（Rust など）は、G2 で速さが足りないときだけ考える（ツールが増えるため）。
5. **録音とホールドアウトを使うか**: → **推奨: 使わない**。一致は「同じ入力で Python と TS の答えが同じか」で決まり、合成音（L0〜L3・LR・M・転調の変化形）で雑音・部屋の響き・弾き方まで含められる。速さも合成音で測れる。録音を使うと匿名化と見る時点の決まりが要るのに、分かることが増えない。どうしても「本物の音での差」を見たいときは、最後に開発用の録音で **Python と TS の一致率だけ**（正解は見ない、集計だけ）を 1 回、をユーザーと決める。
6. **番号**: 鼻歌をスパイク 4 にする（メモ §8.2・`CLAUDE.md` を T20 で書き換える）。→ **推奨: そうする**。

## 4. 「正しく移せた」の決め方

**比べる相手**: `f087ca3` の Python、既定の設定（設定のハッシュ `adec583eb3c6`、T1 で確かめる）。

**入力**: 合成音の調整用の変化形（L0〜L3・LR・M・転調・CH の調整用）。ホールドアウトと録音は使わない（決定 5）。CH は非公開の譜から作るので、`out/` の中だけで扱い、git に入るファイルには曲ごとの値を書かない（集計だけ）。

**2 段構え**:

1. **段階ごと（入力を差し込む）**: Python が段階ごとの中間値を書き出す（T1）。TS の各段階は、**前の段階の Python の値**を入力にして比べる。誤差が次の段階に積もらないので、どこがずれたか分かる。
2. **通し**: TS だけで wav から結果の JSON まで作り、Python の結果と比べ、さらに `score.py` で両方を採点して点数を比べる。

**変換（リサンプル）を外す**: 段階ごと・通しとも、Python の `librosa.load` の後の 22050 Hz の信号（float32）をそのまま TS に渡す。ブラウザの読み込みと自前の変換の差は、別に「読み込みを含む通し」（T15）で測る。

| 段階                                  | 合わせ方                                                            | 許す差（仮。T2 で見直す）                                                     |
| ------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| STFT・逆 STFT                         | 数値                                                                | 相対誤差 1e-5 以下                                                            |
| HPSS（`y_harm`・`y_perc`）            | 数値                                                                | 信号対誤差比 60 dB 以上                                                       |
| 打撃の強さ                            | 数値                                                                | 相関 .9999 以上、最大の相対誤差 1e-3                                          |
| 拍                                    | 拍の数が同じ、時刻                                                  | 同じ数・すべて ±1 ms（Python の打撃の強さを入れたとき）。通しで ±5 ms が 99 % |
| フレームのクロマ・拍のクロマ          | 列ごとの余弦、大きさ                                                | 余弦 .995 以上が 99 % の列、列の和の比 ±3 %                                   |
| コード（Python のクロマを入れたとき） | 列ごとのコード、事後確率                                            | **完全に一致**、事後確率の差 1e-9                                             |
| 小節の頭・セクション・調・後押し      | Python の入力を入れたとき                                           | **完全に一致**                                                                |
| 通し: 結果の JSON                     | 拍・コードの帯・小節の頭の位相・セクションの境目・小節ごとの調・`?` | 下の表                                                                        |

通しの点数（Python との差、合成の変化形ごと）:

| 指標                                    | 一致させるもの                         | 許す差                                                |
| --------------------------------------- | -------------------------------------- | ----------------------------------------------------- |
| 拍 F・小節の頭 F                        | 必須                                   | 変化形ごとに ±.01、小節の頭の位相はすべて同じ         |
| コード / 拍（2 点の採点）・語彙のコード | 必須                                   | 変化形ごとに ±.02、全体の平均 ±.005                   |
| 調 / 小節                               | 必須                                   | 変化形ごとに ±.03                                     |
| セクション F                            | 記録（閾値の近くで出入りしやすいため） | 全体の平均 ±.05                                       |
| `?` の印                                | 記録                                   | 一致 95 % 以上。違う所は事後確率が 0.93 ±.02 の中だけ |

どれかが許す差を超えたら、段階ごとの比べで原因を見つけて直す。直せない差（例: CQT の間引きのフィルタ）は、「その差で点がどれだけ動くか」を記録して G1 でユーザーと決める。

## 5. 主な設計判断

1. **置き場所**: `spikes/analysis/ts/`。`ts/dsp/*.ts` は `py/dsp/*.py` と同じ名前（`audio.ts`・`beats.ts`・`chroma.ts`…）。数値の部品は `ts/dsp/core/`（`fft.ts`・`stft.ts`・`median.ts`・`resample.ts`・`cqt.ts`・`mel.ts`）。ブラウザの部分（読み込み・Worker・計測ページ）は `ts/browser/`。テストは同じ場所の `*.test.ts`（`vitest.config.ts` の `include` に `ts/**` を足す）。`src/` からは読まない。
2. **リサンプル**: 自前の窓つき sinc（ブラウザごとの違いをなくす）。`OfflineAudioContext` での変換とは T8 で比べ、差を記録する。
3. **表**: `py/dsp/tables/*.toml` が唯一の元。Python の道具が `ts/tables/*.json` を作り（コミットする）、テストで TOML から作り直した JSON と同じか確かめる。アプリに TOML の読み手を入れない。
4. **設定**: TS の設定は既定の道筋の値だけを持つ。Python の既定の設定の JSON（T1 が書き出す）と全部の値が同じことをテストで確かめる。既定でない切り替えはエラー。
5. **中間値のファイル**: `out/parity/<変化形>/` に `<段階>.f32`（float32 の生の並び）＋ `meta.json`（形・コミット・設定のハッシュ）。`out/` は git に入らない。数秒の小さな合成の中間値だけは `ts/fixtures/` にコミットしてよい（合成音のみ。中間値が無くても動く単体テストのため）。中間値が無いときの比べのテストは飛ばす（CI では走らない）。
6. **librosa をなぞる**: 動きの元は librosa 0.11.0 のソース（Docker のイメージの中にある）。T2 がパラメータと端の扱いを 1 か所に書き、実装はそれに従う。
7. **Worker**: 解析全体を 1 つの Worker で。並べる（HPSS を周波数の帯ごと、CQT をオクターブごと）のは G2 で遅いときだけ。

## 6. タスク

各タスクは自分の「ファイル」だけを変える（同じ波の中で重ならない）。テストは対象だけ（WSL が落ちやすいため）。自分が起動していないプロセスは止めない。作業ブランチは `spike/3-<slug>`、PR の行き先は `research/audio-analysis`。

## 9. リスク

| リスク                                                              | 対策                                                                                                              |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **CQT のクロマが librosa と合わない**（いちばん大きい）             | T2 で間引きとカーネルを先に書き出す。段階ごとに入力を差し込んで原因を分ける。合わない差は点数への影響で判断（G1） |
| 拍のテンポの推定の小さな差で、拍の並び全体が変わる                  | Python の打撃の強さを入れた比べ（T5）と通し（T15）を分ける。`_refine` が時刻の差を吸う見込み                      |
| 閾値の近くの判断（`?` の 0.93、セクションの山、調の変わり目）が反転 | 「完全に一致」は差し込んだ入力でだけ求め、通しでは記録の指標にする（§4）                                          |
| Chromebook が遅い・メモリが足りない                                 | float32、列ごとの計算（後押し）、配列を早く手放す。T17 で並べる・WASM。目標は G1 で見直す                         |
| ブラウザの読み込み（mp3・m4a）と変換で Python とずれる              | 一致の比べでは変換を外す（§4）。読み込みを含む通しは別に測って記録                                                |
| 移植が Python の凍結を崩す（直したくなる）                          | `py/dsp/` は変えない。見つけたバグは記録してユーザーと決める                                                      |
| ライセンスの混入（GPL の考え方の写し、依存の依存）                  | 依存は FFT の 1 つだけ（決定 4）。`THIRD_PARTY.md`、T18 で確かめる。Chordino・aubio・Essentia のコードは読まない  |
| 中間値のファイルが大きい（5 分の STFT など）                        | 一致の比べは 30〜90 秒の合成の変化形で。長い音は速さの計測だけ。`out/` は git に入らない                          |
| 計測ページの Artifact で Worker が使えない                          | 使えなければメインのスレッドで時間だけ測る（画面は止まるが値は取れる）と記録する                                  |
