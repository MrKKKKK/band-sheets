## 測った数字（中央値、3 回 = 新しいページで 1 回目 + 2 回目以降）

解析 = `analyzeDrums` の時間（ms）、メモリ = 描画プロセスの VmRSS の増え方（解析の前 → 山、MB。100 ms ごとに読む）。

| ---- | ----- | ------------------ | ------ | ------- | ------------------- | ------ |
| 1 分 | S-3   | 1240 / 1270 / 1141 | 1240   | 1318    | 45 / 20 / 22        | 22     |
| 1 分 | S-9   | 1316 / 1397 / 1326 | 1326   | 1408    | 51 / 29 / 28        | 29     |
| 1 分 | S-ext | 1444 / 1434 / 1492 | 1444   | 1501    | 60 / 27 / 33        | 33     |
| 3 分 | S-3   | 2241 / 2479 / 2192 | 2241   | 2393    | 85 / 49 / 83        | 83     |

| 3 分 | S-ext | 3312 / 3054 / 3363 | 3312   | 3494    | 112 / 85 / 44       | 85     |
| 5 分 | S-3   | 3731 / 3731 / 3555 | 3731   | 3941    | 121 / 138 / 117     | 121    |

「全体」は押してから結果までの時間（読み込み・音のデコード・Worker への渡しを含む。中央値）。メモリは 1 回目（冷たい）が大きく出る傾向（1・3 分）があり、ばらつきが大きい（5 分の S-9: 82〜171）。判定には最大も併記した。

### Node（devcontainer、1 回 1 プロセス、3 回）

解析 ms の中央値。メモリ = 音を読んだ後の VmRSS から、解析後の VmHWM（その処理の最大）までの増え方（MB、中央値。GC のタイミングで 0〜40 MB 揺れる）。

| 長さ | S-3 ms (MB) | S-9 ms (MB) | S-ext ms (MB) |
| ---- | ----------- | ----------- | ------------- |
| 1 分 | 1152 (5)    | 1241 (28)   | 1515 (27)     |
| 3 分 | 2247 (1)    | 2696 (30)   | 3400 (46)     |
| 5 分 | 3601 (1)    | 4354 (48)   | 5483 (47)     |

音声 1 分あたり（5 分の値 ÷ 5）: Node は S-3 約 720 ms・S-9 約 870 ms・S-ext 約 1,100 ms、Chromium は約 750・920・1,130 ms。長さにほぼ比例する（1 分の固定費が大きい分、1 分あたりは 1 分の入力が最も高い）。

### 大きさ

`drumBench.vite.config.ts` のビルドの Worker（`drumWorker-*.js` 84,090 B）を `gzip -9`: **31,269 B**（T12 の記録 31,264 B と同じ範囲。今回の変更は Worker に `level` を渡す 1 行だけ）。Worker は 3 段階すべてのコードを持つので、段階ごとの違いは無い。

## 方法と注意

- 入力: 調整用（tuning）・キット A・難しさ D2 の合成（`ext` の型を除く）を、1・3・5 分になるまでつなげて回したモノラル 16 bit の wav（`out/drum/t13/`、gitignore）。ホールドアウト（キット C）・開発用（キット B）・ユーザーの録音は使っていない。つなげた音のテンポは 1 つ（時間の計測だけなので、打点の正しさは見ていない）。
- 追加した道具: `drumBench`（ページ・Worker・プロトコル）に段階の選択（`level`、S-3 既定）を足した。解析のコードと設定（`drum-v0` 29e9d1cb07c2）は変えていない。
- Chromium は Playwright の Desktop Chrome（UA 上は Windows と出るが、実際は devcontainer の Linux 上のヘッドレス Chromium 156）。実機の PC や Chromebook ではない。数字は WSL2 上の値で、実機の PC の Chromium とは違いうる。
- ばらつき: メモリの 3 回は同じ長さ・段階でも 2 倍近く違う（GC と PCM の大きな配列の確保の時期による）ので、中央値と最大の両方を見る。

## コマンド（devcontainer `band-sheets`、作業ディレクトリ `/workspaces/band-sheets/.worktrees/spike5`）

```
# Chromium（ビルド → preview → 3 長さ × 3 段階 × 3 回、約 2 分）。結果: spikes/analysis/out/drum/t13/perf.json
docker exec -u node -w /workspaces/band-sheets/.worktrees/spike5 band-sheets \
  npx playwright test --config spikes/analysis/ts/browser/drumPerf.playwright.config.ts

# Node（上の実行で作られた concat-<n>min.wav を使う。1 回 1 プロセス）
docker exec -u node -w /workspaces/band-sheets/.worktrees/spike5/spikes/analysis band-sheets \
  npx tsx ts/browser/drumPerfNode.ts <1|3|5> <S-3|S-9|S-ext>

# 大きさ（playwright の webServer が drumBench をビルドした後）
gzip -9 -c spikes/analysis/out/drum/dist/assets/drumWorker-*.js | wc -c
```

追加したファイル: `ts/browser/drumPerf.spec.ts`・`drumPerf.playwright.config.ts`・`drumPerfNode.ts`。変えたファイル: `drumBench.ts`・`drumBench.html`・`drumProtocol.ts`・`drumWorker.ts`（`level` の通り道だけ）。`tsc --noEmit` は通る。

## 持ち越し・録音で見ること

- 実機（Chromebook など）の速さ・メモリは測っていない（この研究ブランチの範囲は PC のブラウザ）。アプリに組み込むときの質問 2（Worker の大きさの合わせた枠）の材料になる。
- S-ext を使うと S-9 より 1 分あたり約 2 割遅い（ペダル HH のための NMF の解き直し）。目標には十分収まるので今は直さない。
