## 指摘

### Q1 ホールドアウトの守りは `--dsp-config` の経路だけで、T12 と同じ調整のやり方は止められない（重大度: 中）

- **何が問題か**: `HeldOutError` が出るのは `--include-held-out` と `--dsp-config` を同時に指定したときだけ（`run_all.py:376-378`）。T12 の調整は `config.py` の既定値を書き換えて通し実行するやり方だったが、この経路では `--include-held-out` を付ければ（設定ファイルなしで）何度でもホールドアウトを解析・採点できる。T15 後の通し実行（計画の表）もこの形。`analyze.py --config` と `score.py` の CLI を手で組み合わせても回れる。「既定で除く」ことで、うっかり混ぜることは防げている。ただし「調整に使っていない」ことは記録にも仕組みにも残らない。
- **根拠**: `run_all.py:374-405`、`analyze.py:51`（`load_config(args.config)`）。テスト `test_refused_in_tuning_path` は `dsp_config` を渡したときしか確かめていない。
- **提案**: `--include-held-out` で実行したら、そのときのコミット（`git describe --dirty`）と設定のハッシュを `results/heldout-log.jsonl` に追記する。同じ設定のハッシュで 2 回目に走らせたときは警告を出す。計画の「実績」にも、ホールドアウトを走らせた回数と時点を書く。仕組みを足さない場合は、CLAUDE.md に「既定値を変えたあとに `--include-held-out` を走らせたら、それは最終評価の 1 回として記録する」と書く。

### Q2 CI の `spike-analysis-py` は必須のチェックではなく、GitHub ではまだ一度も走っていない（重大度: 中）

- **何が問題か**: `main` の保護で必須なのは `check` だけ（`gh api .../branches/main/protection/required_status_checks` → `"contexts":["check"]`）。Python のテストが落ちても、PR はマージできる。R1 の「CI で気づけるようにする」は半分しか達成されていない。また、このブランチは origin より 11 コミット先にあり、`gh run list --branch spike/audio-1` は空なので、この job は GitHub ではまだ一度も実行されていない（`requirements.lock.txt` は Docker イメージの `pip freeze` で、ハッシュの固定はない。ubuntu-latest で入るかは未確認）。job 自体は `unittest` が失敗すると exit 1 になるので、落ちれば赤にはなる。
- **提案**: PR を作ったら、`spike-analysis-py` が緑になることを確かめる。そのうえで必須のチェックに加える（14 秒で終わり、`check` とは別の job なので遅くならない）。加えない場合は、CLAUDE.md に「必須ではない。赤ならマージしない」と書く。

### Q3 `dsp-phase0` の名前が `--dsp-name` で変わらず、調整の実行で比べる相手の結果が上書きされる（重大度: 低）

- **何が問題か**: `active.append((PHASE0, "phase0"))`（`run_all.py:391`）は名前が固定。`--dsp-config x.json --dsp-name dsp-try` で走らせると、dsp-v1 の結果は `*.dsp-try.json` に分かれる。一方、それから作る位相 0 の結果は `*.dsp-phase0.json` を上書きし、`summary` にも `dsp-phase0` として出る。既定の設定で作った「比べる相手」が、別の設定の値に黙って入れ替わる。また `report.py` は `results/` にあるファイルを読む（`load_results`）。このため、前の `--include-held-out` で作った古いホールドアウトの結果が、設定を変えたあとも別の表に出続ける。今の数字（計画の表）は既定の設定の 1 回の実行なので、影響はない。
- **提案**: 名前を `f"{dsp_name}-phase0"` にする（既定では `dsp-v1-phase0`。表の名前も合わせる）か、`dsp_name != "dsp-v1"` のときは phase0 を作らない。テストを 1 件足す。

### Q4 R9 の説明が実際の修正と合っておらず、白玉の向きを逆にした比べ方は 1 拍のずれを見落とす（重大度: 低）

- **何が問題か**:
  1. 計画の実績とレビューの状態の欄には「R9: `piano` 以外の `check_alignment` は WARN のみ」とある。しかし、この扱いは T15 の前からあった（`git show ee9cff8:spikes/analysis/py/check_alignment.py` の `:158`、`:244`）。R9 で終了コードが 1 になっていたのは `mix == "piano"` の白玉＋揺れ 2 本（ENFORCED）で、それを直したのは「白玉は、音の始まりごとにいちばん近い正解の拍と比べる」という新しい規則。
  2. この逆向きの比べ方では、音の始まりは「どれかの拍」に近ければよい。そのため、白玉の正解が拍の整数倍ずれていても（小節の頭が 1 拍ずれるなど）見落とす。この 2 本は ENFORCED なので、守る力が少し弱くなった。最初と最後の音の確認（edge）は残っているので、全体が一様にずれていれば見つかる。
  3. `CHORD_MIN_SHARE_QUIET` 0.80 は、実際の値（89.8 %・100 %）より 10 ポイント近く下にある。対象は `pianoGainDb < 0` の 2 本で、どちらも `mix: full`（ENFORCED ではない）。この閾値は WARN を消しているだけで、FAIL を隠しているわけではない。描画の問題を覆い隠しているというより、ピアノを −9 dB にした混ぜ方の性質（ドラム・ベースがクロマに入る）。ただし、85〜90 % へ悪くなっても気づけない。`test_quiet_piano_has_lower_chord_limit` は定数を確かめているだけで、何も守っていない。
- **提案**: 文書の R9 を「白玉は逆向き（ENFORCED の 2 本が直った）、`arp8` は区間ごと、ピアノ −9 dB は 80 %。piano 以外は WARN（前から）」に直す。白玉は、正解の**コードの始まり**（= 鳴らした時刻）と比べる方が厳しく、1 拍のずれも見つかる。閾値は 0.85 程度にするか、80 % にした理由を書く。

### Q5 レベル M のセクション F 0.000 の原因の推定が、観測と逆（重大度: 低、文書）

- **何が問題か**: 計画には「セクションの格子が最初の（途中の）小節を 0 小節目に固定している（未検証）」とある。しかし結果を見ると、解析の最初のセクションは**最初の完全な小節の頭**から始まる（`*__mid1` で 1.55〜1.57 s = 3 拍後）。内側の境目は、正解よりちょうど 1 小節遅い（`full-t116-straight__mid1`: 正解 32.59 s、解析 34.67 s、差 2.08 s）。つまり、途中の小節を数えず、最初の完全な小節を 0 小節目にした 4 小節の格子になっている。採点の窓は 1 小節（2.069 s、`_bar_seconds`）なので、差は窓をわずか 11 ms はみ出し、27 本すべてで F が 0 になる。弱起の曲では、本物の録音でも同じことが起きる。
- **あわせて**: レベル M の 9 本の元は、どれも調整に使った曲。途中の小節から始まるホールドアウトは無い（`midbar` はホールドアウトを使わない設計）。目標の表で小節の頭を「調整用は達成」とした根拠は L0〜L2 だが、L0 と L2 では `dsp-phase0` も dsp-v1 と同じ値（1.000 / .972）。小節の頭を見つける力を示しているのは M（1.000 対 0.000）と L1・L3 で、独立に確かめられたのはホールドアウトの `arp8` だけ（これは外している、0.000）。
- **提案**: 計画の「新しく分かったこと」の原因の推定を、上の観測に置き換える。目標の表の小節の頭の根拠には M と `dsp-phase0` の差を書く。スパイク 2 で、ホールドアウトの曲から M の変化形を作る（ホールドアウトとして扱う）。

### Q6 `report.py` だけが古い決め方のまま（中点で採点、M を曲ごと・全体に入れる）（重大度: 低）

- **何が問題か**: `report.py` の取り違えと確信度の表は、今も拍の中点で比べている（`report.py:8`、`:75-82`。docstring の「like score.py」は正しくなくなった）。このため、REC の取り違えの表には R6 の「表か裏か」の曖昧さが残る。また `build_report` の `by_song` と「全体」には、レベル M の 27 本が入る。ほぼ満点の M が足されるので、「全体」の正解率と位相の表の意味が T15 の前と変わる。`summary.levels.md` が M を曲ごとから除いた方針とも合わない。
- **提案**: `report.py` も 1/4・3/4 の 2 点（重み 1/2）にそろえるか、docstring に「中点のまま」と書く。「全体」と曲ごとの表は M を除く（M はレベル別の行にだけ出す）。

### Q7 R5 で、余韻に出る余分な拍がどの数字にも出なくなった（重大度: 低）

- **何が問題か**: R5 の切り方は、採点としては正しい（上記のとおり）。ただし、解析が余韻に置く拍（REC で 12 個 = 楽譜の最後に空の 3 小節）は、アプリでは目に見える誤り。この拍は今、どの列にも出ない。計画は「解析器の改善ではない」と正しく書いているが、これを測る数字が無くなった。
- **提案**: `score._beats` で、窓の外に出た解析の拍の数（`nEstOutside`、前と後ろ）を出力する。`summary` の列にも足す。スパイク 2 で「最後の音のあとに拍を出さない」規則を足すときの物差しになる。

### Q8 計画の「475 本」は変化形の数ではない（重大度: 低、文書）

- **何が問題か**: 「通し実行（…、475 本）」の 475 は、行数（変化形 95 × 解析器 5、`summary.csv` は 476 行 = 見出し + 475）。変化形は 95 本（基本 38、加工 29、M 27、REC 1）。
- **提案**: 「95 変化形 × 5 解析器」と書く。
