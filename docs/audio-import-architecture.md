# 音源から譜面の下書きを作る機能（入力補助）: アーキテクチャの調査と設計メモ

2026-10-10 作成、同日改訂（ユーザーの判断を反映: AI を使わない機械的な判定、GPU なし、優先順位、評価の考え方、お金の方針）。調査のみで、コードは変えていない。ネット上の情報は 2026-10-10 時点で確かめたもの。数字は「目安」で、本当の精度はスパイク（小さな試作）で測る。

## 0. まとめ（先に結論）

- **解析は AI（機械学習・学習済みモデル）を使わず、機械的に判定する**（2026-10-10 ユーザー決定）。昔からある信号処理（音の強さ・周波数の計算）と、はっきり書ける規則だけで作る。GPU は使わない（持っていない）。
- **構成**:
  1. スパイク（試作）は **PC の Python のコマンド（CLI）＋ librosa**（音の解析の定番ライブラリ、ISC ライセンス）で作る。試行錯誤とグラフでの確認が速い。
  2. 解析結果は **共通の中間データ（JSON）** にし、`.bandsheet` への変換は **band-sheets のリポジトリの TypeScript（テスト付き）** で行う。
  3. 取り込みは **band-sheets に「ファイルから取り込む」（ファイル選択・ドラッグ＆ドロップ）を足す**。Drive を経由した受け渡しはしない。
  4. 機械的な方法は計算が軽いので、**精度が確かめられた方法は後で TypeScript に移して、ブラウザの中だけで動かせる**。そうなれば CLI のインストールも要らなくなる（§2.2）。鼻歌は最初からブラウザで試す。
  5. サーバーは**作らない予定**。運営の費用はほぼゼロのままにする（§6）。
- **AI を使わない場合の弱点**（正直な見込み）: 「バンド全体の音からの歌メロ」と「歌詞の聞き取り」は、機械的な方法ではほぼ無理。代わりに、**歌メロは「曲を聴きながら鼻歌で歌い直す」**、**歌詞はユーザーが貼り、音符の順に並べる（今のメロディ画面の自動割り当てと同じ）**で補う。
- **Drive の重要な発見**: `drive.file` の権限が「OAuth クライアントごと」か「Cloud プロジェクトごと」かは、**Google の公式ドキュメントに書かれていない**。→ ローカルのファイルを取り込む方式にすれば、この問題も Google の審査への影響も無い。
- **評価の考え方**（2026-10-10 ユーザーの指摘を反映）: 「作曲者の意図としての正解」は決められない。そこで、①**band-sheets の曲を alphaTab で音にした合成音源**（正解が完全に分かる）で精度を測り、②**本物の録音では「ユーザーが自分で書くもの」に直すまでの手間**を測る（§7）。

## 1. 前提（band-sheets 側の事情）

- 静的なサイト（GitHub Pages）。サーバーは持っていない。曲は各ユーザーの Google Drive にあり、運営の費用はほぼゼロ。
- 曲のファイル `.bandsheet` = ChordPro（コード譜と歌詞）＋ alphaTex のパート（Vocal のメロディ、Drums）。例: `src/lib/saintsSample.ts`。
- エディタが読み書きできる alphaTex は「決まった書き方（サブセット）」だけ。外れると、そのセクションは読み取り専用になる（`src/lib/melody.ts`、`src/lib/drum.ts` の冒頭の説明）。
- 前のアプリ（sheet-for-player）の反省: 外から自動で持ってきたもの（ChordWiki）は当てにならない。**取り込んだ結果は「下書き」で、ユーザーが直すもの**。精度は 100% でなくてよい（ユーザー）。
- 使うのは当面ユーザー本人だけ（2026-10-10 決定）。

### 2.2 CLI をやめてブラウザだけにできるか

- できる見込みが高い。必要な部品:
  - 音源ファイルの読み込み: Web Audio の `decodeAudioData`（mp3・m4a・wav など、ブラウザが再生できるもの）。マイクは `getUserMedia`。
  - 周波数の計算（FFT）: 小さなライブラリか自前。特徴量のライブラリ **Meyda**（MIT。クロマ＝12 音それぞれの強さ、なども出せる）。
  - 単音の音の高さ: **pitchy**（0BSD。McLeod の方法）。鼻歌ならこれで足りる見込み。
  - 拍の検出（動的計画法）、コードの当てはめ（テンプレート）、平滑化（ビタビ法）、自己類似行列: どれも数十〜数百行で書ける。
- 移すときの注意: librosa の結果と TypeScript の結果を同じ音源で比べるテストを用意する（数値が少しずれるのは許容）。
- **おすすめ**: 鼻歌（優先 2）は最初からブラウザで作る。コード・拍・セクション（優先 1）は Python で試作して方法と設定値を決め、うまくいったら TypeScript に移す。移し終えたら CLI はやめてよい。

## 3. Google Drive との連携（受け渡しの方法）

### 3.1 `drive.file` の見える範囲（調べた結果）

- 公式の説明: 「アプリで開いた、またはユーザーが Google Picker（Google のファイル選択画面）やアプリのファイル選択でアプリに渡したファイル」を作成・変更できる。**非機密（non-sensitive）のスコープ**で、基本の確認だけでよい。
  — https://developers.google.com/workspace/drive/api/guides/api-specific-auth
- **「アプリ」の単位（OAuth クライアントか Cloud プロジェクトか）は公式に書かれていない**（M7 の調査 `docs/m7-drive-findings.md` §1 と同じ結論。今回もう一度探したが見つからなかった）。
  - 「プロジェクト単位」を示す手がかり: Picker の `setAppId` は「`drive.file` を使うときは必須」で、値は **Cloud プロジェクト番号**。
    — https://developers.google.com/workspace/drive/picker/reference/picker.pickerbuilder.setappid
  - 「クライアント単位」を示す報告: rclone（Drive と同期するツール）のフォーラムで「`drive.file` の許可はファイルを作ったアプリ（クライアント）にだけ付く。クライアント ID を変えたら、前のファイルを書き換えられなくなった（`appNotAuthorizedToChild`）」（2018 年。2 つのクライアントが同じプロジェクトだったかは不明）。
    — https://forum.rclone.org/t/google-drive-changing-client-id-and-scope-drive-file-write-access/6693
  - 結論: **同じプロジェクトに「デスクトップアプリ」用の OAuth クライアントを作れば見えるかもしれないが、保証は無い**。Google が動きを変えても困らない設計にする。
- Google Picker は、**任意の Drive のファイルに `drive.file` の許可を与える標準のやり方**。ユーザーが選んだファイルだけ、アプリが読めるようになる。2025 年からはデスクトップアプリ向けの Picker（ベータ。普段のブラウザのタブで開く）もある。
  — https://developers.google.com/workspace/drive/picker/guides/overview 、 https://developers.google.com/workspace/drive/picker/guides/overview-desktop
  - Picker を使うには API キー（公開してよいが、使えるサイトを制限する）とプロジェクト番号が要る。スコープは `drive.file` のままなので、**Google の審査の区分は変わらない**。

### 3.2 受け渡しの方法の比較

| 方法                                                                                            | 手間                             | 確実さ                                                 | 審査への影響                     |
| ----------------------------------------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------ | -------------------------------- |
| ① band-sheets で **ローカルのファイルを選ぶ / ドラッグ＆ドロップ**（`.bandsheet` か 中間 JSON） | 解析 → 保存 → 取り込み、の 1 手  | ◎ Drive の仕様に左右されない。ログインしなくても使える | なし                             |
| ② CLI が Drive の band-sheets フォルダに書く（同じプロジェクトのクライアント）                  | CLI でも Google にログインが要る | △ 見えるかどうかが公式に保証されていない               | 同じ同意画面。非機密なので小さい |
| ③ ②＋ band-sheets に Picker を付けて、ユーザーがそのファイルを選ぶ                              | 選ぶ操作が 1 回増える            | ○ 公式のやり方                                         | なし（API キーの管理が増える）   |
| ④ Drive の「アプリで開く」連携（Drive UI integration）                                          | 設定が多い                       | ○                                                      | 追加の設定と確認が要る可能性     |

**おすすめ: ①**。取り込んだ曲は、今の「サンプル曲を追加」と同じように「この端末だけ」の新しい曲（下書き）として一覧に出し、ユーザーが確かめてから「保存」で Drive に入れる。解析がブラウザに移れば（§2.2）、①の「ファイル」は音源そのものになり、受け渡しの問題自体が無くなる。

## 4. 方法の調べ（AI を使わない、機械的な方法）

ここで「機械的」とは、**学習（大量のデータから自動で値を決めること）をしていない**方法を指す。人が決めた計算と規則、人が決めた設定値だけで動く。

精度は**昔の評価（MIREX など、AI 以前の方法どうしの比較）からの目安**で、実際のバンドの録音（部屋鳴り、スマホのマイク、音の被り）では下がる。

### 4.0 共通の前処理

- **HPSS（調波・打撃の分離）**: 音を「伸びる音（ギター・ベース・歌・鍵盤）」と「叩く音（ドラム）」に分ける古典的な方法（スペクトログラム＝時間と周波数の表を、横方向と縦方向のメディアンフィルタでならす）。学習は不要。librosa の `effects.hpss` / `decompose.hpss`。コードの解析は「伸びる音」側、ドラムと拍は「叩く音」側を使う。完全には分かれないが、前処理として効く。
- **クリック（メトロノーム）付きの録音**: 自分たちの演奏や鼻歌を、クリックを聞きながら録れば、**拍の位置が最初から分かる**。いちばん確実な「機械的な」方法。band-sheets がクリックを鳴らしながら録音する機能を持てば、自分の録音ではいつでも使える。

### 4.1 拍・テンポ・小節の頭（優先 1）

| 方法                                    | 中身                                                                                                                                                                  | 精度の目安・弱点                                                                                                    |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 音の立ち上がりの強さ（onset strength）  | 周波数ごとの音量の増え方を足し合わせた曲線。librosa `onset.onset_strength`                                                                                            | すべての土台                                                                                                        |
| テンポの推定（テンポグラム / 自己相関） | 上の曲線が何秒ごとに繰り返すか。librosa `feature.tempogram`、`feature.rhythm.tempo`                                                                                   | 半分・倍のテンポに間違えやすい（80 と 160）→ band-sheets で直せばよい。既知のテンポを渡すのも手                     |
| 拍の位置（Ellis の動的計画法、2007）    | 「立ち上がりが強い所」と「テンポどおりの間隔」の両方を満たす拍の並びを計算で探す。librosa `beat.beat_track`                                                           | テンポがほぼ一定の曲ならかなり当たる。テンポが大きく揺れる演奏（ルバート）は苦手。PLP（`beat.plp`）は揺れに少し強い |
| 小節の頭（ダウンビート）                | librosa には無い。**規則で決める**: 4 拍ごとの 4 通りの区切り方を試し、「コードが変わる位置」「低音（バスドラ・ベース）の強さ」がいちばん小節の頭に集まる区切りを選ぶ | 最も間違えやすい。外れると全部が 1〜3 拍ずれる → 取り込み画面で「1 拍ずらす」を用意（§5.4）                         |
| 拍子                                    | 4/4 か 3/4 だけを、上と同じ考え方で比べる                                                                                                                             | 不確かなら 4/4                                                                                                      |

### 4.2 コード（優先 1）

| 方法                          | 中身                                                                                                                                                                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| クロマ（12 音それぞれの強さ） | librosa `feature.chroma_cqt`（定数 Q 変換＝音階に合わせた周波数の分け方）か `chroma_cens`（音量の差にゆるい版）。「伸びる音」側から計算し、**拍ごとに平均**する（`util.sync`）                                                                         |
| テンプレートとの比較          | 「C メジャー = C・E・G が強い」のような型を、メジャー 12 ＋ マイナー 12 ＋ 7th（属 7・マイナー 7・メジャー 7）で用意し、拍ごとに一番近い型を選ぶ                                                                                                       |
| ならし（平滑化）              | 1 拍だけ違うコードになる「ちらつき」を消す。①メディアンフィルタ（前後の多数決）、②**HMM ＋ビタビ法**（「同じコードが続きやすい」という確率を人が決めて、全体で一番もっともらしい並びを計算）。librosa `sequence.viterbi` と `sequence.transition_loop` |
| ベース音                      | 低い音域だけのクロマで一番強い音 → 分数コード（`C/E`）の候補。誤りやすいので最初は出さない                                                                                                                                                             |
| コードが変わる位置            | 拍単位で判定し、1 拍か 2 拍単位に丸める                                                                                                                                                                                                                |

- 精度の目安: テンプレート＋ならし の方法は、ポップスで**メジャー / マイナーの区別までなら 6〜7 割程度**（AI 以前の方法の水準）。7th 以上（テンション）は当てにならない。→ **目標は「ルートとメジャー / マイナー」**、7th は確信が高いときだけ。
- 経過音・刺しゅう音（コードの音でない短い音）は、拍ごとに平均することで影響が薄まる。
- 参考になる古典的な実装: Chordino / NNLS Chroma（学習なし、HMM あり）は **GPL-2.0** なので、コードは借りずに考え方だけ参考にする。

### 4.3 セクション（優先 1）

| 方法                             | 中身                                                                                                                                                            |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 自己類似行列（SSM）              | 拍ごと（または小節ごと）のクロマを、すべての組み合わせで比べた表。同じメロディ・コードの繰り返しが「斜めの線」として見える。librosa `segment.recurrence_matrix` |
| 境目の検出（Foote の方法、2000） | 表の対角線に沿って「ここで雰囲気が変わる」点を探す（チェッカーボード型の計算）。librosa には `segment.agglomerative`（似たものをまとめる）もある                |
| 同じセクションの判定             | 区間どうしのクロマの並びが似ていれば同じ記号（A、A …）。**境目は小節の頭（できれば 4 小節や 8 小節の区切り）にそろえる**規則を足す                              |

- 精度の目安: 境目は「だいたい合う」、名前（A メロ・サビ）は付けられない。下書きでは「A」「B」「C」… の記号だけを付け、名前はユーザーが直す。

### 4.4 鼻歌 → メロディ（優先 2）

| 方法                   | 中身                                                                                                                                                                 |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| YIN（2002）            | 波形の繰り返しの周期から音の高さを出す、古典的な方法。librosa `yin`。JS なら pitchy（McLeod の方法、近い考え方）                                                     |
| pYIN（2014）           | YIN の候補を、HMM ＋ビタビ法で「なめらかにつながる」ように選ぶ。声が出ている・いないの判定も出る。librosa `pyin`。設定値は論文の作者が手で決めたもの（学習ではない） |
| 音符への区切り（規則） | ①声が出ている区間ごとに分ける、②同じ区間の中で半音以上の変化が一定時間続いたら別の音、③高さは区間の中央値を一番近い半音に丸める、④短すぎる音は前の音にまとめる       |
| リズム                 | クリックに合わせて歌ってもらい、音の始まりを拍の格子に丸める（§5.4）                                                                                                 |

- 精度の目安: 静かな部屋での鼻歌なら、**音の高さはかなり当たる**（単音なので機械的な方法が得意）。難しいのは「1 音の区切り」と「リズム」。クリックありなら現実的。
- 比べる相手: 今のメロディエディタのキーボード入力はかなり速い（M4 で「非常に使いやすい」）。**鼻歌の取り込みは、これより速くならないと意味が無い**。

### 4.5 録音からの歌メロと歌詞のタイミング（優先 3）

- **バンド全体の音から歌メロだけを取り出すのは、機械的な方法では弱い**。古典的な方法（Melodia、2012 など。一番目立つ音の高さの線を規則で追う）はあるが、ギターのリードやハモリに引っぱられる。しかも Melodia の実装は Essentia（AGPL）か、非商用のみのプラグインでしか手に入らない。
- 現実的な代わり（どれも機械的）:
  1. **歌だけのトラック**がある録音（練習のときにボーカルのマイクだけ別に録る、ミキサーの個別出力など）なら、鼻歌と同じ方法（§4.4）がそのまま使える。
  2. **曲を聴きながら鼻歌で歌い直す**（イヤホンで曲を流し、クリック代わりにする）。§4.4 の機能を流用でき、拍の位置も元の曲に合う。
  3. HPSS の後、ボーカルの音域だけで一番強い音を追う簡易版（精度は低い。試す価値はある程度）。
- **歌詞**（自動の聞き取りはしない、2026-10-10 決定）: ユーザーが歌詞を貼る。音節（M4 の規則: 小さい「ゃゅょ」「っ」は前とまとめる、「ー」は 1 音節、`src/lib/syllables.ts`）に分け、**メロディの音符に順番に並べる**。これは今のメロディ画面の「自動割り当て」（`src/lib/melodyLyrics.ts` の `autoAssign`）と同じで、ずれたら既にある「のばす・つめる・分ける・歌詞なし」で直す。新しい技術は要らない。
- **コード譜の `[C]` を歌詞のどの文字に置くか**には、歌詞の各音節の時刻が要る。機械的な方法:
  - メロディがあれば、音節の時刻 = 割り当てた音符の時刻。
  - メロディが無ければ、**タップで合わせる補助**: 曲を流しながら、音節ごとにキーを叩く（カラオケの歌詞データ作りと同じやり方）。1 曲数分で、確実。band-sheets の画面として作る（Claude Design でスケッチしてから）。
  - 現実的な見込み: 自動で音節の時刻を当てるのは（AI なしでは）難しい。**タップ方式がいちばん確実で手間も小さい**。

### 4.6 ドラム（優先 4）

| 方法                                    | 中身                                                                                                                                                                                    |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HPSS の「叩く音」＋帯域ごとの立ち上がり | 低い帯域（〜150 Hz 付近）の立ち上がり → BD、中域（150 Hz〜1 kHz）と雑音成分（1〜5 kHz）が同時 → SD、高域（5 kHz〜）の短い音 → HH                                                        |
| 長さと高さの規則                        | 高域の音が長く残る → HO（オープン）か シンバル。シンバルの区別（CR / RD）は、立ち上がりの強さと残り方で大まかに。タム（T1 T2 FT）は中低域の「音程のある」立ち上がりを高さの順に         |
| 自分のドラムの音を型にする（任意）      | 自分のキットの各太鼓を 1 回ずつ録り、その周波数の形を型にして、曲の音を「型の重ね合わせ」に分ける（NMF＝非負値行列因子分解。型を固定するので学習ではないが、グレーゾーン。§8 の質問 2） |
| 強弱                                    | 立ち上がりの大きさが周りより明らかに小さい SD → ゴースト、大きい → アクセント（信頼性は低い）                                                                                           |

- 精度の目安: **BD・SD・HH の 3 つは、ドラムがはっきり聞こえる録音なら使える程度**。オープン / クローズの区別、タム 3 種、クラッシュ / ライドの区別は大きく下がる。
- 拍の格子（§4.1）に丸めると、「基本の 8 ビート＋フィルの位置」は出せる見込み。それだけでもドラムの入力の手間は減る。

### 4.7 参考: AI を使う場合（今回は採らない）

AI（学習済みモデル）を使うと、特に「全体の音からの歌メロ」「歌詞の聞き取り」「ドラムの細かい区別」が大きく良くなる。代表: 音源の分離 Demucs（MIT）、拍 Beat This!（MIT）、セクション all-in-one（MIT）、コード BTC（MIT）、音の高さ Basic Pitch（Apache-2.0）・CREPE（MIT）・RMVPE（Apache-2.0）、歌詞 Whisper（MIT）、ドラム ADTOF（**非商用**）・MT3（Apache-2.0）。なお、日本語の歌の自動の聞き取りは AI でも文字の誤りが約 40%（IdolSongsJp、2025: https://arxiv.org/abs/2507.01349 ）で、歌詞を貼る方式はどちらにしても正しい。機械的な方法で足りない所が分かったら、その部分だけ改めて考える。

### 5.1 解析側が出さなければならないもの

| ------------------------ | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |

### 5.3 変換（中間データ → `.bandsheet`）の置き場所と作り方

- **band-sheets のリポジトリの `src/lib/import/`** に、純粋な関数として置く（テスト駆動。今までの `src/lib` と同じやり方）。CLI の結果でも、ブラウザの解析でも、同じ関数を通す。
- 出力のテキストは、**既にある `serializeMelody` / `serializeDrums` / `serializeSong` で書く**。これでエディタが読める書き方から外れない（読み取り専用にならない）ことが保証される。テストでは「変換 → `parseSong` → 各パートの読み取りが成功する」を必ず確かめる。
- 解析をブラウザに移すとき（§2.2）は、解析のコードも `src/lib/analysis/` などに純粋な関数として置ける（入力は数値の配列なので、テストしやすい）。

### 5.4 丸め（クオンタイズ）とテンポの問題

用語: **クオンタイズ**＝ずれた時刻を、楽譜のマス目（8 分・16 分など）に合わせること。**ルバート**＝テンポを意図的に揺らす演奏。

1. **拍の時刻を基準にする**（テンポの数字から計算しない）。各音を「何拍目の何割の位置か」に直してから丸める。テンポが少しずつ揺れても、ずれが積み重ならない。人間のバンドの録音ではこれが必須。
2. **マス目の候補は 16 分と 8 分の 3 連**。拍ごとに、両方で丸めて誤差の小さい方を選ぶ。5 連以上は自動では作らない。
3. **シャッフルの曲**は、8 分の 3 連の「1 つ目と 3 つ目」に来る音を普通の 8 分として書き、セクションに `\tf triplet8th` を付ける（band-sheets の決まり: 音価は変えずに Shuffle 表記）。
4. **短すぎる音は捨てる / まとめる**（例: 16 分の半分未満）。同じ高さが続くなら 1 つの音にする。
5. **小節の頭を間違えると、全部が 1〜3 拍ずれる**。取り込みの画面で「小節の頭を 1 拍ずらす」を選べるようにする（中間データを持っていれば、変換をやり直すだけ）。
6. **弱起は band-sheets に無い**ので、最初の小節は休符で埋める（「聖者の行進」のサンプルと同じ）。
7. **テンポ**は拍の間隔の中央値から 1 つ決める。途中で大きく変わる曲は、セクションごとの値を `{comment: …}` で書き残すだけにする。
8. **拍子**は 4/4 と 3/4 だけを判定し、不確かなら 4/4。途中の変更は扱わない。
9. **音名の書き方**（`C#4` か `Db4` か）は、推定したキーで決める（フラット系のキーならフラット）。キーの推定は、曲全体のクロマを長調・短調の型（Krumhansl のキープロファイル。心理実験で人が決めた値）と比べる機械的な方法。
10. **セクション**は、検出した境目を小節の頭にそろえる。コード譜の 1 行は 4 小節（歌詞があれば歌詞の区切り）を目安にする。

### 5.5 「下書き」であることの示し方

- 取り込んだ曲は「この端末だけ」の新しい曲として作り、題名の後ろに「（下書き）」を付ける案。
- ファイルの先頭に `{comment: 自動解析の下書き 2026-10-10 band-sheets-analyzer 0.1.0}` を入れる（band-sheets は知らない行もそのまま残す）。
- 確信度の低いコードには `?` を付ける（例: `[Am?]`）。コードは解釈しない文字列なので、そのまま表示できる。

## 8. 評価の考え方と段階的な進め方

### 8.1 「正解」をどう決めるか（2026-10-10 ユーザーの指摘を反映）

演奏の録音には、作曲者の意図・演奏者のアドリブ・経過音や刺しゅう音などが混ざり、「唯一の正解」は決められない。そこで基準を 3 段にする。

1. **合成音源（正解が完全に分かる）で、精度を測る**
   - band-sheets の曲を **alphaTab の音声書き出し**（alphaTab 1.6 から `exportAudio`。band-sheets は 1.8.4 を使用）か MIDI 書き出し＋音色（同梱の Sonivox、Apache-2.0）で音にする。正解は元の `.bandsheet` そのもの。
   - 最初の曲は内蔵の「聖者の行進」（`src/lib/saintsSample.ts`）。Vocal と Drums のパートがある。コード譜のコードは音にならないので、**評価用にコード譜からピアノの伴奏パート（各拍に和音）を自動で作る**小さなスクリプトを用意する。
   - 条件を変えて試す: テンポ（80〜160）、楽器の組み合わせ（ピアノ伴奏だけ／＋ドラム／＋メロディ）、シャッフルあり・なし、音量のバランス。必要なら雑音や部屋の響きを足す。
   - 合成音は本物より「きれい」なので、ここでの結果は上限の目安。
2. **アプリが実際に使う粗さで測る（細かすぎる差は数えない）**
   - コード: **拍ごと（または小節ごと）に、ルートとメジャー / マイナーが合っているか**の割合。7th の有無は別に数える。短い経過音などは評価に入らない（拍ごとの比較なので自然にそうなる）。
   - 拍: **許容幅つきの F 値**（正解の拍の ±70 ms 以内なら当たり。mir_eval という評価の定番ライブラリ、MIT）。小節の頭の正解率は別に数える。
   - メロディ: 一定より短い音（例: 16 分未満）は無視し、丸めた後の音の高さと始まりの位置で比べる。
   - セクション: 境目が正解から 1 小節以内なら当たり。
3. **本物の録音では「役に立つか」を測る**
   - 基準は「作曲者の正解」ではなく、**「ユーザー自身が band-sheets に書くもの」**。
   - 測るもの: 下書きを、ユーザーが納得する形に直すまでの**時間と直した箇所の数**。比べる相手は、同じ曲を**一から手で入れる時間**。
   - 録音: 自分たちのバンドの練習（スマホで十分）、自分で弾き語りした曲。市販の曲は手元だけで使う。

### 8.2 スパイクと進め方

各スパイクは「作ってみて、測って、続けるか決める」。続ける判断の基準は **「下書きを直す時間」が「一から手で入れる時間」より明らかに短いこと**。

- **スパイク 0（評価の土台）**: 合成音源を作るスクリプト（alphaTab で `.bandsheet` → wav、コード譜 → ピアノ伴奏）と、評価のスクリプト（§8.1 の 2）。以後のスパイクはすべてこれで測る。
- **スパイク 1（優先 1）: コード＋拍＋セクション**: Python ＋ librosa の CLI（band-sheets とは別の Dev Container）。HPSS → 拍（Ellis の方法）→ 小節の頭（規則）→ 拍ごとのクロマ → テンプレート＋ならし → 自己類似行列で境目。出力は中間 JSON と、小節ごとのコードの一覧。合成音源で測り、次に本物の録音 2〜3 曲で直す時間を測る。
- **スパイク 2（優先 2）: 鼻歌 → メロディ（ブラウザ）**: `spikes/` の下の小さなページ。クリックを鳴らしながらマイクで歌う → pitchy（または自前の YIN）→ 規則で音符に区切る → 拍に丸める → メロディの alphaTex。「聖者の行進」「きらきら星」を歌って、キーボード入力の時間と比べる。
- **スパイク 3: 変換を band-sheets に入れる**（スパイク 1 か 2 がよければ）: `src/lib/import/`（中間 JSON → `.bandsheet`）をテスト駆動で作る。「ファイルから取り込む」画面を Claude Design でスケッチしてから作る。小節の頭のずらし、確信度の低いコードの印。
- **スパイク 4（優先 3）: 録音からの歌メロ＋歌詞のタイミング**: 歌だけのトラックがある録音で §4.4 の方法を試す。「曲を聴きながら歌い直す」方式と、歌詞のタップ補助の画面（スケッチから）。
- **スパイク 5（優先 4）: ドラム**: HPSS ＋帯域ごとの規則。合成音源（Drums パート）で BD / SD / HH の当たりを測り、自分たちの練習の録音で直す時間を測る。
- **その後**: うまくいった方法から TypeScript に移し、ブラウザの中だけで動かす（§2.2）。全部移せたら CLI をやめる。

## 9. ユーザーの判断と、確認したいこと

### 決まったこと（2026-10-10）

- GPU は無い。**解析は AI を使わず、機械的に判定する**（信号処理＋はっきり書ける規則）。
- 優先順位: ①コード＋拍＋セクション → ②鼻歌のメロディ → ③録音からの歌メロと歌詞のタイミング → ④ドラム。
- 使うのは当面ユーザー本人だけ → Python の CLI で十分（試作）。
- 歌詞はユーザーが貼る。自動の聞き取りはしない。
- 評価は「合成音源の正解」と「ユーザー自身が書くもの」を基準にする（§8.1）。
- 収入は運営の費用をまかなう分だけ。有料機能・決済は作らない。あっても寄付のリンク。サーバーは作らない予定。
- ライセンスは商用可・継承条件なし（ShareAlike / コピーレフトでない）を優先。
- 下の「確認したいこと」1〜5・7〜10 は**おすすめどおり**に決定（2026-10-10 ユーザー）。HMM・ビタビ法は「機械的」に入れる／ドラムの型（NMF）は帯域の規則で足りないときだけ／受け渡しはファイルを選んで取り込む／試作は `spikes/analysis/`／合成音源で評価／クリックあり／タップ補助を優先 3 でスケッチから／下書きの印は 3 つとも／寄付のリンクは今は付けない。
- 6（本物の録音）は**保留**。ユーザーが協力者を募ってみる。それまでは合成音源と自分の鼻歌だけで進める（スパイク 0〜2 は録音なしで進められる）。

### 確認したいこと（6 以外は決定済み。記録として残す）

1. **人が決めた設定値で動く「確率の計算」（HMM・ビタビ法）は「機械的」に入れてよいか**。例: pYIN（鼻歌の音の高さ）、コードのならし（「同じコードが続きやすい」という値を人が決める）。これらは**データから学習しておらず、値は人が決めて書いたもの**で、計算の中身も全部説明できる。**おすすめ: 入れてよい**。外すと、鼻歌の音の高さとコードの「ちらつき」がかなり増える。
2. **自分のドラムの音を型にして分ける方法（NMF、§4.6）はよいか**。型は自分の録音から取り、その後に自動で調整はしない（学習ではない）。**おすすめ: よい（ただしスパイク 5 で、帯域の規則だけで足りなければ）**。
3. **受け渡しは「band-sheets でファイルを選んで取り込む」方式でよいか**。**おすすめ: これ**。解析をブラウザに移せば、音源ファイルを直接選ぶ形になる。
4. **解析のコードの置き場所**。**おすすめ**: Python の試作は band-sheets の中の `spikes/analysis/`（`spikes/format/` と同じく、本体とは別の依存関係）。お金の方針で非公開にする理由が無くなったので、別のリポジトリにしなくてよい。変換と、移した後の解析（TypeScript）は `src/lib/` に置く。
5. **評価用の合成音源の作り方**（コード譜からピアノの伴奏を自動で作る、テンポや楽器を変える）でよいか。**おすすめ: よい**。正解を手で作る手間がゼロになる。
6. **本物の録音を用意できるか**（バンドの練習 2〜3 曲。できれば歌だけのトラックも）。**おすすめ: スマホで十分**。歌のマイクだけ別に録れるなら優先 3 がずっと楽になる。市販の曲は手元だけで使い、リポジトリには入れない。
7. **鼻歌や演奏の録音のとき、クリック音に合わせるのは負担ではないか**。**おすすめ: クリックあり**（拍の検出が要らなくなり、精度が大きく上がる）。
8. **歌詞のタイミングを合わせる「タップ補助」の画面を作ってよいか**（曲を流しながら音節ごとにキーを叩く）。**おすすめ: 作る（優先 3 の中で、スケッチから）**。
9. **「下書き」の印の付け方**（題名に「（下書き）」、先頭のコメント、自信の無いコードに `?`）。**おすすめ: 3 つとも**。題名の印は保存のときに外せるようにする。
10. **寄付のリンクをいつ付けるか**。**おすすめ: 今は付けない**。人に使ってもらう段階（Google の本番の確認をするころ）で考える。
