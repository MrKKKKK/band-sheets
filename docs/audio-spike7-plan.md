## 1. 問いと「できた」の意味

**問い**: v1a に、ベースの音を使ったルートの決め方と、段階的に広げた語彙を足すと、転回形・クリシェの曲で「コード名（ルート・種類・`/X`）」が正しく出る割合は上がるか。既存の曲の点を下げずに、アプリの予算に収まるか。

値打ち: `C/E` が `Em` と出るのを直せば、スパイク 6 のベースの段階がそのまま `/X` を付けられる。`Am – AmM7 – Am7 – Am6` は今は全部 `Am` か取り違えで、一から書き直す。**直す手数が減ること**が目的で、決めつけより候補。

できた:

- `ts/chords2/` の v2 が動き、切り替えを全部切ると v1a と 1 ビットも同じ出力（固定のテスト）。
- 合成と録音で §5 の指標を測り、基準（§5）と比べた表が、B と採用した語彙の段階ごとにある。止めた段階は理由がある。
- main への写し方（§6）と、写すファイルの一覧・大きさが分かる。

**やらないこと**: アプリへの組み込み。v1a の値の調整。解析済みの要素を引く（将来）。11・13 のテンション、`add9`・`madd9` 以外の add、複合拍子、鼻歌、ベースの音符（B-4）。

## 2. 方法

### 2.0 v2 の形（U1）

v1a の区間はコードの Viterbi の出力を `mergeChords` でまとめたものなので使い回さない。v1a の拍・拍ごとのクロマ・小節ごとの調を受け取り、広げた状態で v2 の Viterbi を回して区間を作り直す（時間は最大 4 倍。T7 で Viterbi の割合を測る）。v1a の `vocab.ts`・`harmony.ts` の値は読むだけで、状態を広げる部分（型・遷移の行列）は `ts/chords2/` に書く。T3 の終わりの条件に「内声のクリシェの合成で区間が 4 つ作れる」を入れる。

### 2.1 B: ベースをルートに使う（T8 で比べ、G2 で採用を決める）

仮説: v1a の全帯域のクロマでは低いベースの音とその 3 倍音（5 度）が強く、`C/E` の E と B が `Em` を押す（誤りのルートとの差で +4 が一番多いのと合う）。

| 案                              | 中身                                                                                                                                                                        | 費用・リスク                                                                                |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **M3 2 段階で決め直す**（最初） | 区間ごとに、ベースの段階の音 b と高い帯域の音から、b を含む和音を選び直す。差が小さいときは基本形。`redecideRoot` を一般にしたもの。音が同じ組は対象外（§2.3 だけが決める） | 安い。スパイク 6 の結論 4（直した数と壊した数がほぼ同じ）があるので、壊した数を必ず表に出す |
| **M1 高い帯域のクロマ**         | 型の採点に、全帯域からベース帯域（計算済みの `cols.bass`）を引いたものを使う                                                                                                | 左手だけがルートを弾く形でルートが消える。合成の「ピアノだけ」で見る                        |
| **M2 ベースつきの型**           | 状態を（ルート・種類・ベースの度数）に広げ、高い帯域の点＋重み × ベースの点                                                                                                 | 状態の数の 2 乗で時間が増える。M1・M3 で足りないときだけ                                    |

### 2.2 V: 語彙の段階（T10〜T12。段階ごとに関門）

足し方は今の「はっきり勝ったときだけ」の差（`vocab_margin`）と同じ守り。遷移の後押しは、v1a の `harmony.json` を読み、新しい種類をノート §1.4 の種類の仲間へ写す小さな対応（`ts/chords2/` の定数。JSON・TOML は作らない）で引く。写し方は T2 でノートを直してから。状態の数は 12 × 種類の数（今 120）。

| 段階   | 足す種類                                                | 状態 | 生まれる取り違え                                                                                                                                        |
| ------ | ------------------------------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **V1** | `mM7`・`m6`・`6`                                        | 156  | 音が同じ: `C6` = `Am7`、`Am6` = `F#m7b5`。含む: `CmM7` ⊃ `Ebaug`、`m6`・`6` ⊃ 3 和音                                                                    |
| **V2** | `sus2`・`7sus4`・`add9`・`madd9`                        | 204  | 音が同じ: `Csus2` = `Gsus4`。含む: `C7sus4` ⊃ `Csus4`・`Fsus2`、`Cadd9` ⊃ `Csus2`・`C`、`Cmadd9` ⊃ `Csus2`・`Cm`                                        |
| **V3** | `9`・`m9`・`M9`（5 度を省いた形も同じ種類の型に入れる） | 240  | ルートを省いた弾き方で音が同じ: `C9` → `Em7b5`（= `Gm6`）、`Cm9` → `Ebmaj7`、`CM9` → `Em7`。5 音の型が 4 音の和音に勝ちやすい（型の大きさで点をならす） |

分け方の理由: V1 は今の 3 和音に 1 音足すだけで、内声のクリシェに要る組。V2 は 2 度（9 度）の音を初めて読み、V3 の土台になる。V3 は 5 音・省いた音・ルートの無い弾き方が重なり一番難しいので最後。V3 で 9 の名前を出すのはベースがルートを示すときだけ（ほかは上の和音を出し、9 は候補）。
名前（T3 で app の表示と合うか確かめる）: `mM7`・`m6`・`6`・`sus2`・`7sus4`・`add9`・`madd9`・`9`・`m9`・`maj9`（今の `maj7` に合わせる）。

### 2.3 音が同じ組の読み分け（決定 8。T9 の部品、V1 から使う）

**順**: v2 の Viterbi と M3 の後に 1 回だけ動く後処理。音の集合が同じ組（例 {`C6`, `Am7`}）の区間ごとに、組の中の読みを**この点だけで**選び直す（HMM の点には足さないので二重に数えない）。左から順に決め、前は決めた読み、次は Viterbi の読みを使う。
**点**（読み r ごと。値はノートの段の値で固定し、調整しない）:

- ベース: b が r のルートなら ＋1.0。
- 前後: 前 → r と r → 次の移り方の段の値（強 1.0・中 0.6・弱 0.3。`harmony.json` と T2 の写し）× 調の確信度（ノート §1.3・§2.2〜2.5・§6.1〜6.2）。
- ルートの続き: r のルートが前か次と同じなら ＋0.6（内声のクリシェ。ノートへ足す。T2）。

一番高い読みを出し、差が 0.3（弱い段の値）以内の読みは候補（結果の `chordCandidates`）。同点は今の語彙の読み。aug・dim7 の同点は今の `ROOT_TIE` のまま（この規則の外）。
**正解と測り方**: 組の正解は T2 の「正解表」（例の進行と読み、ノートの § つき）で、規則を走らせる前にユーザーが確かめる（U2）。ベースのルートと正解の読みのルートが違う「食い違う例」を組の点の 1/3 にする。出した読みの当たりと候補の上位 3 の当たりを、食い違う例・食い違わない例に分けて、「ベースだけ」「音だけ」の読みと並べる。

**止める目安**（G1 で確定）: 調整用の合成で 2 回調整しても、適合率 < .60、または後戻り > .02 が差（`vocab_margin`）で直らない、または時間が予算を超える。そのときは止める案を出し、ユーザーが決める。止めても前の段階は残す。
**ホールドアウトの判定**（G1 で確定）: 開発用との差が合成 .10・録音 .15 以内（スパイク 6 と同じ）。

## 6. アプリへの道（main の §2.1 の決まり。スパイクではやらず、一覧だけ作る）

- main へは `chore/<issue>-analysis-sync-<commit>` の「写し直し」の PR だけ。v2 を採用するなら `src/lib/analysis/` に v2 を写し、`origin.ts` の `ORIGIN_COMMIT` と `CHORDS_CONFIG_HASH`（今 `adec583eb3c6`）を v2 の値に、固定のテストの答えを研究ブランチの v2 で作り直す。
- `/X` を出すには、スパイク 6 のベースの段階（`ts/bass/` の一部）も写す（今の main には無い）。Worker の空きは約 3.2 KB で、ベースの段階だけで +3.4 KB なので、遅延読み込みの塊にするかは main で決める。
- 結果に足す欄: `chords[].bass`（既存）と `chordCandidates`（音が同じ組のもう一方。スパイク 6 の `bassCandidates` と同じ形）。アプリはコード名の文字をそのまま使い、移調は種類を変えない。
